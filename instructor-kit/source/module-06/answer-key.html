2.4 · Touch and Input: self-check

Q1
The lesson's PressLog: a volunteer holds the Try me button for a full second, then lifts. What does the log show?
A) pressIn → press → longPress
B) pressIn → pressOut → press
C) pressIn → longPress → pressOut
D) longPress only
Why: Holding gives pressIn, then longPress at 500 ms, then pressOut when the finger lifts, and no press: when you handle a long press, the tap does not count as well. The kit ran the lesson's PressLog in Jest with a real hold: long press: pressIn → longPress → pressOut (the lesson measured the same in the web preview).
A is wrong: There is no press after a handled long press.
B is wrong: That is a quick tap.
D is wrong: pressIn always comes first: it starts the pressed look.
Q2
Predict: the search field's clear button gets onClick={() => onChangeText('')} instead of onPress. What do npx tsc --noEmit and npx expo lint print, and what happens when a finger taps it?
<Pressable
  onClick={() => onChangeText('')}
  accessibilityRole="button"
  accessibilityLabel="Clear search"
  hitSlop={8}
>
tsc prints nothing; lint prints only its two env: lines (no problem); the tap does nothing
Why: React Native 0.88's types accept onClick on any view (keyboards and other pointing devices), so nothing complains. Pressable puts its own click handler on top of yours: taps go to onPress. The kit ran both checks on the finished app with this change.
Q3
npx tsc --noEmit prints this after a change to SearchField.tsx. What is the fix?
src/components/SearchField.tsx:22:43 - error TS18048: 'event.target' is possibly 'undefined'.

22         onChange={(event) => onChangeText(event.target.value)}
                                             ~~~~~~~~~~~~

src/components/SearchField.tsx:22:56 - error TS2551: Property 'value' does not exist on type 'number | ReactNativeElement'. Did you mean 'valueOf'?
  Property 'value' does not exist on type 'number'.

22         onChange={(event) => onChangeText(event.target.value)}

Found 2 errors in the same file, starting at: src/components/SearchField.tsx:22
A) onChange={(event) => onChangeText(event.target?.value ?? '')}
B) onChangeText={onChangeText}
C) onChange={(event) => onChangeText(String(event.target))}
D) Add // @ts-expect-error above the line
Why: In React Native an event's target is a reference to a native view, not an element with a value. onChangeText hands you the new text as a string, so the setter goes straight in (the kit's run is the lesson's card).
A is wrong: There is no value to read: the field would always be ''.
C is wrong: That is the view's number or object, not the text.
D is wrong: Silencing the checker leaves a field that never updates.
Q4
Shoreline Crew's Button has minHeight: 48. Why not height: 48?
A) height is not allowed on a Pressable
B) minHeight is faster to lay out
C) With larger text the button can still grow instead of cutting its words
D) Android ignores height
Why: 48 is the finger-sized minimum (Apple asks 44 pt, Android 48 dp; the course uses 48 for both). minHeight keeps that minimum and still lets the button grow when a volunteer has made their text larger (Lesson 2.1).
A is wrong: It is allowed; it just stops growing.
B is wrong: Layout speed is not the reason.
D is wrong: Both platforms honor height.
Q5
The Show details button tells screen readers whether the details are open. Which prop does Shoreline Crew use, and why?
A) aria-expanded: the web preview passed it on, and React Native reads it first on phones
B) accessibilityState={{ expanded }}: the only one phones understand
C) accessibilityHint: hints carry state
D) None: the words Show and Hide are enough
Why: React Native accepts both names; its Pressable reads aria-expanded first. In the web preview only aria-expanded arrived (react-native-web ignored accessibilityState), so the course writes state with aria-* names and keeps accessibilityRole and accessibilityLabel.
B is wrong: Phones read both; the web preview only aria-expanded.
C is wrong: A hint describes what happens, not a state.
D is wrong: Words change, but a screen reader announces state from the state prop.
Q6
Which keyboardShouldPersistTaps value lets a tap on the clear button reach the button while the keyboard is open, and still closes the keyboard on a tap on empty space?
A) 'never' (the default)
B) 'always'
C) Leave it out and add hitSlop
D) 'handled'
Why: With 'never' the first tap outside the field only closes the keyboard, and "children will not receive the tap" (React Native's description). 'handled' gives a tap that a button handles to the button; empty space still closes the keyboard. Screen sets it once for every scrolling screen. Only a phone shows this (the web preview has no on-screen keyboard).
A is wrong: That swallows the first tap: volunteers tap twice and think the app is slow.
B is wrong: Then a tap on empty space no longer closes the keyboard.
C is wrong: hitSlop makes the target bigger; the tap is still swallowed.
Q7
npx tsc --noEmit prints this for SwitchRow.tsx (first lines). Which words tell the whole story, and what is the fix?
src/components/SwitchRow.tsx:20:9 - error TS2322: Type '(value: boolean) => void' is not assignable to type '(event: Readonly<{ bubbles: boolean | undefined; cancelable: boolean | undefined; currentTarget: number | ReactNativeElement; defaultPrevented: boolean | undefined; ... 11 more ...; type: string | undefined; }>) => void | Promise<...>'.
  Types of parameters 'value' and 'event' are incompatible.
"Types of parameters 'value' and 'event' are incompatible": onChange gets an event, not the new value; use onValueChange={onValueChange}
Why: Switch also has onChange, and it hands you an event. onValueChange hands you the new boolean, like a checkbox's checked in React (the kit's run matches the lesson's shortened card).

Found 1 error in src/app/index.tsx:90
A) IntrinsicAttributes
B) TouchableNativeFeedback: React Native's own Button, which takes a title
C) label: Shoreline Crew's Button
D) Omit: a Button with props removed
Why: React Native's core Button is built from the old touchables and takes a title; the type after ref? names TouchableNativeFeedback. Fix the import: import { Button } from '@/components/Button'; (Exercise 3; the kit's run is the lesson's card).

Q9
A field has inputMode="numeric". A volunteer types 12. What does onChangeText hand you?
A) The number 12
B) The string '12'
C) NaN until the field loses focus
D) An event with a value property
Why: The number keyboard only changes the keys: the value is still a string. Turn it into a number yourself (Lab 2.4's parseBags) or with Zod (Lesson 5.4).
A is wrong: No input type converts it.
C is wrong: Nothing is converted.
D is wrong: That is onChange, and it has no value either.
Q10
matchesSearch(event, site, '') (an empty search box). What does it return, and why?
A) true: an empty query has no words, and every() on an empty list is true
B) false: there is nothing to match
C) It throws: split of an empty string
D) true only for the first cleanup
Why: ''.split(/\s+/).filter(Boolean) is [], and [].every(...) is true: an empty search shows every cleanup, which is what a volunteer expects.
B is wrong: every on an empty list is true, not false.
C is wrong: Splitting an empty string is fine.
D is wrong: The same rule runs for every cleanup.
Q11
Every card's button has accessibilityLabel={${showDetails ? 'Hide' : 'Show'} details for ${event.title}}. Give two reasons for this label.
eight buttons all called "Show details" are indistinguishable to a screen reader; starting with the visible words lets voice control ("tap Show details") still find it
Why: On a phone the label replaces what is read, so it names the cleanup (the HQ used hidden text for the same job), and it begins with the words on the screen.
Q12
The clear button is 32 by 32 with hitSlop={8}. In the web preview you click 4 pixels outside its circle. What happens, and on a phone?
A) It clears in both
B) Nothing in the web preview (it ignores hitSlop); on a phone the finger's 48 by 48 area clears it
C) It clears in the web preview only
D) A red screen: hitSlop needs a number per side
Why: The course measured it: react-native-web ignores hitSlop (a click 10 px outside a hitSlop of 20 missed). On a phone React Native's Pressable uses it. A mouse is precise; fingers are the problem hitSlop solves.
A is wrong: The web preview ignores hitSlop.
C is wrong: It is the other way round.
D is wrong: A single number means the same on every side.

The Lesson Page's Own Quick Quiz

Lesson 2.4 · Touch and Input
  1. B The button looks pressed, then not; the details stay closed: onPressIn and onPressOut run (the button shows and then drops its pressed look), but onPress only runs when the finger lifts while still on the control. Sliding off is how people cancel a tap.
  2. D tsc reports errors; the fix is onChangeText={setQuery}: tsc reports that event.target may be undefined and that value does not exist on it: a native event's target is a reference to a view, not an element with a value. onChangeText={setQuery} hands you the text directly.
  3. A The keyboard closes and the text stays; a second tap clears it: With the default, never, a tap outside the field while the keyboard is open only closes the keyboard, and the button never receives it. keyboardShouldPersistTaps handled lets the button handle the tap.
  4. C accessibilityLabel="Clear search" on the Pressable: An icon-only control has no words of its own, so the Pressable carries them in accessibilityLabel (with accessibilityRole button). In the web preview it became aria-label.
  5. A hitSlop={8}: hitSlop extends the area that reacts to touches beyond the drawn box: 32 plus 8 on each side is 48. On a phone, that is; the web preview ignores hitSlop, which is fine for a precise mouse pointer.

Exit Ticket

  1. Web habits: onClick → onPress; onChange + event.target.value → onChangeText; a Switch's onChange → onValueChange; a 36-high target → minHeight 48 (and hitSlop); nothing → keyboardShouldPersistTaps="handled". Any two.
  2. A hold: pressIn, onLongPress (when there is one), pressOut; onPress does not run.
  3. "handled": a tap that a button handles reaches the button while the keyboard is open; a tap on empty space still closes the keyboard.

Common Wrong Answers and What They Reveal

  • Q1 A or B. Thinks a long press is a slow tap. Run the PressLog demo again.
  • Q2 "tsc catches it". Trusts types to know the platform. Show P1.
  • Q3 A. Patches the web habit instead of dropping it. Ask what target is.
  • Q6 A or B. Has not met the swallowed tap; it only shows on a phone: pair them with a phone owner.
  • Q9 A. Expects the keyboard to convert values: back to Zod in 5.4.
  • Q12 A or C. Treats the web preview as a phone (Lesson 1.1's warning).
