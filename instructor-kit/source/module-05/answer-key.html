Session 5: Images, Icons, Fonts and Safe Areas

Answers and reasoning for every Session 5 item: the warm-up, the self-check, the predict-then-check items, the lab reference outputs, the demo files, the lesson page's own quiz and the exit ticket.

Session 5 12 self-check items Confidential

Warm-up: Lesson 2.2, Retrieved

  1. A View holds a title and a badge, with no style. Do they sit side by side or one under the other, and why? Answer: One under the other: every View is a flex container whose default flexDirection is 'column' (CSS's is row).
  2. In a row, a long title pushes the badge off the right edge on a phone (the web preview looked fine). Which one style fixes it, and on which element? Answer: flex: 1 (or flexShrink: 1) on the Text: text in a row gets flex: 1 so it wraps; React Native's flexShrink defaults to 0.
  3. Why does Shoreline Crew's Screen give its outermost View flex: 1? Answer: So the screen fills the space the navigator gives it, not just its content's height (the page color reaches the bottom).

2.3 · Images, Icons, Fonts and Safe Areas: self-check

Q1
Exercise 2's logo: <Image source={require('@/assets/images/splash-icon.png')} accessibilityLabel="" /> from expo-image, with no style. The file is 400 by 400. What shows?
A) The logo at 400 by 400, the file's own size
B) Nothing: the picture is 0 by 0
C) A red error screen: a required picture needs a size
D) The logo at 24 by 24, the default icon size
Why: expo-image never sizes itself from the file, even for a require()d one: the course measured 0 by 0 (React Native's own Image would have used the file's 400 by 400). No error, no warning. Every expo-image gets a size: a width and height, or a width from its parent plus an aspectRatio (Lesson 2.3, the size rule).
A is wrong: That is React Native's own Image with a required file; expo-image does not do it.
C is wrong: Nothing complains: that is why it is a silent mistake.
D is wrong: 24 is expo-symbols' default icon size, not a picture size.
Q2

const icons = {

tsc prints nothing (a plain SF Symbol name is a valid name); Android and the web preview show no icon at all
Why: name accepts a plain SF Symbol too, so the table type-checks (the kit ran it on the finished app: no output). Only iOS can draw it; on Android and the web there is no name for the platform and no fallback, so nothing. Give all three names (Lab 2.3, Task 2).

Q4
Why does Shoreline Crew describe each site picture with accessibilityLabel instead of expo-image's alt?
A) alt is only for local pictures
B) Screen readers on phones ignore alt
C) With alt alone, the web preview's picture had no alt attribute (expo-image 58); accessibilityLabel works everywhere
D) accessibilityLabel makes the picture load faster
Why: expo-image's docs list alt as another name, and on phones it is (the kit's Jest run on iOS turned alt into the label). In the web preview, alt alone gave the loaded <img> no alt at all, which cost the course a failed accessibility check; accessibilityLabel became the alt. One prop that works everywhere.
A is wrong: Both kinds of source take a description.
B is wrong: On phones alt is read; the web preview is the problem.
D is wrong: A description has nothing to do with loading.
Q5
The card's picture gets { aspectRatio: site.image.width / site.image.height } and no width. What gives it its width?
A) expo-image measures the file when it arrives
B) The card: a column stretches its children across
C) aspectRatio sets both width and height
D) Nothing: it needs width: '100%' as well
Why: Lesson 2.2's flexbox: a column stretches its children across (alignItems: 'stretch'), so the picture is as wide as the card, and aspectRatio turns that width into a height before the picture arrives. That is the noticeboard frame: pinned up first, the right shape.
A is wrong: Layout happens before the picture arrives; expo-image never sizes itself.
C is wrong: aspectRatio only relates the two; one of them must come from somewhere.
D is wrong: The stretch already gives the width (the lesson's snippet uses width: '100%' for a picture outside a column).
Q6
_layout.tsx says const ready = fontsLoaded || fontError !== null;. What would happen with const ready = fontsLoaded; on a phone where Outfit fails to load?
A) The headings use the system font
B) The app shows a red error screen
C) useFonts tries again every second
D) The splash screen never goes away
Why: useFonts returns [loaded, error]. If loading fails, loaded stays false; with ready = fontsLoaded the layout keeps returning null and never calls SplashScreen.hideAsync(). "A volunteer with a slightly plainer heading is fine; a volunteer stuck on a splash screen is not."
A is wrong: That is what the lesson's version does: it treats an error as ready.
B is wrong: A failed font is an error value, not a crash.
C is wrong: useFonts does not retry.
Q7
npx tsc --noEmit prints this after a change to typography.ts. What was the change, and what would a phone have shown if fonts were plain strings without satisfies?
src/theme/typography.ts:10:3 - error TS2820: Type '"Outfit_700bold"' is not assignable to type '"Outfit_600SemiBold" | "Outfit_700Bold"'. Did you mean '"Outfit_700Bold"'?

10   title: 'Outfit_700bold',
     ~~~~~


Found 1 error in src/theme/typography.ts:10
title: 'Outfit_700bold' (a lowercase b); without the typed names the titles would silently use the system font
Why: A misspelled fontFamily is not an error anywhere: the web preview drew the browser's default font, iOS only logs "Unrecognized font family". typography.ts's as const satisfies Record<string, keyof typeof fontFiles> turns the typo into TS2820 with a Did you mean (the kit's run is the lesson's card).
Q8
A heading style says fontFamily: 'Outfit_600SemiBold', fontWeight: 'bold'. It looks bold in the web preview. On a phone?
A) Maybe bold, maybe semibold, maybe the system font: do not depend on it
B) Always bold: React Native fakes a bold weight
C) A tsc error: fontWeight is not allowed with a fontFamily
D) The phone downloads Outfit's bold weight
Why: Each weight of a loaded font is its own family. A browser fakes a bold version; React Native's fontFamily documentation does not promise that on phones. Pick the weight by its family name (Outfit_700Bold) and add the weight to fontFiles.
B is wrong: That is the browser's behavior, not a promise on phones.
C is wrong: Both props type-check.
D is wrong: Only the weights you import ship in the app; nothing downloads.
Q9
The lesson's Screen, run headless with a notched phone's insets (47 at the top, 34 at the bottom). Which line is a detail screen under a header bar (Lesson 4.1)?
notch, all four edges (Cleanups)     frame paddingTop 47 · content paddingBottom 50
notch, edges={['bottom','left','right']} frame paddingTop 0 · content paddingBottom 50
web preview (every inset is 0)       frame paddingTop 0 · content paddingBottom 16
A) The first: every screen should add every inset
B) The third: a header removes every inset
C) None: a header bar needs SafeAreaView from react-native
D) The second: the header already pads the top, so the frame adds 0 there
Why: A header bar already sits below the status bar and pads itself; adding insets.top again gives an empty band. So a screen under a header leaves 'top' out of its edges, and keeps the bottom inset inside the scrolling content (the lesson's quiz Q4).
A is wrong: Under a header that doubles the top inset (Common Mistakes).
B is wrong: The third line is the web preview, where every inset is 0.
C is wrong: React Native's SafeAreaView is deprecated and never handled Android.
Q10
A detail screen ends with a bar pinned to the bottom (it does not scroll) holding a Sign up button. Where does the bottom inset go?
A) Nowhere: the home indicator is transparent
B) On the ScrollView's contentContainerStyle above the bar
C) On the bar's own paddingBottom, so its background reaches the glass and the button stays above the indicator
D) On the Sign up button's marginBottom
Why: Only scrolling content carries the bottom inset inside its contentContainerStyle. A bar that does not scroll pads itself: paddingBottom = its own padding + insets.bottom (Lesson 2.3, Scrolling screens; Lab 2.3 Task 3).
A is wrong: The indicator is drawn on top of your app: a button under it is hard to press.
B is wrong: The bar is below the scroll view; the inset belongs to whatever touches the bottom edge.
D is wrong: A margin leaves a band of page color under the bar instead of the bar's background.
Q11

Why: The kit rendered it once in Jest: React Native printed that warning (with a link to the library). React Native's own version only ever worked on iOS. The library's SafeAreaView takes edges; the hook gives the numbers.
Q12
You copied the six icon files and edited app.json. Which of these can you check today, without a build?

B) Shoreline Crew's icon under Expo Go on your phone

B is wrong: Expo Go shows its own icon: it is the installed app.
C is wrong: Expo's docs recommend a development build for testing the splash screen.

Demo files (Live demo 2, "What Screen does with a notch")

In a copy of labs/module-05/l2_3-images-icons-fonts-and-safe-areas/solution/: the stage's Screen.tsx, theme/colors.ts and theme/spacing.ts copied into src/ (Screen's two @/theme/ imports changed to ./theme/), and this test as src/insets.test.tsx. It renders Screen inside a SafeAreaProvider with a notched phone's insets and writes what Screen hands the native scroll view:

import { render, screen } from '@testing-library/react-native';
import { Image } from 'expo-image';
import { StyleSheet, Text } from 'react-native';
import { SafeAreaProvider } from 'react-native-safe-area-context';

import sites from '../fixtures/sites.json';
import { Screen } from './Screen';
import { SitePicture } from './SitePicture';
import type { Edge } from 'react-native-safe-area-context';
import type { Site } from './types';

type Host = { type: string; props: Record<string, unknown>; children: Host[] | null };
const lines: string[] = [];
const phone = (top: number, bottom: number) => ({
  frame: { x: 0, y: 0, width: 390, height: 844 },
  insets: { top, right: 0, bottom, left: 0 },
});

// What Screen hands the native scroll view: the frame's style and the content's style, flattened
async function screenWith(name: string, top: number, bottom: number, edges?: Edge[]) {
  await render(
    <SafeAreaProvider initialMetrics={phone(top, bottom)}>
      <Screen scroll edges={edges}>
        <Text>Upcoming cleanups</Text>
      </Screen>
    </SafeAreaProvider>,
  );
  const scroll = (screen.toJSON() as Host).children![0];
  const frame = StyleSheet.flatten(scroll.props.style as object) as { paddingTop: number };
  const content = StyleSheet.flatten(scroll.props.contentContainerStyle as object) as { paddingBottom: number };
  lines.push(`${name.padEnd(36)} frame paddingTop ${frame.paddingTop} · content paddingBottom ${content.paddingBottom}`);
}

test('Screen and the safe area, headless', async () => {
  await screenWith('notch, all four edges (Cleanups)', 47, 34);
  await screenWith("notch, edges={['bottom','left','right']}", 47, 34, ['bottom', 'left', 'right']);
  await screenWith('web preview (every inset is 0)', 0, 0);
  await render(<Image source={(sites as Site[])[0].image.url} />);
  lines.push(`${'expo-image with no style'.padEnd(36)} style ${JSON.stringify((screen.toJSON() as Host).props.style)}`);
  await render(<SitePicture site={(sites as Site[])[0]} />);
  const style = StyleSheet.flatten((screen.toJSON() as Host).props.style as object) as { aspectRatio: number };
  lines.push(`${'the lab card picture'.padEnd(36)} aspectRatio ${style.aspectRatio.toFixed(3)} (1200 / 675)`);
  const fs = require('fs') as { writeFileSync(file: string, text: string): void }; // Node's, inside Jest
  fs.writeFileSync('insets.txt', lines.join('\n') + '\n');
});

The Lesson Page's Own Quick Quiz

Lesson 2.3 · Images, Icons, Fonts and Safe Areas
  1. D Nothing: the picture is as wide as the card but 0 tall: A picture from a server has no size when the screen is laid out, and expo-image never sizes itself from the file, so the image stretches across the card but is 0 tall. Give it a width and height, or let the parent set the width and add aspectRatio.
  2. B The iPhone shows a calendar; Android and the web preview show no icon at all: A plain SF Symbol name only works on iOS. On Android and the web, expo-symbols finds no name for the platform and draws the fallback, which is nothing. Give the object with ios, android and web names.
  3. A So the first screen appears only once Outfit is ready, instead of jumping from the system font: Until useFonts has registered Outfit, headings would draw in the system font and then jump. Keeping the splash screen up until the fonts are loaded (or have failed) means the first screen appears in its final font.
  4. C ['bottom', 'left', 'right']: The header bar covers the top edge and pads itself below the status bar, so the screen adds only the edges nothing else covers. Adding the top inset again would leave an empty band under the header.
  5. B The installed app is Expo Go; your icon only appears in your own build: The app installed on the phone is Expo Go, so the home screen shows Expo Go's icon. Your own icon and native splash screen are built into your own app: a development build in Module 9.

Exit Ticket

  1. Three silent mistakes: an expo-image with no size (0 tall); a plain SF Symbol name (no icon on Android or the web); a misspelled fontFamily (the system font). Each made loud: the size rule, the three-name table, typed family names.
  2. Typed family names: a misspelled family becomes TS2820 with a Did you mean, instead of a silently wrong font on every platform.
  3. Under a header: ['bottom', 'left', 'right']: the header pads itself below the status bar; adding the top inset again leaves an empty band.

Common Wrong Answers and What They Reveal

  • Q1 A. Expects expo-image to behave like React Native's Image (or a browser). Show the lesson's measured table.
  • Q2 "tsc catches it". Expects a type to promise a platform; a plain SF name is a valid name. Run P1.
  • Q5 A or D. Has not connected flexbox's stretch with the picture's width: back to Lesson 2.2's column default.
  • Q6 A. Reads the lesson's version instead of the question's: point at the || fontError !== null.
  • Q9 A. "Every inset everywhere, to be safe" is the double-inset bug of Lesson 4.1. Draw the header over the status bar.
  • Q12 B. Expects Expo Go to become your app; it is the installed app. Module 9 makes your own.
