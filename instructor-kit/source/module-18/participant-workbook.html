7.1

Animation with Reanimated 4

By the end you can
  • Explain why phone animations run on the UI thread, and what shared values and worklets do about it
  • Animate with shared values: useSharedValue, useAnimatedStyle, withTiming, withSpring and withSequence, read and written with get() and set()
  • Hand a value from the UI thread back to React with useAnimatedReaction and scheduleOnRN, without drawing the screen 60 times a second
  • Use Reanimated 4's CSS-style transitions and keyframe animations, and choose between them and shared values
  • Respect the phone's Reduce Motion setting: know what Reanimated does about it by itself, and what it leaves to you
Key ideas
  • Two threads, one frame: the JavaScript thread runs React, queries and the queue; the UI thread draws and reads touches. A frame has 16.7 ms (8.3 at 120 Hz). Animating with setState per frame is only as smooth as the busiest thing on the JavaScript thread.
  • Shared values and worklets: useSharedValue, read with get() and written with set() (never .value with the React Compiler, never while rendering); useAnimatedStyle runs on the UI thread; useAnimatedReaction + scheduleOnRN hand a value back to React, as rarely as possible.
  • Timing or spring: withTiming lands exactly (numbers, bars, opacity); withSpring moves like an object and may overshoot (a bounce); withSequence, withDelay, withRepeat chain them; the finished callback runs on the UI thread.
  • CSS-style transitions and keyframes live in an Animated view's style: transitionProperty/transitionDuration for a style that changes, animationName (the keyframes object itself) for a loop.
  • Reduce Motion: Reanimated's functions jump to the end by default (ReduceMotion.System); CSS-style ones do not, so check useReducedMotion(). Both read the setting once, at start.
Worked example: the skipper and the helm, in code

The heart of Tally.tsx, from the finished code. Read it as the skipper and the helm: React sets the destination once (count.set(withTiming(value, ...))), the UI thread moves count every frame, and the reaction calls React back only when the number reaches a new whole step:

shoreline-crew/src/components/Tally.tsx
  // On the UI thread, every frame: has the count reached a new step? Then tell React (JS thread).
  useAnimatedReaction(
    () => Math.round(count.get() * steps),
    (step, previous) => {
      if (step !== previous) {
        scheduleOnRN(setShown, step / steps);
      }
    },
  );

  // Count when the screen comes into view, and when the value changes while it is in view
  useFocusEffect(
    useCallback(() => {
      if (count.get() === value) {
        return;
      }
      setCounting(true);
      const counted = {
        duration: 900,
        easing: Easing.out(Easing.cubic), // fast at first, slowing down at the end
        reduceMotion: ReduceMotion.System, // the default, written out: Reduce Motion on = jump to the end
      };
      count.set(
        withTiming(value, counted, (finished) => {
          // Runs on the UI thread when the count stops (finished is false if something interrupted it)
          if (finished) {
            scheduleOnRN(setCounting, false);
            // A bounce: grow quickly, then spring back. dampingRatio below 1 lets it overshoot a little.
            scale.set(
              withSequence(
                withTiming(1.2, { duration: 120 }),
                withSpring(1, { dampingRatio: 0.35, duration: 500 }),
              ),
            );
          }
        }),
      );
    }, [count, scale, value]),

Two shared values (count on its way, scale resting at 1), one state for the number shown. steps is 10 for kilograms (one decimal), 1 for pieces. With Reduce Motion on, withTiming jumps to the end by itself (ReduceMotion.System, written out in counted).

7.2

Gestures

By the end you can
  • Explain why React Native apps read gestures with React Native Gesture Handler, on the UI thread, and set it up with GestureHandlerRootView
  • Build a drag with usePanGesture and GestureDetector that moves a view through Reanimated shared values and springs it into place when the finger lets go
  • Make a sideways swipe share the screen with vertical scrolling (activeOffsetX, failOffsetY) and combine gestures on one view
  • Give every gesture a way that needs no gesture, and keep swipe rows correct in a recycled FlashList
  • Decide what a swipe may do to data that has not reached the server yet
Key ideas
  • Gesture Handler reads touches on the UI thread; its callbacks are worklets that write shared values, so a view follows the finger with no React render; scheduleOnRN tells React the result.
  • One GestureHandlerRootView (with flex: 1) around the whole app, in the root layout. Without it, a phone in development stops with a red screen; the web preview carries on.
  • Gesture Handler 3 Hooks: usePanGesture({ ... }) + <GestureDetector>; callbacks onBegin, onActivate, onUpdate, onDeactivate, onFinalize (not onStart/onEnd). The finger drives, a spring finishes.
  • Sharing the finger: activeOffsetX and failOffsetY let a swipe and a scroll share a touch; useExclusiveGestures, useCompetingGestures and useSimultaneousGestures combine gestures on one view.
  • Another way, and the data rule: every gesture has a visible button (WCAG 2.5.1); phone-only data is never removed without asking, never while sending; in a recycled list, swipe state lives in the parent, keyed by id.
Worked example: the deckhand on the line, in code

SwipeToRemove's pan, from the finished code. The config says when the gesture may start (the two offsets), what the finger does while it moves (onUpdate) and what letting go means (onDeactivate):

shoreline-crew/src/components/SwipeToRemove.tsx
  const pan = usePanGesture({
    enabled,
    activeOffsetX: [-12, 12], // 12 points sideways first: this is a swipe...
    failOffsetY: [-10, 10], // ...10 points up or down first: a scroll, so the swipe lets go
    // These run on the UI thread, many times a second, while the finger moves
    onUpdate: (event) => {
      offset.set(Math.min(0, event.translationX)); // follow the finger, leftwards only
    },
    onDeactivate: (event) => {
      if (offset.get() < -reach || event.velocityX < flick) {
        scheduleOnRN(onSwipe); // React decides what a swipe means
      }
      offset.set(withSpring(0)); // back into place, from wherever the finger let go
    },
  });

Both callbacks are worklets: they run on the UI thread, many times a second. Math.min(0, ...) lets the row go left only. Far OR fast asks; scheduleOnRN(onSwipe) tells React, which shows the question. withSpring(0) brings the row home either way (instantly with Reduce Motion on).
