Session 18 12 self-check items Confidential

Refresher

  1. Lesson 5.5's queue: a debris log is saved with no signal. Where does it wait, and what sends it later? **Answer:** In the log queue (a Zustand store saved on the phone), shown under "Not sent yet" in the Logbook; the queue sender sends waiting logs when the phone is online again (or with Send now). Lesson 7.1's tally counts what arrives; Lesson 7.2 lets a waiting log be swiped away.
  2. Lesson 4.3's useFocusEffect: when does its function run, compared with useEffect? **Answer:** When the screen comes into view (and again when its dependencies change while it is in view), not only when the component mounts: a tab you are not looking at stays still. Tally starts its count with it.
  3. Lesson 2.5's createThemedStyles: what does it give a component? **Answer:** A useStyles() Hook whose StyleSheet is built from the current theme's colors (light or dark). Tally and SwipeToRemove take their colors from it (colors.pressed, badges.danger).
  4. Lesson 3.2's FlashList: what does it do with a row that scrolls off the screen? **Answer:** Recycles it: the same row component is reused for another item, with whatever state it holds. Lesson 7.2 builds on that: swipe state lives in the parent, keyed by id.

7.1 · Animation with Reanimated 4: self-check

Q1
While the tally counts from 42 to 44, TanStack Query parses a long logbook answer. Which version stays smooth on a phone, and why?
A) A setInterval that calls setShown 30 times a second: timers run on their own thread
B) A shared value animated with withTiming: the UI thread works out every frame without the JavaScript thread
C) A useEffect that calls setShown once per frame: React batches the updates
D) Neither: animations on a phone always stutter while data loads
Why: React says once where the value should go (the skipper); the UI thread steps it frame by frame (the helm). A busy JavaScript thread cannot make it late. Timers and setState per frame both need the JavaScript thread for every frame (Lesson 7.1, Two Threads, One Frame).
A is wrong: JavaScript timers fire on the JavaScript thread: late whenever it is busy (the lesson's setInterval question).
C is wrong: Every frame would still need React and the JavaScript thread.
D is wrong: That is exactly the problem Reanimated solves.
Q2
A teammate writes count.value = withTiming(...) in Tally.tsx. npx expo lint prints this. Which change fixes it?
~/shoreline/shoreline-crew/src/components/Tally.tsx
  63:7  error  Error: This value cannot be modified
> 63 |       count.value = withTiming(value, counted, (finished) => {
     |       ^^^^^ `count` cannot be modified
  ...  react-hooks/immutability
✖ 1 problem (1 error, 0 warnings)
A) Add // eslint-disable-next-line above the line
B) Make count a let instead of a const
C) Write count.set(withTiming(...)), and read with count.get()
D) Switch the React Compiler off in app.json
Why: The React Compiler's lint rules treat what a Hook returns as unchangeable. set() and get() do the same thing as a method call, which the compiler leaves alone, and Reanimated recommends them for compiled code (Lesson 7.1, Common Mistakes; the kit's run is the lesson's card).
A is wrong: Hiding the rule leaves code the compiler may optimize wrongly.
B is wrong: count is never reassigned; the rule is about changing a Hook's value.
D is wrong: The project relies on the compiler; one method call fixes it.
Q3
A progress number counts from 0 to 42 pieces. Which animation fits it?
A) withTiming(42, { duration: 900, easing: Easing.out(Easing.cubic) })
B) withSpring(42, { mass: 1, stiffness: 100, damping: 10 })
C) withSpring(42, { dampingRatio: 0.35, duration: 500 })
D) withRepeat(withTiming(42), -1)
Why: A number must land exactly on its target: withTiming ends on time and on the value. The course measured Reanimated 3's old default spring showing 49, then 41, before settling on 42: totals that were never true. Springs are for the bounce, not the count.
B is wrong: Overshoots: the measured 0 … 49 … 41 … 42.
C is wrong: A dampingRatio below 1 overshoots on purpose: right for the bounce, wrong for the number.
D is wrong: Repeats forever: a count is not a loop.
Q4
Reduce Motion is on and the app was restarted. Which of these still moves in the web preview, as the lesson measured?
A) The tally's count (withTiming)
B) The tally's bounce (withSequence of a timing and a spring)
C) FadeIn's opacity (withTiming)
D) A breathing dot with a CSS-style keyframe animation and no useReducedMotion() check
Why: Reanimated's animation functions default to ReduceMotion.System and jump to the end. The CSS-style transitions and keyframe animations do not look at the setting (measured), so the code must check useReducedMotion() itself, as SendingDot and Lab 7.1's LiveBadge do.
A is wrong: Jumps to the end: the totals appear at once.
B is wrong: Jumps to the end too: no bounce.
C is wrong: Was 1 at the first sample.
Q5
Inside useAnimatedReaction, why does Tally call scheduleOnRN(setShown, step / steps), and only when the rounded step changes? Two reasons.
The reaction runs on the UI thread, which cannot call a React setter (on a phone: the Worklets red screen); and React should draw once per visible step, not once per frame
Why: Anything that is not a worklet goes through scheduleOnRN to the JavaScript thread. The step check keeps React's work to about one render per number shown (42 renders for 42 pieces). The web preview runs worklets on its one thread, so the direct call works there: the trap.
Q6
Maya turns on Reduce Motion while Shoreline Crew (at the end of Lesson 7.1) is open, and opens her Logbook. What happens?
A) The tallies stop counting at once
B) The tallies still count: the setting was read when the app started
C) The app crashes: the setting changed underneath it
D) Only the background highlight stops
Why: Reanimated reads the setting once, at start (its documentation: changing it "doesn't cause your components to rerender"). Restart the app, or reload the web preview. Lesson 7.3 makes the app follow it live.
A is wrong: That is Lesson 7.3's code, not 7.1's.
C is wrong: Nothing crashes; the old value is simply used.
D is wrong: The highlight is a CSS-style transition: it is kept on purpose, and does not follow the setting anyway.

7.2 · Gestures: self-check

Q7
A pan copied from a Gesture Handler 2 tutorial. npx tsc --noEmit prints this. What is the fix?
src/components/SwipeToRemove.tsx:42:5 - error TS2353: Object literal may only specify known properties, and 'onEnd' does not exist in type 'PanGestureConfig'.
src/components/SwipeToRemove.tsx:42:13 - error TS7006: Parameter 'event' implicitly has an 'any' type.
Found 2 errors in the same file, starting at: src/components/SwipeToRemove.tsx:42
A) Rename onEnd to onDeactivate (Gesture Handler 3's name); the second error goes with it
B) Type the parameter: (event: any) =>
C) Use Gesture.Pan().onEnd(...) instead of the Hook
D) Install Gesture Handler 2
Why: The config object is typed: for a property it does not know, TypeScript cannot tell what event is, hence TS7006. Fix the first error and both go (Lesson 7.2, Common Mistakes; the kit's run is the lesson's card). The names are onBegin, onActivate, onUpdate, onDeactivate, onFinalize.
B is wrong: Silences the second error; the callback still never runs.
C is wrong: The builder API is deprecated in version 3.
D is wrong: SDK 58 pins 3.3.
Q8
The root layout's GestureHandlerRootView is taken out. Where does the missing root view show up?
A) In npx tsc --noEmit
B) In the web preview, as soon as a card is dragged
C) Nowhere: gestures just stop working everywhere
D) On a phone in development (a red screen), and in Jest, which renders as iOS; not in the web preview
Why: Gesture Handler checks for the root view only when __DEV__ and the platform is not web. The lesson measured the web preview carrying on; the kit rendered Lab 7.2's list without it in Jest (jest-expo renders as iOS) and got the phone's message word for word.
A is wrong: Types are fine: nothing in the code is wrong for tsc.
B is wrong: The web preview skips the check: the card still followed the mouse.
C is wrong: In development a phone stops with the error message.
Q9
In SwipeToRemove, what do activeOffsetX: [-12, 12] and failOffsetY: [-10, 10] do together?
A) Limit how far the card can move: 12 points sideways, 10 up or down
B) Make the swipe win only after 12 points sideways, and give up if the finger first moves 10 points up or down
C) Slow the card down to 12 points per frame
D) Make the swipe and the scroll run at the same time
Why: Whichever threshold the finger crosses first wins the touch: sideways first is a swipe, vertical first is a scroll. Without them, a crooked scroll moved the card 54 points (measured).
A is wrong: They are thresholds for starting, not limits on movement.
C is wrong: Nothing about speed.
D is wrong: That would be useSimultaneousGestures.
Q10
SwipeToRemove asks when offset.get() < -reach || event.velocityX < flick (reach 120, flick -800). Theo flicks a card 70 points to the left at 1,200 points per second. What happens?
A) Nothing: 70 points is short of the reach
B) It asks: a quick flick counts even when it is short
C) The card is removed at once
D) The card stays where he left it
Why: Far OR fast: -1,200 points per second is below -800. The card springs back either way, and the screen asks; nothing is removed without "Yes, remove it" (Lesson 7.2's Exercise 1; Lab 7.2 Task 1).
A is wrong: Distance is one of two ways in.
C is wrong: A swipe only asks.
D is wrong: withSpring(0) brings it back.
Q11
Why does every waiting card also have a visible Remove button, and when would accessibilityActions be the better choice?
A gesture is a shortcut, never the only way (WCAG 2.5.1): the button reaches screen readers, keyboards, switch and voice control. accessibilityActions fit a row that is ONE accessible element with no controls inside
Why: The queue card has its own buttons, so it is not one accessible element: a visible Remove is the way in for everyone (Lesson 7.2, Every Gesture Needs Another Way). Lesson 8.1 audits it with a screen reader.
Q12
In a FlashList of 300 swipe rows, each row keeps const [asking, setAsking] = useState(false). Item 2 is swiped, then the list is scrolled far down. What can happen?
A) Nothing: every row has its own state
B) The app crashes when the row is recycled
C) FlashList refuses to recycle rows that have state
D) A row nobody touched asks "Item 95: remove it?": the recycled row kept Item 2's state
Why: FlashList reuses the row component for another item, state included (measured). Keep "which item is asking" in the parent, keyed by id, and pass extraData so the rows draw again (Lesson 7.2, Swipe Rows in Long Lists).
A is wrong: Recycling is exactly what shares the state.
B is wrong: No crash: a wrong question, which is worse.
C is wrong: It recycles every row.

The Lesson Pages' Own Quick Quizzes

Lesson 7.1 · Animation with Reanimated 4
  1. B So the animation stays smooth even when the JavaScript thread is busy with React, the network or the queue: React says once where the count should go and how; the UI thread works out every frame by itself. Whatever else the JavaScript thread is doing (parsing an answer, drawing a list) cannot make the animation late.
  2. D So React draws the number once per visible step, not once per frame: The count changes every frame, but the text only needs to change when it reaches a new step. Sending only new steps to React draws the component about 42 times for 42 pieces, not once per frame for a whole second.
  3. A It shows her total at once, without counting or bouncing: withTiming and withSpring default to ReduceMotion.System: with the setting on, they jump to the end. The tally shows the total at once, with no count and no bounce, and the words are the same as for everyone.
  4. C A CSS-style transition: transitionProperty: 'width' with a duration on an Animated.View: The width is a style that changes because state changed, which is exactly what a CSS-style transition is for: React draws the new width, and transitionProperty plus transitionDuration make it glide, with no shared value and no Hook.
  5. B A red screen: the UI thread cannot call a React setter, which must go through scheduleOnRN: On a phone the reaction runs on the UI thread, where a React state setter is not a worklet. react-native-worklets stops with an error about synchronously calling a Remote Function on the UI Runtime. scheduleOnRN runs the setter on the JavaScript thread instead.
Lesson 7.2 · Gestures
  1. D So the card follows the finger on the UI thread, even while the JavaScript thread is busy: Gesture Handler recognizes the gesture on the UI thread and its callbacks are worklets, so the card can follow the finger through a shared value every frame, however busy the JavaScript thread is. React only hears about the result, through scheduleOnRN.
  2. B There is no GestureHandlerRootView around the app: Gesture Handler checks for the root view in development on every platform except the web, so the web preview works while a phone stops with GestureDetector must be used as a descendant of GestureHandlerRootView. One root view around the app in the root layout fixes it.
  3. C activeOffsetX: [-12, 12] and failOffsetY: [-10, 10] on the pan gesture: activeOffsetX makes the pan wait for 12 points of sideways movement, and failOffsetY makes it give up after 10 points up or down, so a vertical drag goes to the scroll view and a sideways one to the swipe.
  4. A She moves to the card's Remove button, double taps it, then answers Yes, remove it: Every card has a Remove button, labeled with the cleanup's name for screen readers; it leads to the same question as the swipe, which is announced as a live region. The swipe is a shortcut, never the only way.
  5. B A different item, one nobody swiped, shows the question: FlashList reuses Item 2's row for an item coming on screen, and the row's own state comes with it: the course measured Item 95 asking to be removed. Keep the asking id in the parent, keyed by id, or use useRecyclingState.

Exit Ticket

  1. Timing or spring: a number must land exactly on its target, so withTiming; a spring overshoots (the measured 0 … 49 … 41 … 42), which suits a scale bounce and lies on a total.
  2. Setter in a worklet: on a phone the callback runs on the UI thread, which cannot call a React setter: a red screen (per the library's code). scheduleOnRN(setAsking, id). The web preview runs worklets on its one thread, so it hides the mistake.
  3. Two doors: a swipe far (120 points) or fast (800 points per second) enough, and the Remove button; both lead to the question. Neither while the queue is sending.

Common Wrong Answers and What They Reveal

  • Q1 A. Thinks timers live on their own thread: draw the two lanes again.
  • Q2 A or D. Fixes the tool instead of the code: the rule protects the compiler's assumptions.
  • Q3 B or C. Likes springs everywhere: run the measured spring count from Common Mistakes.
  • Q4 A, B or C. Has not separated Reanimated's functions from CSS-style animations: Lab 7.1 Task 2.
  • Q8 B. Trusts the web preview as a phone: the kit's Jest run (P2) and the lesson's card.
  • Q12 A. Has not met recycling: Lesson 3.2, then the lesson's measured "Item 95".
