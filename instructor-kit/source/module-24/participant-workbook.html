Lessons

9.3

Updates and Monitoring

By the end you can
  • Explain how expo-updates and EAS Update deliver new JavaScript and assets to an installed build, and when a phone starts using them
  • Choose a runtime version policy, and measure on your computer whether a change needs a new build or can go out as an update
  • Connect build profiles to update channels, and publish an update to the right builds with the right environment variables
  • Say what an over-the-air update may and may not change, under Expo's technical limits and the app stores' rules
  • Tell the user-facing version from build numbers, and add a crash screen and a reporting seam that a crash-reporting service can plug into
  • Write a GitHub Actions workflow that runs the type check, lint and tests on every push, including the step a fresh checkout of an Expo project needs
Key ideas
  • Two parts of every app: the native part (compiled into the build) and the JavaScript part with its assets. expo-updates replaces the second part in a release build: it asks at every start, downloads in the background, runs the update at the NEXT start, and falls back to the embedded code.
  • Runtime version: a label for the native part; a phone takes only updates with exactly its own. Shoreline Crew uses the fingerprint policy: npx expo-updates runtimeversion:resolve measures it before you publish.
  • Channels come from build profiles (preview, production). npx eas-cli@latest update --channel preview --environment preview --message "…" publishes; the variant's settings must be in the EAS environment, because eas update does not read the profile's env.
  • What an update may change: JavaScript and assets (fixes, text, styles); never native code, and never what the app is (store rules). Rollback, republish and percentage rollouts are updates too.
  • Version vs build number: the version (1.0.0) is yours and user-facing; build numbers live on EAS and count up. An update changes neither: Profile gets an Updates line.
  • Monitoring and CI: a root ErrorBoundary shows CrashScreen; every error goes through reportError, and setReporter can plug a service in later. CI runs npm ci, npx expo customize tsconfig.json, tsc, lint and the tests on every push.
Worked example: build or update? measure it

Does a change need a new build? Measure it. The runtime version is a fingerprint of everything native; a phone takes only updates with exactly its own. On the course app (only the runtimeVersion of each line kept):

npx expo-updates runtimeversion:resolve --platform android
APP_VARIANT=preview npx expo-updates runtimeversion:resolve --platform android
29268b22f86138bf4fc840f53d9fee4a7e94525a
142af542088aaca299daa3c4fdc8d957b9068665

Two variants, two runtime versions. A comment in the Logbook screen: the preview hash stays 142af542… (JavaScript: an update). A reworded location permission sentence: a510c337… (native: a build). The rule of thumb: what ends up in the JavaScript bundle (screens, text, styles, EXPO_PUBLIC_ values) can travel by update; what is compiled into the native project (packages with native code, permission sentences, the icon, the name, the ids) needs a build. The measurement decides.

9.4

The App Stores

By the end you can
  • Name what Google Play and the App Store require before an app can be published: developer accounts and their real costs, permanent app ids, and the technical rules builds must meet
  • Build a data inventory from an app's own code and use it to answer Apple's App Privacy details and Google Play's Data safety form
  • Explain both stores' rules for privacy policies and account deletion, and give an app an honest in-app path to both
  • Prepare a store listing within the stores' limits, and avoid the most common reasons apps are rejected in review
  • Configure eas submit for a testing track, and work through a release checklist from code to production
Key ideas
  • Two stores, two accounts: Apple's is yearly, Google Play's one-time, and new personal Play accounts run a closed test with testers before production (the lesson's table; check the official pages: they change). None is needed for this course.
  • Ids are permanent and on a domain you control (reversed); com.example is refused. Builds must meet each store's current technical rules: a current Expo SDK keeps you inside them.
  • Collected = leaves the phone and is kept. Answer Apple's App Privacy details and Google Play's Data safety from an inventory of the code AND every SDK, never from memory; redo it when the app changes.
  • Privacy policy and deletion: a policy link inside the app; apps that create accounts must let people start deleting them inside the app (Google also wants a web link). Shoreline Crew's API cannot delete, so its Your data screen says so and opens a request page.
  • Listing and review are your work, not eas submit's: texts within limits, real screenshots, a running server and a demo account for the reviewer. Most rejections are about completeness.
  • Testing tracks first: internal testing and TestFlight before production; eas submit sends a build to the track its submit profile names. The release checklist turns it into a routine.
