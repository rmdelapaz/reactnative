1.1 · How React Native Works: self-check

Q1
On an Android phone, what does the CleanupCard's <Text> become?
A) A <p> element inside a hidden browser
B) A native text view, created by the Fabric renderer
C) A picture of the text that Hermes draws
D) A WebView that shows the card's HTML
Why: React Native renders to the platform's own building blocks: Fabric creates a native view for each component (TextView-like on Android, UILabel-like on iOS). Only the web preview turns <Text> into HTML, a <div dir="auto"> (Lesson 1.1, Native Views, Not a DOM).
A is wrong: There is no browser and no DOM in the app.
C is wrong: Hermes runs your JavaScript; it does not draw.
D is wrong: A WebView is the other approach (a website inside an app); React Native does not use one.
Q2
Predict: this card renders {title} straight inside the <View>. What does a phone (or Jest) say, and does npx tsc --noEmit complain?
<View style={styles.card}>
  {title}
  <Text>{spotsLeft} spots left</Text>
</View>
An error: Text strings must be rendered within a <Text> component. (a red screen on a phone); tsc says nothing
Why: Every piece of text sits in a <Text>. The type checker allows any child in a View, so only running it shows the problem: on a phone a red error screen, in Jest an Invariant Violation with the same words (the kit's demo and Lab 1.1, Task 1).
Q3
You copy onClick={() => setJoined(!joined)} from your web code onto a <Pressable>. What happens?
A) tsc reports that onClick does not exist on Pressable
B) The phone shows a red error screen
C) Nothing happens when a finger presses it, and no tool complains
D) It works exactly like onPress
Why: React Native's touch prop is onPress. onClick type-checks and lints clean, and a press does nothing: a silent bug only a test or a finger finds (the kit's Predict P1 and P2, Lab 1.1 Task 2).
A is wrong: The kit ran it: npx tsc --noEmit printed nothing.
B is wrong: No error at all: that is the danger.
D is wrong: A test that presses it fails: Unable to find an element with role: button, name: You're in!
Q4
Which piece of Shoreline Crew HQ can the phone app use exactly as it is?
A) A CSS Module for the event cards
B) A helper that saves the session in localStorage
C) An <img src> for the site photos
D) A Zod schema that checks an API response
Why: Plain TypeScript and JavaScript libraries with no browser API carry over unchanged (the lesson's "what carries over" table); Lesson 1.3 brings the shared code across.
A is wrong: There is no CSS on a phone: StyleSheet objects (Lesson 2.1).
B is wrong: localStorage is a browser API: AsyncStorage and SecureStore (Lesson 5.3).
C is wrong: <img> becomes an Image component with a source and a size (Lesson 2.3).
Q5
Which part of Expo builds an iPhone app in the cloud, without a Mac?
A) EAS Build
B) Expo Go
C) Metro
D) Expo Router
Why: EAS (Expo Application Services) builds for the stores, iOS included, in the cloud, with a free plan (Lesson 9.2). The course never requires a Mac.
B is wrong: Expo Go runs your project while you develop; it builds nothing.
C is wrong: Metro bundles your JavaScript on your computer.
D is wrong: Expo Router is navigation from files.
Q6
Your code asks for the phone's location. Which parts of the New Architecture are involved?
A) Fabric and the bridge
B) A native module, reached from JavaScript through JSI
C) Hermes alone: JavaScript can read the GPS directly
D) Metro and Expo Go
Why: Native modules (expo-location here) give JavaScript the phone's features, and JSI lets JavaScript call them directly (Lesson 1.1, Exercise 2). Hermes runs the JavaScript that makes the call.
A is wrong: Fabric renders views; the bridge is the old design that the New Architecture replaced.
C is wrong: JavaScript reaches the GPS only through native code.
D is wrong: Those deliver your code to the phone; they are not involved in a location request.

1.2 · Your Toolchain: self-check

Q7
Expo Go shows Shoreline Crew. You change styles.tagline to styles.tagLine and save. What does the phone show?
A) A red error screen naming index.tsx
B) Nothing changes until you scan the QR code again
C) Metro refuses to bundle the file
D) The tagline, without its size and color
Why: Metro removes the types without checking them, so the file bundles and Fast Refresh shows it: the style is just undefined, and the text silently loses its look. Only npx tsc --noEmit names it (Lesson 1.2, Common Mistakes; Lab 1.2 Task 1).
A is wrong: A red screen comes from code that cannot run (a syntax error, a crash); this runs.
B is wrong: Fast Refresh shows saved changes within a second or two.
C is wrong: Metro transforms TypeScript without type-checking it.
Q8
npx tsc --noEmit prints this in shoreline-crew. Which change fixes it?
src/app/index.tsx:9:27 - error TS2551: Property 'tagLine' does not exist on type 'Readonly<{ … }>'. Did you mean 'tagline'?

9       <Text style={styles.tagLine}>Many hands, cleaner sands.</Text>
                            ~~~~~~~


Found 1 error in src/app/index.tsx:9
A) Change styles.tagLine to styles.tagline on line 9
B) Set "strict": false in tsconfig.json
C) Run npx expo start --clear
D) Run npx expo install --fix
Why: Read it from the top: file:line:column (src/app/index.tsx:9:27), the code (TS2551), the message with its Did you mean, then the line with the squiggle. StyleSheet.create is fully typed, so a style name that does not exist is an error.
B is wrong: Switching the checks off hides the bug; the tagline still loses its look.
C is wrong: Metro's cache has nothing to do with a type error.
D is wrong: No package is out of date.
Q9
Phone and laptop are on the same home Wi-Fi, Metro is running, and Expo Go on an iPhone cannot connect. What do you check first?
A) Reinstall Node.js
B) Delete node_modules and run npm install
C) Settings > Privacy & Security > Local Network: Expo Go must be on
D) Press r in the Metro terminal
Why: On iOS, Expo Go needs Local Network access to find your computer (the lesson's checklist). The other common causes: a different network, a firewall, WSL's private 172. address (Lesson 1.2).
A is wrong: Metro is running, so Node works.
B is wrong: The packages are fine: the app bundles in the web preview.
D is wrong: r reloads apps that are already connected.
Q10
Name the two commands the project's AGENTS.md asks for before a task is done, and what each prints when the project is clean.
npx expo lint and npx tsc --noEmit; both print nothing at all
Why: No news is good news: ESLint and tsc speak only when something is wrong. A lint problem ends with a line like ✖ 1 problem (1 error, 0 warnings); a type error starts with file:line:column.
Q11
The very first npx expo lint installs ESLint, says ESLint has been configured, then ends with CommandError: npx expo lint requires ESLint version 8.57.0 or greater. What now?
A) Install a newer ESLint by hand
B) Run npx expo lint again
C) Delete eslint.config.js and start over
D) Run npm audit fix --force
Why: A known first-run hiccup: the CLI checked for ESLint before it had installed it. The second run lints, and prints nothing when the project is clean (Lesson 1.2, Step 7).
A is wrong: ESLint 9 was just installed; it is the version Expo's rules use.
C is wrong: The file it wrote is the one you want.
D is wrong: "force" may install versions that break the SDK's tested set: never.
Q12
On the phone, an app reads http://localhost:4000/api/events. Where does that request go?
A) To your computer, where the API runs
B) To Expo's servers
C) To the Wi-Fi router
D) To the phone itself, where no API runs
Why: On a phone, localhost is the phone. The web preview runs in your computer's browser, so localhost works there; Lesson 5.1 gives the app your computer's address for a real phone.
A is wrong: Only a browser ON the computer reaches the computer as localhost.
B is wrong: Expo's servers never see your API traffic.
C is wrong: The router is not localhost for anyone.

{
  "error": "not_found",

}
Why: 404 with a JSON body: not_found and a sentence a person can read. Not an empty answer and not a crash: an API says precisely what is wrong, and the app shows it (Module 5).
P4
Predict the status code and the answer, then open it.
/api/events?_status=500
HTTP/1.1 500 Internal Server Error
content-type: application/json; charset=utf-8

{
  "error": "server_error",
  "message": "Simulated 500 response (the _status parameter)."
}
Why: The API's own switch: ?_status=500 makes it answer a server error on purpose, so you can build and test the error screen without breaking anything (Module 5).

The Lesson Pages' Own Quick Quizzes

Lesson 1.1 · How React Native Works
  1. C A native Android view, created by React Native's renderer: React Native renders to the platform's own building blocks. The Fabric renderer creates a native Android view for the View component; there is no DOM on the phone. Only the web preview turns it into a div.
  2. A As JavaScript in Hermes, the engine inside the app: Your TypeScript is turned into JavaScript and runs in Hermes, the JavaScript engine inside the app. Native code (views, modules) runs alongside it, reached through JSI.
  3. B The shoreline-api types in src/api/types.ts: The API types describe the data, not the screen, and the API is the same one. Plain TypeScript with no browser APIs carries over unchanged; Lesson 1.3 copies it.
  4. D A development build of your app: Expo Go contains a fixed set of native modules. A development build is your own version of it, built with exactly the native code your project needs; EAS can build it in the cloud (Lesson 9.2).
  5. B How the camera permission prompt behaves on a phone: The web preview translates components into HTML in a browser. Native-only behavior such as a camera permission prompt, notifications or the platform's own controls needs a phone or an emulator.
Lesson 1.2 · Your Toolchain
  1. B The 172 address is WSL's private address, which the phone cannot reach: By default WSL 2 sits behind its own private address, and Expo prints that address. The phone cannot reach it. Run the commands in PowerShell, switch WSL to mirrored networking and allow the ports, or use the web preview.
  2. D Run npx expo start once, then run tsc again: expo-env.d.ts and the typed routes are generated by the first npx expo start and are not committed. Start Metro once, stop it, and run the type check again.
  3. A n, because files kept in example/ are still checked and their imports break: With y the template moves to an example folder inside the project, where TypeScript and ESLint still check it and its imports no longer resolve. Answering n gives a clean project; you can always create a sample project elsewhere to read the template.
  4. C Fast Refresh shows the new tagline within a second or two, without a reload: Metro sees the saved file, rebuilds that module and Fast Refresh swaps it into the running app, keeping component state. A full reload is only needed when the app gets into a strange state.
  5. A The Android emulator from Android Studio: The Android emulator is a virtual Android phone that runs Expo Go, so it shows native Android views. It runs on Windows, macOS and Linux; the web preview renders HTML instead, and the iOS Simulator needs a Mac.

Opening: Reading the Room

There is no retrieval warm-up in Session 1. The opening's two checks have their answers above: the environment check output (what READY looks like) and the diagnostic D1 to D6. Learners who end the clinic still NOT READY leave with a numbered plan in their workbook's Start Here box.

Exit Ticket

  1. Native views: a native view (an Android view, an iOS UIView) created by React Native's renderer, Fabric; the app is a real app, with no browser inside it, so there is nothing to build a DOM in. (Only the web preview makes HTML.)
  2. The silent typo: npx tsc --noEmit names it (TS2551: StyleSheet.create is typed). Metro removes the types without checking them, and the phone simply ignores a style that is undefined. Running is not checking.
  3. Two terminals: shoreline-api running node server.ts (the API, http://localhost:4000) and shoreline-crew running npx expo start (Metro, port 8081). The API first.

Common Wrong Answers and What They Reveal

  • Q1 A or D. Still pictures a browser inside the app. Show the demo's outline next to the web preview's HTML.
  • Q2 "tsc catches it". Expects the type checker to know React Native's rules. Run the demo's two commands side by side.
  • Q3 A or D. Assumes web props either fail loudly or work. Run P2: the test presses, nothing happens.
  • Q7 A or C. Expects Metro to check types (the same misconception as Vite's dev server in the web course).
  • Q9 A, B or D. Debugs the computer when the phone's permission is the problem. Walk the lesson's checklist in order.
  • Q12 A. The localhost trap Lesson 5.1 builds on: say it now, solve it then.
