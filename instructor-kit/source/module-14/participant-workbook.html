Lessons

5.5

Offline First

By the end you can
  • Explain "offline first" as an outbox: write on the device first, send when you can, and say what a paused mutation from Lesson 5.2 cannot do
  • Persist a Zustand store on a phone with persist and AsyncStorage, load it behind the splash screen, and say what differs from the web course's localStorage store
  • Send a queue safely: one log at a time, the same clientId on every try, and a different reaction to each kind of answer (sent, refused, signed out, no answer)
  • Choose the moments to send (start, sign-in, back online, back in the foreground) with the online and focus managers you already have
  • Keep each volunteer's unsent work apart on a shared phone
Key ideas
  • Offline first is an outbox: write on the device first, send when you can. Lesson 5.4's paused mutation waits in memory, which ends when the app does; today's queue is saved in AsyncStorage the moment Send is pressed.
  • Two rules: save before sending; leave the queue only after the server and the logbook both have it. Queue what a person creates (a log); let what the server decides (a sign-up) wait for the server.
  • Zustand on a phone: persist comes across from the web, with three differences: name the storage (createJSONStorage(() => AsyncStorage)), load it yourself behind the splash (skipHydration + rehydrate()), save only what should survive (partialize). merge checks saved data, as in the HQ.
  • Every answer means something: 201 and 200 done; other 4xx refused (kept with the server's words); 401 stop and sign in; no answer or 5xx: keep, count, stop. The clientId makes "no answer: send again" safe (200 with the saved log).
  • When to send: Send, start or sign-in, back online (onlineManager), back in the foreground (focusManager), Send now. The sender does nothing when it should not run, so calling it often is harmless. Not while the app is closed.
  • A shared phone: every queued log names its volunteer; only that volunteer's sign-in sends it (checked before each request); sign-out keeps the queue.
Worked example: persist with no storage

The web course's persisted store, copied to the phone with no storage option. tsc and the linter say nothing, and the web preview works (it has localStorage). Run the way the lesson ran it (Node, a window without localStorage, as on a phone):

// The web course's persisted store, copied as it was: no storage option
globalThis.window = {}; // a window without localStorage, as on a phone
const { create } = await import('zustand');
const { persist } = await import('zustand/middleware');

const useLogQueue = create()(
  persist((set) => ({ logs: [], add: (log) => set(({ logs }) => ({ logs: [...logs, log] })) }), {
    name: 'shoreline-crew-log-queue',
  }),
);
try {
  useLogQueue.getState().add({ clientId: 'c3a0f6b2' });
  console.log('add worked');
} catch (error) {
  console.log('add threw: ' + error);
}
add threw: TypeError: Cannot read properties of undefined (reading 'setItem')

Read it from the top: a TypeError, reading setItem of something undefined: persist reached for a storage that is not there. On a phone, the same moment is the red screen when Send is pressed. The fix is one option: storage: createJSONStorage(() => AsyncStorage), and with it the two other phone differences: skipHydration with loadLogQueue() behind the splash (AsyncStorage answers later), and partialize (save the logs only: sending must end with the app).

6.1

Permissions Done Right

By the end you can
  • Describe the life of a permission on an iPhone, an Android phone and the web preview: not asked, granted, denied, and blocked (plus the one-time and approximate answers)
  • Ask at the moment a feature needs it, explain why first, and handle "no" and "don't ask again" without trapping the person
  • Use Expo's permission model: the permission Hooks, get…PermissionsAsync versus request…PermissionsAsync, the PermissionResponse object, and what the Hooks leave to you
  • Write the words on the phone's question with a config plugin in app.json, ask only for what you use, and check what reaches the native projects
  • Say what Expo Go, a development build and the web preview each show you about permissions
Key ideas
  • The life of a permission: not asked, granted (one-time and approximate answers count), denied (Android may ask once more), blocked (iPhone after one no, Android after two, Chrome after Never allow). Answers change in Settings at any time: check before every use.
  • Five rules (the farm gate): ask in context; explain first, with Continue (the real Allow is the phone's) and Not now; a no is an answer (everything else keeps working); say when only Settings can help; check before every use.
  • Expo's model: get…PermissionsAsync reads, request…PermissionsAsync asks if it still may, the Hook returns [response, request, get]; every answer is a PermissionResponse (status, granted, canAskAgain, expires). The Hook never asks by itself and never re-reads after Settings.
  • The project's step: permissionStep turns an answer into checking, not-asked, denied, blocked or granted (a web no is blocked); usePermission re-reads on focus; PermissionGate has one face per step and renders the feature only after a yes.
  • The words on the question: an iPhone shows the purpose string from Info.plist; Android lists permissions in its manifest. Config plugins in app.json write both; expo-location's plugin runs with default words even when unlisted: list it to use your words and false for what you do not use. npx expo config --type introspect shows the result.
  • Where you see what: Expo Go asks as itself, with its own words, and remembers answers across projects; a development build asks as Shoreline Crew, with your words (Module 9); the web preview asks as the browser, per address.

Glossary

TermMeaning
offline first / outboxWrite on the device first, send when the network allows; the record survives the app closing
queueThe saved list of records on their way to the server (here: debris logs in AsyncStorage)
persist (Zustand)Middleware that saves a store after every change and reads it back
createJSONStorage(() => AsyncStorage)Tells persist where to save on a phone (there is no localStorage)
hydration / rehydrate()Reading the saved state back into the store; on a phone it is async, so the app waits behind the splash
partializepersist's option for saving only part of the state
idempotent retryA resend that changes nothing: the clientId makes the server answer 200 with what it already has
useShallowCompares a selector's items, so a filtered list does not render forever
runtime permissionThe phone's own question before an app may use location, the camera, the microphone, notifications…
PermissionResponseEvery Expo permission answer: status, granted, canAskAgain, expires
canAskAgainfalse: the phone will not ask again; only Settings can change the answer (always true on the web)
pre-permission explanationThe app's own sentence before the phone's question, with Continue and Not now
purpose stringThe iPhone's usage description in Info.plist, printed in its question
config pluginCode in app.json's plugins that writes the native projects' settings at prebuild
npx expo config --type introspectPrints what the plugins will write, without creating ios/ or android/
haversineThe formula for the straight-line distance between two latitude/longitude points
