5.5 · Offline First: self-check

Q1
With Lesson 5.4's code, Theo sends a debris log in airplane mode, then force-quits Expo Go. What happens to the log?
A) It is sent the next time Theo opens the app
B) It waits in AsyncStorage until the phone is online
C) It is gone: a paused mutation waits in memory, and memory ends with the app
D) The server receives it twice
Why: TanStack Query's paused mutation waits in its mutation cache, in memory (Lesson 5.2, 5.4's "Keep the app open until then"). Lesson 5.5's queue writes the log to AsyncStorage the moment Send is pressed, before the network is tried at all.
A is wrong: Nothing was saved anywhere that outlives the app.
B is wrong: That is today's queue, not Lesson 5.4's mutation.
D is wrong: Nothing reached the server; and the clientId would make a resend harmless anyway.

Q3
Why does the queue save its state with partialize: ({ logs }) => ({ logs }) instead of everything?
A) So sending always starts as false: an app killed during a send would otherwise never send again
B) Because AsyncStorage cannot store booleans
C) To make the saved JSON smaller than 1 KB
D) Because persist cannot save functions without it
Why: sending means "a send is running right now"; it must end with the app. Saved, it would come back true, and the sender's first guard (if (queue.sending) return) would stop every future send. persist already skips the action functions.
B is wrong: JSON holds booleans; AsyncStorage stores the string.
C is wrong: A log is well under a kilobyte; size is not the reason.
D is wrong: Functions are dropped by JSON anyway; partialize is about sending.
Q4
Theo's first POST reached shoreline-api and was saved, but the answer never reached the phone. The queue sends the same log again with the same clientId. What does the API answer? (The kit ran it against the course API.)
A) 201 and a second saved log
B) 409, so the log is marked refused
C) 400: the clientId is already used
D) 200 with the log it already has, and the server holds one log
Why: The kit sent one log twice: Theo, first try: 201, then Theo, same clientId again: 200, same log: true, and Theo's logs with this clientId on the server: 1. The device-made clientId (Lesson 5.4) is what makes "no answer: send again" safe.
A is wrong: The API looks the clientId up first: no duplicate.
B is wrong: 409 is "this cleanup has not happened yet", not a resend.
C is wrong: A resend is expected; the API answers it with the saved log.
Q5
Sort these answers to a queued log into what the queue does: 201, 200, 403, 401, no answer, 503.
201 and 200 = done (logbook, then out of the queue); 403 = refused, kept with the server's words, never sent again by itself; 401 = keep everything, "Your sign-in has ended", stop; no answer and 503 = keep waiting, count the try, stop for now
Why: The question for every failure: would asking again, unchanged, ever get a different answer? A dead network or a busy server: yes, later. A 403 "no spot": no. Treating them the same either loses data or retries forever (Common Mistakes).
Q6
A screen selects useLogQueue((state) => state.logs.filter((item) => item.volunteerId === viewer)). What happens, and what is the fix?
A) It works: Zustand compares arrays by their items
B) tsc reports that filter returns a new array
C) It renders forever (Maximum update depth exceeded): wrap the selector in useShallow
D) It shows every volunteer's logs: add a second filter
Why: filter builds a new array every time Zustand asks, so Zustand sees a new answer, renders, asks again... The lesson measured a blank page and React error #185 in the web preview; Lab 5.5's Task 3 fails in Jest with the same words. useShallow compares the items; a selector that returns a number (the tab badge's .length) needs nothing.
A is wrong: That is what useShallow adds; plain selectors compare with Object.is.
B is wrong: Types are fine: the bug is at run time.
D is wrong: The filter by volunteerId is right; the new array each call is the problem.

5.5 · Offline First: predict, then check

P1
The same debris log is sent to shoreline-api four times: as Theo (who has a spot), as Theo again with the same clientId (the first answer was lost), as Amara (no spot at this cleanup), and with no sign-in. Predict each status code and what the queue would do with it.
// One debris log, sent the ways a queue meets: what does shoreline-api answer each time?
const api = process.env.API_URL ?? 'http://localhost:4000';
const log = {
  clientId: 'c3a0f6b2-5d1e-4c7a-9b8f-2e6d1a4c9f70', // made on the phone, saved with the log
  items: [{ category: 'glass', count: 2 }],
  bags: 1,
  weightKg: 1.5,
  recordedAt: new Date().toISOString(),
};

async function send(token) {
  const response = await fetch(`${api}/api/events/e17/logs`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', ...(token && { Authorization: `Bearer ${token}` }) },
    body: JSON.stringify(log),
  });
  return { status: response.status, body: await response.json() };
}

const first = await send('dev-volunteer'); // Theo, who has a spot
console.log(`Theo, first try: ${first.status}`);
const again = await send('dev-volunteer'); // the answer was lost: the queue sends it again
console.log(`Theo, same clientId again: ${again.status}, same log: ${again.body.id === first.body.id}`);

const signIn = await fetch(`${api}/api/auth/sign-in`, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ email: 'amara.diallo@example.com', password: 'shoreline-demo' }),
});
const amara = await send((await signIn.json()).token); // Amara has no spot at this cleanup
console.log(`Amara: ${amara.status} ${amara.body.message}`);
const nobody = await send(null); // a sign-in that has ended
console.log(`No sign-in: ${nobody.status} ${nobody.body.message}`);

const logs = await fetch(`${api}/api/events/e17/logs`, { headers: { Authorization: 'Bearer dev-volunteer' } });
const saved = (await logs.json()).filter((item) => item.clientId === log.clientId);
console.log(`Theo's logs with this clientId on the server: ${saved.length}`);
Theo, first try: 201
Theo, same clientId again: 200, same log: true
Amara: 403 Only volunteers with a spot at this cleanup can log for it.
No sign-in: 401 Sign in first.
Theo's logs with this clientId on the server: 1
Why: Run against the course API (a private copy, sample data built around one fixed day). 201: a new log. 200 and the same log: the server already had this clientId (the queue then removes it: done). 403: refused, kept with these exact words, never sent again by itself. 401: keep everything, show that the sign-in has ended, stop. And the server holds ONE log from Theo, whatever the queue resent.

The Lesson Pages' Own Quick Quizzes

Lesson 5.5 · Offline First
  1. B The queue is read back at startup and the log is sent right away: Send saved the log in the queue, which persist wrote to AsyncStorage at once. At startup the root layout reads the queue back behind the splash screen, and the Hook sends the signed-in volunteer's waiting logs as soon as everything is loaded.
  2. D 200 with the log the server already has, because the clientId is the same: The clientId was made once and saved with the log, so the second try carries the same one. shoreline-api finds the log it already has for that volunteer and clientId and answers 200 with it. The queue treats 200 like 201: into the logbook, out of the queue, one log on the server.
  3. A Mark it refused, keep the server's message, and stop sending it by itself: Asking again, unchanged, would get the same answer, so retrying only wastes battery and hides the problem. Deleting it silently loses the volunteer's work. Keeping it as refused, with the server's words and a Remove button, tells the volunteer and lets them decide.
  4. C It waits, unseen by Maya, until Theo signs in on this phone again: The server records the log for whoever's token sends it, so sending Theo's log with Maya's sign-in makes it Maya's (measured). The queue sends only the signed-in volunteer's logs, Maya's Logbook shows none of Theo's, and his log goes out the next time he signs in on this phone.
  5. B The first change fails, because a phone has no localStorage: persist defaults to window.localStorage. The web preview has it; a phone has a window without localStorage, so saving fails on the first change (measured in Node in the same situation: Cannot read properties of undefined, reading setItem). Name the storage: createJSONStorage with AsyncStorage.
Lesson 6.1 · Permissions Done Right
  1. C After the volunteer presses Show my distance and reads the one-sentence reason: Asked in context, the question explains itself, and the panel's one-sentence reason comes first. Asked at launch or at sign-in, nobody knows why, and on an iPhone a no given then is final unless the volunteer digs into Settings.
  2. A The blocked face, with Open Settings: On an iPhone one Don't Allow sets canAskAgain to false, so permissionStep returns blocked as soon as the Hook reads the answer. A request would return the same no without showing anything, so the panel offers Open Settings instead.
  3. D Expo Go is its own app with its own purpose strings; yours appear in your own build: The purpose string lives in the app's Info.plist, which config plugins write when your own app is built. Expo Go is a different app with its own Info.plist and words, used for every project. Your string appears in a development build or a store build.
  4. B usePermission reads it again when the focus manager says the app is back in the foreground: Expo's Hook reads once when it mounts and after each request. usePermission subscribes to the focus manager, which AppState tells when the app is back in the foreground, and calls check() then. Without it (measured), the panel kept saying no.
  5. A The web answer always says true, but a browser never asks again after a block, so the Hook does not trust it there: expo-location's web code answers canAskAgain true for every answer, but a browser told Never allow never asks again: a request returns the no at once. Treating the web's no as blocked shows the site-settings note instead of an Ask me again button that could do nothing (measured).

Exit Ticket

  1. The two rules: save the log on the phone before anything is sent; remove it from the queue only after the server has it AND the logbook has a copy. Between the two steps, a crash means "send again", which the clientId makes harmless.
  2. A 403: mark it refused, keep the server's words ("Only volunteers with a spot at this cleanup can log for it."), stop sending it by itself, show it with Remove. Asking again unchanged gets the same answer: retrying drains the battery and hides the problem.
  3. Continue: the real Allow is the phone's own question, which Continue leads to (and Apple asks that a screen before it does not imitate it); Not now asks nothing. After an iPhone's first "Don't Allow" the phone never asks again: canAskAgain false, the blocked face, Open Settings (documentation-based: the course could not run a phone).
