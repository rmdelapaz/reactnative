Part 1 Assessment: Written Part (model answers and marking)

10 points. W2 and W3 show real tsc output from a copy of the project's model solution with the change made.

W1
Metro bundles a file with a type error and the phone shows the app. Why does nothing complain, and which command finds the error? (1)
Metro removes the types and bundles the JavaScript that is left: it never checks them. npx tsc --noEmit (here npm run typecheck) reads the types and reports the error.
Marking: The point needs both halves: running is not checking, and a tsc command.
W2
A learner writes this line in the ticket card and npm run typecheck prints the error below. What does it mean, and how do you fix it? (2)
src/components/TicketCard.tsx:37:56 - error TS18048: 'ticket.fixer' is possibly 'undefined'.
Found 1 error in src/components/TicketCard.tsx:37
fixer is optional in Ticket (fixer?: string), so its type is string | undefined, and checking the status does not tell TypeScript that a fixer is there. Fix: check the property itself, ticket.fixer !== undefined && ... (or ticket.fixer?.toUpperCase()).
Marking: 1 point for "possibly undefined because it is optional", 1 for a fix that narrows. A non-null assertion ! or as string scores 0 for the fix.
W3
The café adds a fifth status, 'collected', to TicketStatus. What does npm run typecheck do next, and why is that useful? (1)
src/utils/tickets.ts:12:14 - error TS2741: Property 'collected' is missing in type '{ waiting: string; 'in-repair': string; fixed: string; 'not-fixable': string; }' but required in type 'Record<TicketStatus, string>'.
src/utils/tickets.ts:19:14 - error TS2741: Property 'collected' is missing in type '{ waiting: "neutral"; 'in-repair': "info"; fixed: "success"; 'not-fixable': "danger"; }' but required in type 'Record<TicketStatus, BadgeTone>'.
Found 2 errors in the same file, starting at: src/utils/tickets.ts:12
It reports every Record<TicketStatus, ...> table that has no entry for 'collected' (here statusLabels and statusTones, TS2741). The compiler lists every place the new status needs a decision before anything runs.
Marking: The point needs "it lists the tables missing the new key".
W4
On a phone, this card shows the text Fixer: and nothing else when there is no fixer, but a string straight inside a <View> stops the app. Which rule is behind the second, and which tool finds it? (1)
Every piece of text sits in a <Text> (AppText here); text straight in a View is an error when it runs (the red screen; in Jest Text strings must be rendered within a <Text> component). tsc does not find it: only running it (a test, the app).
Marking: The point needs the rule and "only running it".
W5
Why does the queue use keyExtractor={(ticket) => ticket.id} and not the index? (1)
A key tells the list which drawn row belongs to which ticket. When the search or Hide finished removes tickets, an index would point at a different ticket, so an open Show problem would jump to the wrong card. An id stays with its ticket.
Marking: Accept any answer that ties the key to the item's identity when the list changes.
W6
A teammate writes ListHeaderComponent={() => <SearchField ... />}. What does a volunteer notice on a phone, why, and what do you write instead? (2)
The keyboard closes after every letter (the field loses what is typed). A new function on every render is a new component type, so React throws the old header away and builds a new text field. Build the header as an element (const header = (...)) and pass that.
Marking: 1 point for the symptom and the reason, 1 for the element.
W7
The window gets wider than 700 and the queue goes from one column to two. Without key={columns} the screen stops. Why does the key fix it? (1)
A FlatList cannot change its number of columns (Changing numColumns on the fly is not supported). A new key tells React it is a different list, so it builds a new one with the new number of columns.
Marking: The point needs "a new key builds a new list".
W8
Name two things a phone's dark mode needs from the code, as the course does it. (1)
Any two of: colors by job in a light and a dark set (ThemeColors); styles made per theme (createThemedStyles), never a color baked in when the file loads; colors handed to props from useTheme(); a sticky heading with a background from the theme.
Marking: Half a point each, rounded down.

The solution's component:

import { useState } from 'react';
import { FlatList, Pressable, StyleSheet, Switch, Text, TextInput, View } from 'react-native';

import { shiftLabel, signedUp, type Volunteer } from './shifts';

export function SignUpList() {
  const [volunteers, setVolunteers] = useState<Volunteer[]>(signedUp);
  const [onlyRepair, setOnlyRepair] = useState(false);
  const [name, setName] = useState('');
  const [message, setMessage] = useState('');

  // Derived on every render, never stored
  const shown = onlyRepair ? volunteers.filter((v) => v.shift === 'repair') : volunteers;
  const count = shown.length === volunteers.length ? `${volunteers.length} volunteers` : `${shown.length} of ${volunteers.length} volunteers`;

  function add() {
    if (name.trim() === '') {
      setMessage('Type a name first.');
      return;
    }
    setVolunteers((current) => [...current, { id: `v${current.length + 1}`, name: name.trim(), shift: 'repair' }]);
    setName('');
    setMessage('');
  }

  const header = (
    <View style={styles.header}>
      <TextInput accessibilityLabel="Volunteer name" value={name} onChangeText={setName} style={styles.input} />
      {message !== '' && <Text accessibilityRole="alert">{message}</Text>}
      <Pressable accessibilityRole="button" onPress={add} style={styles.button}>
        <Text>Add volunteer</Text>
      </Pressable>
      <View style={styles.row}>
        <Text style={styles.grow}>Only repair tables</Text>
        <Switch accessibilityLabel="Only repair tables" value={onlyRepair} onValueChange={setOnlyRepair} />
      </View>
      <Text>{count}</Text>
    </View>
  );

  return (
    <FlatList
      data={shown}
      keyExtractor={(v) => v.id}
      renderItem={({ item }) => (
        <View style={styles.item}>
          <Text accessibilityRole="header">{item.name}</Text>
          <Text>{shiftLabel(item.shift)}</Text>
        </View>
      )}
      ListHeaderComponent={header}
      ListEmptyComponent={<Text>Nobody yet.</Text>}
    />
  );
}

Self-check: Part 1 Review

Q1
On a phone, what does a <View> become?
A) A <div> in a hidden browser
B) A picture drawn by Hermes
C) A native view, made by React Native's renderer
D) A WebView
Why: React Native renders to the platform's own views (Fabric); only the web preview turns a View into a <div> (Lesson 1.1).
A is wrong: There is no browser in the app.
B is wrong: Hermes runs JavaScript; it does not draw.
D is wrong: A WebView is a website inside an app.
Q2
tsc prints this for the project's ticket card. On a phone, what did the item name look like before anyone ran tsc?
src/components/TicketCard.tsx:29:77 - error TS2551: Property 'Item' does not exist on type 'Readonly<{ card: { gap: 8; padding: 16; borderWidth: number; borderColor: string; borderRadius: 12; backgroundColor: string; }; top: { flexDirection: "row"; alignItems: "center"; gap: 8; }; tag: { minWidth: number; alignItems: "center"; paddingVertical: number; borderRadius: 8; backgroundColor: string; }; t
Found 1 error in src/components/TicketCard.tsx:29
A) A red error screen
B) Plain text: the style is just undefined, so the name lost its look silently
C) Nothing: the card did not render
D) The app would not bundle
Why: Metro removes the types without checking them; an undefined style is ignored. Only npx tsc --noEmit names it, with a Did you mean (Lessons 1.2 and 2.1).
A is wrong: The code runs fine.
C is wrong: The card renders; only the style is missing.
D is wrong: Metro bundles without checking types.
Q3
A row of a tag badge and a long item name pushes the name past the right edge on a narrow phone. Which two flexbox settings fix it?
flexDirection: 'row' on the row (column is React Native's default) and flexShrink: 1 on the name, so it wraps
Why: React Native's flexbox starts in a column and items do not shrink by default (Lesson 2.2); the project's TicketCard does exactly this.
Q4
A screen draws under the notch and the home indicator. What does Shoreline Crew (and the Part 1 project) use?
A) Padding from useSafeAreaInsets(), here through useScreenScroll()
B) A fixed paddingTop: 44
C) <SafeAreaView> from react-native
D) Nothing: phones handle it
Why: The insets differ per phone and orientation; react-native-safe-area-context reports them (Lesson 2.3, then 3.1's useScreenScroll).
B is wrong: Right for one phone, wrong for the rest.
C is wrong: React Native's own is deprecated (and iOS-only).
D is wrong: They do not.
Q5
<Pressable onClick={toggle}>: what happens when a finger presses it?
A) A type error
B) It works like onPress
C) A red screen
D) Nothing, and no tool complains
Why: React Native's touch prop is onPress. onClick type-checks and lints clean and does nothing (Lessons 1.1 and 2.4).
A is wrong: tsc accepts it.
B is wrong: Nothing listens to it on a phone.
C is wrong: No error at all: that is the danger.
Q6
A "Show problem" button opens a panel. What must a screen reader hear besides the button's name, and how do you say it?
Whether it is open: accessibilityState={{ expanded: open }} (and aria-expanded for the web preview)
Why: State changes that sighted people see must be announced (Lessons 2.4 and 8.1); the project's C3 test checks it.
Q7
A teammate adds a short-name table and tsc prints this. What does it tell you?
src/utils/tickets.ts:5:14 - error TS2741: Property 'furniture' is missing in type '{ electronics: string; textiles: string; bikes: string; }' but required in type 'Record<Category, string>'.
Found 1 error in src/utils/tickets.ts:5
A) The union has a typo
B) A Record<Category, string> needs one entry per member: furniture is missing
C) Records cannot hold strings
D) Add as const
Why: A Record over a union is a complete table: tsc lists the missing keys (Lesson 2.5's ThemeColors works the same way).
A is wrong: The union is fine; the table is incomplete.
C is wrong: string is the value type given.
D is wrong: as const would not add the key.
Q8
Which way gives a style sheet dark-mode colors that follow the phone's setting?
A) StyleSheet.create({ card: { backgroundColor: lightColors.surface } }) at the bottom of the file
B) const { colors } = useTheme() at the top of the file
C) createThemedStyles(({ colors }) => StyleSheet.create({ ... })), then useStyles() in the component
D) An if in every style
Why: Both sheets are made once; the hook picks the current one on every render (Lesson 2.5). Colors for props come from useTheme() inside the component.
A is wrong: Worked out once: stays light.
B is wrong: Hooks only run inside components (the linter's rules-of-hooks).
D is wrong: Repetitive and easy to miss one.
Q9
ListHeaderComponent={() => <SearchField ... />}: what does a volunteer notice?
A) The keyboard closes after every letter
B) The app does not compile
C) Cards appear twice
D) Nothing
Why: A new function each render is a new component: React rebuilds the field. Pass an element (Lesson 3.1; Session 8 ran it headless: lo became l).
B is wrong: It compiles and lints.
C is wrong: No duplication.
D is wrong: The field loses what is typed.
Q10
Why keyExtractor={(ticket) => ticket.id} and not the index?
The key keeps each drawn row with its item; after filtering an index points at another item (an open panel jumps), an id stays
Why: Keys come from the data's identity (Lesson 3.1 measured the index-key bug).
Q11
What does FlashList do with a card that scrolls far off the top?
A) Unmounts it
B) Keeps it drawn
C) Reuses it for a card coming in, with new data
D) Caches its picture
Why: Recycling: rows go into a pool per item type and are drawn again (Lesson 3.2). State inside the row travels with it unless reset (useRecyclingState).
A is wrong: That is FlatList.
B is wrong: Only a small area around the screen is drawn.
D is wrong: It reuses components, not pictures.
Q12
Name the three rules that make infinite scroll safe to ship.
Ask once (only when idle), stop after a failure (only Try again asks), never show an item twice (drop known ids); stop at the API's X-Total-Pages
Why: Lesson 3.2; Lab 3.2's MSW counted the requests.
