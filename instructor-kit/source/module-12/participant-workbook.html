5.1

Reaching the API from a Phone

By the end you can
  • Explain what localhost means on a computer, a phone, an Android emulator and an iOS Simulator, and pick the right API address for each
  • Open shoreline-api to your network with --host, find your computer's network address, and test it before the app is involved
  • Point the app at an address through EXPO_PUBLIC_API_URL per device, and rebuild the bundle so the change takes effect
  • Say why a phone app needs no CORS while the web preview does, and why the API's picture addresses work on every device
  • Make the HQ's typed client name the address that failed and suggest a fix, and add a connection check you can use on any device
  • Get past Windows and WSL networking, firewalls and Wi-Fi that keeps devices apart
Key ideas
  • localhost means "this device". The web preview and the iOS Simulator: http://localhost:4000. The Android emulator: http://10.0.2.2:4000. A phone on your Wi-Fi: your computer's address, such as http://192.168.1.42:4000, with the API started node server.ts --host.
  • --host makes the API listen on every address your computer has and print on your network:. Trusted networks only; Ctrl+C when done. Metro's exp://ADDRESS:8081 line shows the same address.
  • Test one link at a time: curl to the network address from the computer (Connection refused = no --host), then /api/health in the phone's browser, then the app.
  • EXPO_PUBLIC_API_URL is copied into the bundle: change .env.local, restart with npx expo start --clear. One Metro, one address. A variable set in the shell wins over the file. No /api at the end, no spaces around =.
  • No CORS on a phone: native fetch sends no Origin. The web preview belongs in the computer's own browser. Picture URLs follow the address the request used.
  • Errors that name the address: AddressError for a badly written address, NetworkError.address, advice per Platform.OS; Profile's Connection section shows the address the bundle has and checks it with an eight-second limit.
Worked example: the API on your Wi-Fi

The API started with --host prints one more line: the address other devices on your Wi-Fi use (192.168.1.42 is the course's example; yours differs):

node server.ts --host
Shoreline Crew API running at http://localhost:4000/api
  on your network:  http://192.168.1.42:4000/api
  sample sign-in: maya.okafor@example.com (organizer) or theo.nakamura@example.com (volunteer), password shoreline-demo
Press Ctrl+C to stop.

Test the road from the computer before the app drives on it:

curl http://192.168.1.42:4000/api/health
{
  "ok": true,
...
}

Then the same address in the phone's browser. If the phone shows that little JSON, the network works and anything left is in the app; if it spins, look at the Wi-Fi, the firewall and WSL. Every connection problem splits in half here. And when something fails, the client now says which address it tried and what to try on this kind of device. 5.2

TanStack Query on Mobile

By the end you can
  • Say which signals a browser gives TanStack Query that a phone does not, and connect focusManager to AppState and onlineManager to NetInfo
  • Explain what a "paused" query or mutation is, and show volunteers what is happening while the phone has no connection
  • Load a list page by page with useInfiniteQuery, keeping the footer states, pull to refresh and the "ask only when idle" rule from Lesson 3.2
  • Refresh a screen's data when it comes back into view, because tabs and stacks keep screens mounted
  • Sign up for a cleanup and cancel with mutations that wait for the API and invalidate what they change
  • Notice an ended sign-in (a 401) in one place for every query and mutation
Key ideas
  • A browser tells the cache two things a phone does not: coming back to the app (AppState 'active' → focusManager.setFocused, in useAppStateFocus) and the connection (NetInfo → onlineManager.setEventListener, in useOnlineManager, with isConnected !== false). Both run once, in the root layout; the web preview keeps the browser's own events.
  • Offline = paused, not failed. A query that needs to fetch offline does not try (fetchStatus: 'paused'), the cached answer stays, and it continues by itself online. Mutations pause too (in memory only: closing the app forgets them).
  • useInfiniteQuery: initialPageParam, queryFn({ pageParam, signal }), getNextPageParam (undefined = last page); hasNextPage, fetchNextPage(), isFetchingNextPage. Ask only when idle; remove duplicates when flattening; a refetch asks for every loaded page in order. Infinite options go with the infinite hook.
  • Screens stay mounted: useRefreshOnFocus(key) = useFocusEffect + refetchQueries({ queryKey: [key], type: 'active', stale: true }), first focus skipped.
  • Sign up and cancel are mutations that wait for the API (spot or waiting list), invalidate ['events'] and ['signups'] in onSettled, and return the promise. A 409 shows the API's own words.
  • One place for 401s: QueryCache and MutationCache onError mark the sign-in as ended (src/auth/ended.ts); the viewer in every private key makes the list recover as a guest.
Worked example: a sign-up, as the API sees it

Signing up, as the API sees it (Theo's token, Boardwalk and Mudflats with 9 of 16 spots left). The first POST:

HTTP/1.1 201 Created

{
  "eventId": "e09",
  "status": "confirmed"
}

The same request a second time (another phone, or a paused mutation sent after a reconnect):

HTTP/1.1 409 Conflict

{
  "error": "conflict",
  "message": "You are already signed up for this cleanup."
}

The API decides: a spot or the waiting list, and "no" with words for a second try. So Shoreline Crew waits for the answer ("Signing up…") instead of guessing, and afterwards, success or not, invalidates the two keys a sign-up changes:

shoreline-crew/src/api/mutations.ts
// A sign-up changes the spots left (on every list and cleanup screen) and your own sign-ups.
// Returning the promise keeps the mutation pending until the screens have the new answers.
function refreshSignups() {
  return Promise.all([
    queryClient.invalidateQueries({ queryKey: ['events'] }),
    queryClient.invalidateQueries({ queryKey: ['signups'] }),
  ]);
}

/** Sign up for a cleanup. Waits for the API: it decides between a spot and the waiting list. */
export function signUpMutation() {
  return mutationOptions({
    mutationFn: (eventId: string) => postSignup(eventId),
    // onSettled, not onSuccess: after a "no" (already signed up on another phone, the last spot
    // just went) the screens need the truth too
    onSettled: refreshSignups,
  });
}

['events'] reaches the paged list and every cleanup screen, ['signups'] your sign-ups: the spots line and the panel update without a line of code that knows about spots.
