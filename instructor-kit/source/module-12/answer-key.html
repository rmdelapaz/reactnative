5.1 · Reaching the API from a Phone: self-check

Q1
shoreline-api runs on your computer with plain node server.ts. Which EXPO_PUBLIC_API_URL reaches it from the Android emulator?
A) http://localhost:4000
B) http://10.0.2.2:4000
C) http://127.0.0.1:4000
D) http://192.168.1.42:4000
Why: 10.0.2.2 is the emulator's built-in name for the computer it runs on (Lesson 5.1's table, from Android's documentation). Inside the emulator, localhost and 127.0.0.1 are the emulator itself.
A is wrong: localhost is the emulator, a separate virtual phone.
C is wrong: 127.0.0.1 is localhost by number: the same device.
D is wrong: Your network address works only once the API listens on it: node server.ts --host.
Q2
Predict: the API runs with plain node server.ts, and from the computer you curl its network address. What does curl say?
curl http://192.168.1.42:4000/api/health
Connection refused (curl exits with code 7): without --host the API listens on localhost only
Why: The kit ran it: curl: (7) Failed to connect to 192.168.1.42 port 4000 after 0 ms: Connection refused The API is running (localhost still answers), it just does not listen on that address. node server.ts --host listens on every address and prints the on your network: line.
Q3
What does the stage's addressAdvice return for this call (the web preview, built with the emulator's address)?
addressAdvice('http://10.0.2.2:4000', 'web')
A) Check that shoreline-api is running, then try again.
B) On Android, 10.0.2.2 is the device itself. ...
C) 10.0.2.2 works only inside the Android emulator: the web preview uses localhost.
D) Check that shoreline-api is running with --host and that this device is on the same Wi-Fi as your computer, then try again.
Why: The function checks the platform first: on 'web', 10.0.2.2 gets its own sentence. The kit ran the stage's src/api/address.ts with Node for every address and platform; this is its real output (Lesson 5.1, Exercise 1).
A is wrong: That is the web answer for localhost.
B is wrong: The "is the device itself" sentences are for localhost on a phone or emulator.
D is wrong: That is the answer for a network address on a phone.
Q4
The API answers a request sent with Origin: http://192.168.1.42:8081 (the web preview opened in a phone's browser) like this. What happens on the phone?
HTTP/1.1 200 OK
A) The cleanups load: the request reached the API
B) The API refuses the connection
C) The app falls back to localhost
D) The phone's browser blocks the answer: there is no Access-Control-Allow-Origin header
Why: The API answered (200), but it allows only http://localhost:* origins, so the browser keeps the answer from the page ("blocked by CORS policy"). Expo Go's native fetch sends no Origin and needs no header: the phone runs the app in Expo Go, the web preview stays in the computer's browser.
A is wrong: Reaching the API is not enough in a browser: CORS decides whether the page may read the answer.
B is wrong: The 200 shows the connection worked.
C is wrong: Nothing in the client does that.
Q5
.env.local says EXPO_PUBLIC_API_URL=http://localhost:4000, and you start Metro like this. Which address is in the bundle?
EXPO_PUBLIC_API_URL=http://10.0.2.2:4000 npx expo start --clear
A) http://10.0.2.2:4000, and Metro leaves out its env: lines
B) http://localhost:4000: the file always wins
C) Both: the phone gets one, the web preview the other
D) None: Metro refuses two values
Why: A variable set in the shell wins over the file (measured in Lesson 5.1); Metro then prints no env: load .env.local line, which is how you tell. In PowerShell the variable stays set in that window until you remove it.
B is wrong: The file is the everyday way; the shell overrides it for one session.
C is wrong: One Metro, one address: phone and web preview get bundles from the same values.
D is wrong: Nothing refuses; one value simply wins.
Q6
Why does Profile's Check the connection give up after eight seconds instead of waiting for the request to fail by itself?
A refused connection fails at once, but an address nobody answers on Wi-Fi can hang far longer; an AbortController stops the wait and the advice can show
Why: The kit's Lab 5.1 Task 3 shows both: MSW's "never answers" computer made the starter wait until Jest's own five-second limit; the solution aborts after its limit and says which address it tried.

5.2 · TanStack Query on Mobile: self-check

Q7
In a browser, TanStack Query hears visibilitychange when you come back to the tab. What reports "back in the foreground" in a phone app?
A) React Native's AppState changing to 'active'
B) NetInfo
C) Expo Router's useFocusEffect
D) Expo Linking
Why: AppState.addEventListener('change', ...) reports 'active' and 'background'; useAppStateFocus passes it to focusManager.setFocused(). Without it, Lesson 5.2's quiz Q1: the list shows its cache and asks nothing.
B is wrong: NetInfo reports the connection: that feeds the onlineManager.
C is wrong: useFocusEffect is about one SCREEN coming back into view (useRefreshOnFocus).
D is wrong: Linking opens and reads URLs.
Q8
After a change to the Cleanups screen, npx tsc --noEmit starts with this. What is the fix?
src/app/(tabs)/index.tsx:34:27 - error TS2769: No overload matches this call.
src/app/(tabs)/index.tsx:91:16 - error TS2339: Property 'hasNextPage' does not exist on type 'DefinedUseQueryResult<InfiniteData<Page<CleanupEvent>, unknown>, Error>'.
A) Add hasNextPage to the query factory
B) useInfiniteQuery(upcomingEventsQuery(...)): infinite options go with the infinite hook
C) Wrap the screen in a second QueryClientProvider
D) Set "strict": false
Why: The kit made the lesson's mistake in a copy of the finished app: useQuery with an infiniteQueryOptions factory. tsc found 8 errors in the file, the lesson's card word for word; the first one is long, the TS2339 lines say the plain thing.
A is wrong: hasNextPage comes from useInfiniteQuery's result, not from the factory.
C is wrong: The provider is a runtime matter, and one is enough.
D is wrong: Hiding the types leaves the screen broken.
Q9
The phone is offline, useOnlineManager has told the onlineManager, and a screen's query needs to fetch. What is its fetchStatus?
A) 'idle'
B) 'fetching', then an error after the retries
C) 'paused': no request is sent, the cached data stays
D) 'error'
Why: With networkMode 'online' (the default) a query that cannot fetch offline pauses and continues by itself when the connection returns. Lab 5.2 Task 2 proves it headless: no request at all while offline, "Waiting for a connection…", then the first page as soon as the fake NetInfo says online.
A is wrong: idle means nothing needs fetching.
B is wrong: That is what a phone WITHOUT the online manager does.
D is wrong: fetchStatus has no 'error'; status does, and a paused query is not failed.
Q10
A test renders a screen that calls useInfiniteQuery and fails at once with this. What is missing?
No QueryClient set, use QueryClientProvider to set one
A) npx expo install @tanstack/react-query
B) A queryKey in the factory
C) The onlineManager
D) A QueryClientProvider around the screens (the root layout's job in the app)
Why: Every useQuery looks for the client the provider gives it (Lesson 5.2, Common Mistakes; Lab 5.2 Task 1's first failure). tsc and expo lint say nothing: it is a runtime rule. On a phone it should be a red error screen with the same words.
A is wrong: The import worked, or the test would fail on the import.
B is wrong: A missing key is a type error.
C is wrong: Without it the app still runs, it just never hears the connection.
Q11
Theo signs up for Boardwalk and Mudflats, then presses Sign up again from another phone. The API answers this. Why does Shoreline Crew put its invalidation in onSettled, not onSuccess?
HTTP/1.1 409 Conflict

{
  "error": "conflict",
  "message": "You are already signed up for this cleanup."
}
A) After a "no" the screens need the truth as much as after a "yes"
B) onSuccess does not exist for mutations
C) onSettled runs before the request
D) To retry the POST
Why: onSettled runs after success AND error. The 409 means the cached spots and sign-ups are out of date (this phone did not know), so ['events'] and ['signups'] are invalidated either way, and describeError shows the API's own words. Mutations are not retried; the 409 makes a repeated sign-up harmless.
B is wrong: It does; it just skips errors.
C is wrong: onMutate runs before; onSettled after.
D is wrong: Invalidation refetches queries, not the mutation.
Q12
The past-cleanups list has two pages loaded and is refetched. Which pages does TanStack Query ask for, in which order, and why does the list not shrink back to one page?
Page 1, then page 2: an infinite query refetches every loaded page in order, so the pages stay consistent and the list keeps its length
Why: Lab 5.2's last test records the requests: ['page 1', 'page 2']. Lesson 5.2 measured the same on the Cleanups tab ("A List That Pages Itself"). That is also why the screen keeps its own refreshing state: the cache refetches by itself a lot.

The Lesson Pages' Own Quick Quizzes

Lesson 5.1 · Reaching the API from a Phone
  1. B Could not reach the server at http://localhost:4000, with advice that localhost is the device itself: On the phone, localhost is the phone itself, where no API runs. The client names the address and, on Android, explains that localhost is the device itself and suggests your computer's network address.
  2. C Without --host, the API listens only on localhost, so the network address refuses the connection: Without --host the API listens on localhost only, so a connection to the network address is refused, even from the same computer. Start it with node server.ts --host.
  3. A The old value is inside the bundle Metro already built: restart with npx expo start --clear: EXPO_PUBLIC_ values are copied into the bundle when Metro builds it. Reloading gets the same bundle; stop Metro and start it with npx expo start --clear.
  4. D CORS is a browser rule; a native app's fetch sends no Origin and ignores the header: CORS is enforced by browsers for web pages. A native app's fetch sends no Origin and does not check the answer's CORS headers, so it simply reads the answer.
  5. C http://192.168.1.42:4000/images/…, the address the request arrived at: The API builds each picture's address from the address the request arrived at, so the phone gets http://192.168.1.42:4000/images/... and the pictures load with no extra code.
Lesson 5.2 · TanStack Query on Mobile
  1. B Shows the cached cleanups and asks the API nothing: TanStack Query hears focus from browser events, which a phone does not send. Without AppState wired to focusManager, the cache never learns the app came back, so the cached list stays until something else asks.
  2. D The mutation pauses, and is sent when the connection comes back: Offline, the mutation is paused: nothing is sent, the button says Signing up and the panel says it will be sent. When NetInfo reports the connection, the paused mutation continues by itself.
  3. A The answer depends on who is signed in, so another person on the same phone must not get it from the cache: The answer depends on who asks. On a shared phone, the next person to sign in must get their own cache entry, not the previous person's fresh answer.
  4. C The screen's own refreshing state, set by the refresh the volunteer asked for: The list refetches on its own after every sign-up, when the app returns to the foreground and when the connection returns. Only a refresh the volunteer asked for should show the spinner, so the screen keeps its own refreshing state (and hides it while the refresh is paused offline).
  5. D The list as a guest, and Profile and My cleanups say his sign-in has ended: The 401 makes the client forget the session; the viewer in the key becomes guest, so the list asks again as a guest and shows the cleanups. The cache's error handler marks the sign-in as ended, so Profile and My cleanups say so.

Exit Ticket

  1. Address and --host: put the computer's network address in .env.local (Metro's exp:// line; no /api), restart with npx expo start --clear, and start the API with node server.ts --host. Then test it: curl, the phone's browser, the app.
  2. Two signals: coming back to the foreground (AppState 'active' → focusManager.setFocused) and the connection (NetInfo → onlineManager). Without them a phone app never refetches on return and fails offline instead of pausing.
  3. Invalidation: a sign-up changes the spots on the list and every cleanup screen (['events']) and your own sign-ups (['signups']); onSettled because after a 409 or a full cleanup the screens need the truth too.

Common Wrong Answers and What They Reveal

  • Q1 A or C. Still pictures the emulator sharing the computer, like the Simulator. Show the table's emulator row and say "a separate virtual phone".
  • Q2 "a CORS error". Mixes up "refused" (nobody listening) with "blocked" (a browser rule). Read curl's words aloud.
  • Q4 A. Believes reaching the server is enough in a browser. Show the three CORS answers above side by side.
  • Q5 B. Thinks the file always wins: the shell overrides it for one session, and Metro's missing env: lines say so.
  • Q9 B. Describes a phone without the online manager: the difference the web preview cannot show.
  • Q11 B or D. Has not separated mutations from queries: mutations are not retried, queries are refetched by invalidation.
