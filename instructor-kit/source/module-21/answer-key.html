import { Pressable, StyleSheet, Text, View } from 'react-native';

type CleanupRowProps = {
  title: string;
  spotsLeft: number;
  onJoin: () => void;
};

// C1 (Lesson 8.1): one row of a cleanup list, as a screen reader meets it: a heading, the words,
// and one button whose name starts with what is written on it. The wave is decoration.
export function CleanupRow({ title, spotsLeft, onJoin }: CleanupRowProps) {
  const full = spotsLeft === 0;
  return (
    <View style={styles.row}>
      <Text aria-hidden style={styles.wave}>
        🌊
      </Text>
      <View style={styles.text}>
        <Text accessibilityRole="header" style={styles.title}>
          {title}
        </Text>
        <Text>{full ? 'Full' : spotsLeft === 1 ? '1 spot left' : `${spotsLeft} spots left`}</Text>
      </View>
      <Pressable
        accessibilityRole="button"
        accessibilityLabel={`Join ${title}`}
        disabled={full}
        onPress={onJoin}
        style={styles.join}
      >
        <Text>Join</Text>
      </Pressable>
    </View>
  );
}

const styles = StyleSheet.create({
  row: { flexDirection: 'row', alignItems: 'center', gap: 12, minHeight: 48 },
  wave: { fontSize: 24 },
  text: { flex: 1 },
  title: { fontSize: 18, fontWeight: '600' },
  join: { minWidth: 64, minHeight: 48, alignItems: 'center', justifyContent: 'center' },
});

accessibilityRole="header" on the title; the button's name starts with its visible word, then says which cleanup (Label in Name); aria-hidden on the wave; disabled keeps a full cleanup's button on the screen, switched off, and RNTL's toBeDisabled() and user.press() both respect it.

8.3 · Testing Screens and Flows: self-check

Q1
Which line renders a component correctly in a React Native Testing Library 14 test?
A) render(<SwitchRow ... />);
B) await render(<SwitchRow ... />); inside an async test
C) render(<SwitchRow ... />).then(screen.debug); at the top of the file
D) await screen.render(<SwitchRow ... />);
Why: In RNTL 14, render, rerender, renderHook, fireEvent and act return Promises (React 19's async rendering): await each one, in an async test. Without the await the kit's run says render function has not been called , with the arrow on the next line (the lesson's first Common Mistake).
A is wrong: The web habit: the render has not happened when the next line asks screen.
C is wrong: Rendering belongs inside a test, and the next line still runs before it finishes.
D is wrong: screen holds the queries of the last render; it does not render.
Q2
The kit made the lesson's mistake: a plain getByText('Group by date') in the SwitchRow test. Which change makes the test right without weakening it?
● flips exactly once for a tap on the switch or on the words

  Unable to find an element with text: Group by date

  <View
    accessible={false}
  >
    <Text
      aria-hidden={true}
    >
      Group by date
    </Text>
    <RCTSwitch
      accessibilityLabel="Group by date"
      accessibilityRole="switch"
      value={true}
A) Remove aria-hidden from the words in SwitchRow
B) Add a testID to the Text and use getByTestId
C) Find the switch by role and name, or add { includeHiddenElements: true } to press the words as a finger can
D) Wrap the query in waitFor()
Why: RNTL skips what a screen reader skips: the words are aria-hidden on purpose (Lesson 8.1), so a screen reader meets one control, the switch, named by accessibilityLabel. Ask for it by role and name; to press the words (a finger can), say so with includeHiddenElements: true.
A is wrong: That breaks the design the test protects: a screen reader would hear the words twice.
B is wrong: A testID peeks at the wiring; the lesson keeps it for things with no good name.
D is wrong: Nothing is loading: the element is hidden, not late.
Q3
Lesson 8.3's sign-in test imports screen and userEvent from expo-router/testing-library. Jest passes. What happens next?
A) Nothing: both modules export the same names
B) Metro refuses to bundle the app
C) npx expo lint reports a duplicate import
D) npx tsc --noEmit reports TS1362: userEvent was exported using export type
Why: Expo Router's testing library passes RNTL's exports through at run time, but its type file only re-exports RNTL's types (export type *), so TypeScript says 'userEvent' cannot be used as a value (the kit's run is the lesson's card). Import RNTL's names from @testing-library/react-native, only renderRouter, testRouter and the matchers from Expo Router.
A is wrong: At run time, yes; the type checker disagrees, and it is right to.
B is wrong: Test files are not part of the app bundle.
C is wrong: The linter accepts the import.
Q4
Without "fakeTimers": { "doNotFake": ["nextTick", "queueMicrotask"] }, the Cleanups screen test stays on "Loading cleanups…", while Lesson 8.2's sendLogs.test.ts still passes. Why the difference?
A) Only renderRouter switches on Jest's fake clock, and that clock froze the steps Node's fetch uses to finish
B) The sender's tests use a different mock API
C) FlashList's stand-in blocks requests
D) The sender's tests do not send requests
Why: renderRouter calls jest.useFakeTimers(); by default that also fakes process.nextTick and queueMicrotask, which Node's fetch and MSW need. The sender's tests never start a fake clock, so their requests finish (the kit ran both: Predict P2). Suspect the clock, not the API.
B is wrong: Both use the HQ's handlers through startMockApi().
C is wrong: FlashList's stand-in measures; it sends nothing.
D is wrong: They do: POST /api/events/e17/logs.
Q5
Predict, then check: in SwitchRow.tsx you delete style={styles.switch} (the pointerEvents: 'none'). The test presses the switch with user.press(). What does Jest report on the first expect, and why?
The second test fails: onChange.mock.calls is [] (Received: Array []), because the press now stops at the switch, and in Jest there is no native switch to flip itself
Why: user.press() follows React Native's touch rules: with pointerEvents: 'none' the touch passes to the row's Pressable, which flips the value once. Without it the switch takes the touch; on a phone the native switch would flip, in Jest nothing does. The test pins down Lesson 8.1's decision that the row takes the finger.

Modules 7 and 8 review: self-check

Q7
Why does Reanimated move an animation with shared values instead of React state?
A) State is not allowed inside Animated.View
B) React state cannot hold numbers
C) Shared values are saved between app launches
D) Shared values change on the UI thread every frame without re-rendering React; state would re-render on the JavaScript thread
Why: Lesson 7.1's skipper and the helm: React sets the destination once; the UI thread steers every frame. A frame lasts 16.7 ms (8.3 on 120 Hz screens): a setState per frame competes with everything else on the JavaScript thread.
A is wrong: Animated.View takes ordinary props too.
B is wrong: State holds anything; it is the re-render per frame that hurts.
C is wrong: Nothing is saved: a shared value lives while the component does.
Q8
A swipe-to-remove row sits in a vertical list. Volunteers complain the list jumps sideways when they scroll. What does Lesson 7.2 add to the pan gesture?
A) activeOffsetX (start only after a clear sideways move) and failOffsetY (give up on a vertical one)
B) numberOfTaps: 2
C) A setTimeout before onActivate
D) pointerEvents: 'none' on the list
Why: Without offsets the pan activates on any movement, so a crooked vertical drag slides the card (the lesson measured 54 points). activeOffsetX waits for a clear sideways move; failOffsetY hands a vertical one to the list.
B is wrong: That is a tap gesture's option.
C is wrong: Gestures are recognized on the UI thread; a timer only delays the problem.
D is wrong: Then the list could not scroll at all.
Q9
With Reduce Motion on, which of these still moves, unless the app checks useReducedMotion() itself?
A) withTiming(1) on a shared value
B) withSpring(0)
C) A CSS-style transition or keyframes animation in a style
D) withSequence(...)
Why: Lesson 7.1 measured it: withTiming, withSpring and withSequence jump to their end (ReduceMotion.System by default); the CSS-style transitions and keyframes do not, so the app reads useReducedMotion() for them (and, as Lesson 7.3 notes, Reanimated reads the setting once, at start).
A is wrong: It jumps to the end.
B is wrong: It jumps to the end.
D is wrong: It jumps to the end.

Why: Label in Name (WCAG 2.5.3, Lesson 8.1): the name starts with the words you see, so "Join" works for voice control and the rest tells a screen reader which card. Checkpoint 3's C1 asks for exactly this.

C is wrong: The role is announced already; the name must say what it does.

Q11
Lesson 8.2 tests the log sender with jest.mock('@/storage/logbook') and no factory. What do the stand-ins do?
A) Nothing: every function exists and returns undefined, and remembers its calls
B) Write to a temporary SQLite file
C) Throw, so the test notices storage
D) Call the real module
Why: An automatic mock keeps the module's shape with empty jest.fn()s: they answer undefined and record calls. That is why Lesson 8.2 mocks its own SQLite module (no SQLite in Jest) and asserts on what the sender asked for.

// Task 1 (reference): the tests for BagCounter, by role and name. Run: npm test
import { render, screen, userEvent } from '@testing-library/react-native';
import { useState } from 'react';

import { BagCounter } from './BagCounter';

// A screen's part that keeps the count, as a log form would. onChange records every change.
function Bags({ onChange }: { onChange: (count: number) => void }) {
  const [count, setCount] = useState(0);
  return (
    <BagCounter
      count={count}
      onChange={(next) => {
        setCount(next);
        onChange(next);
      }}
    />
  );
}

it('starts at no bags, with the minus button switched off', async () => {
  await render(<Bags onChange={jest.fn()} />);
  expect(screen.getByText('0 bags')).toBeOnTheScreen();
  expect(screen.getByRole('button', { name: 'One bag fewer' })).toBeDisabled();
});

it('counts one bag per press, as a finger would', async () => {
  const onChange = jest.fn();
  const user = userEvent.setup();
  await render(<Bags onChange={onChange} />);
  await user.press(screen.getByRole('button', { name: 'One more bag' }));
  await user.press(screen.getByRole('button', { name: 'One more bag' }));
  expect(screen.getByText('2 bags')).toBeOnTheScreen();
  expect(onChange.mock.calls).toEqual([[1], [2]]);
});

it('keeps the decoration away from screen readers', async () => {
  await render(<Bags onChange={jest.fn()} />);
  expect(screen.queryByText('♻')).toBeNull();
  expect(screen.getByText('♻', { includeHiddenElements: true })).toBeOnTheScreen();
});

Lesson 8.3: the page's own quiz

The five questions on the lesson page, with their answers and the page's own reasons:

Lesson 8.3 · Testing Screens and Flows
  1. C The words are hidden from screen readers, and RNTL's queries skip hidden elements by default: SwitchRow hides its words from screen readers (aria-hidden) and puts them on the switch as its accessibilityLabel. RNTL skips hidden elements, like a screen reader. Find the control with getByRole('switch', { name: 'Only cleanups with spots left' }), or pass includeHiddenElements: true when you really want the words, for example to press them.
  2. A The fake clock that renderRouter switches on froze the small steps Node's fetch needs to finish a request: renderRouter switches on Jest's fake timers, and by default they also freeze process.nextTick and queueMicrotask, which Node's fetch and MSW need to finish a request. The fakeTimers doNotFake setting in package.json keeps those two real.
  3. D The touch goes to the row's Pressable, which flips the value once, as a finger would: user.press respects pointerEvents and passes the touch to the nearest parent that takes it, the row's Pressable, whose onPress flips the value once, exactly as a finger does on a phone. A screen reader takes the other path: it flips the native switch, which reports valueChange.
  4. B An end-to-end flow, for example with Maestro, run against that build on a device or emulator: Only an end-to-end test drives the real app on a device: Maestro opens the build, taps, types and checks what appears. Jest tests run in Node with stand-ins for the phone, so they prove the app's decisions, not that the build works on a device.
  5. B true, because React Native's Jest preset pretends a window with text at twice its size: React Native's Jest preset pretends a 750 by 1334 window with fontScale 2, so useLargeText() (fontScale of 1.5 or more) is true. Shoreline Crew's jest.setup.ts sets a phone-sized window with fontScale 1 before every test, and tests that care change it with Dimensions.set().

Exit Ticket

  1. Role and name = accessibility check: RNTL finds what a screen reader finds; a control with no role or name, or hidden, cannot be found by the test either.
  2. What is new in RNTL 14: await before render (and rerender, renderHook, fireEvent, act), in an async test.
  3. What Jest cannot prove: that the built app works on a real device; an end-to-end flow such as Maestro on a device or emulator can.
