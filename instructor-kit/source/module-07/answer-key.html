Warm-up: Lesson 2.4, Retrieved

  1. A Pressable has onClick={signUp}. What do tsc and lint say, and what does a tap do? Answer: Nothing and nothing: onClick type-checks and lints clean; a tap does nothing. Taps go to onPress.
  2. The HQ's onChange={(e) => setQuery(e.target.value)} on a TextInput: what replaces it? Answer: onChangeText={setQuery}: React Native hands you the new text as a string.

2.5 · Responsive, Platform-Specific and Themed UI: self-check

Q1
The kit ran the lesson's Dimensions.get snippet in Jest, where every test first sets a 390-wide phone. It printed this. Why 2?
columns from Dimensions.get:   2 (read when the file loaded)
A) The file was loaded (and read the width) before the test set the phone's size
B) Jest has no window, so it guesses
C) Dimensions.get rounds 390 up to 700
D) Two columns is the default
Why: A top-level read runs once, when the file is first imported: under Jest that was the default window, before the test's 390. On a phone it is the size at launch, and it never follows a tablet turning or a split screen widening. Inside components, use useWindowDimensions (the lesson's quiz Q1).
B is wrong: Jest has a window: the same run printed 390 by 844 from the hook.
C is wrong: Nothing rounds.
D is wrong: The snippet computes it from the width it read.
Q2
An iPad runs Shoreline Crew in split screen, in a third of the screen. What does useWindowDimensions().width report?
A) The iPad's full screen width
B) The width of the app's window: a third of the screen
C) 0 until the app is full screen
D) The width the app had when it launched
Why: It measures the window your app draws in, not the device, and re-renders when it changes. In split screen the window is what the layout has to fit (Dimensions.get('screen') gives the whole screen; rarely what you want).
A is wrong: That is the screen, not the window.
C is wrong: The window always has a size.
D is wrong: That is the stale top-level read.
Q3
The kit rendered the lesson's PlatformNote in Jest and got this line. What does it tell you about the web preview and the phones?
PlatformNote:                  ios: Swipe from the left edge to go back
A) Every platform says the same thing
B) Jest is broken: the web preview should be the default
C) This Jest run renders as iOS; the web preview shows the default branch, an Android phone the android one
D) Platform.select only works on iOS
Why: jest-expo's preset renders as iOS, so Platform.OS is 'ios' there. The lesson ran the snippet in the web preview and got the default hint and "0.0.0" as the version. Each phone runs its own branch: the only way to see both is to test on both (or ask a friend with the other kind).
A is wrong: Platform.select picks one value per platform.
B is wrong: Each environment runs its own branch.
D is wrong: It picks ios, android, web or default.
Q4
Why does the lesson's snippet check Platform.OS === 'android' before comparing Platform.Version >= 33?
const newAndroid = Platform.OS === 'android' && Platform.Version >= 33;
Platform.Version is a number (the API level) only on Android; on iOS it is a string (and "0.0.0" on the web), so TypeScript narrows it to a number only after the OS check
Why: React Native's types narrow Version by OS. Comparing first would compare a string on iOS.
Q5
Shoreline Crew has src/hooks/useColorScheme.ts and src/hooks/useColorScheme.web.ts. Code imports @/hooks/useColorScheme. Which file does npx tsc --noEmit check against?
A) The .web.ts file
B) Both, merged
C) Neither: platform files are not type-checked
D) The plain .ts file: keep the .web.ts version exporting the same names with the same types
Why: Metro picks the file for the platform it bundles; TypeScript checks the plain file. A .web.ts that drifts can break one platform without tsc noticing, so platform files stay tiny and same-typed.
A is wrong: TypeScript resolves the plain name.
B is wrong: There is no merging.
C is wrong: The plain file is checked; the variant is checked only on its own.
Q6
Exercise 2: trackOff is deleted from darkColors. npx tsc --noEmit prints this first (shortened). What does satisfies ThemeColors buy you?
src/theme/colors.ts:74:3 - error TS1360: Type '{ page: "#0f1b26"; surface: "#16283a"; border: "#2b4257"; text: "#e9eef3"; textMuted: "#a9b4c0"; heading: "#bfe3df"; error: "#ff9b85"; banner: "#0b3954"; onBanner: "#ffffff"; onBannerAccent: "#bfe3df"; ... 7 more ...; knob: "#ffffff"; }' does not satisfy the expected type 'ThemeColors'.
  Property 'trackOff' is missing in type '{ page: "#0f1b26"; surface: "#16283a"; border: "#2b4257"; text: "#e9eef3"; textMuted: "#a9b4c0"; heading: "#bfe3df"; error: "#ff9b85"; banner: "#0b3954"; onBanner: "#ffffff"; onBannerAccent: "#bfe3df"; ... 7 more ...; knob: "#ffffff"; }' but required in type 'ThemeColors'.
A) Nothing: theme.ts would report the same
B) The error points at the palette itself, the cause, with "Property 'trackOff' is missing"
C) It makes darkColors a ThemeColors at run time
D) It fills the missing role with the light value
Why: Without satisfies you only get theme.ts's error, further from the cause. With it, tsc stops you where the palette is written (the kit's run matches the lesson's card: 2 errors in 2 files).
A is wrong: That is the second error, further away.
C is wrong: satisfies is a check only; it changes nothing at run time.
D is wrong: Nothing is filled in: it is an error.
Q7
npx expo lint prints this for Screen.tsx after const { colors } = useTheme(); was put at the top of the file. Even if it ran, why would it be wrong?
52:20  error  React Hook "useTheme" cannot be called at the top level. React Hooks must be called in a React function component or a custom React Hook function  react-hooks/rules-of-hooks
it would run once, when the file loads: the same baked-in (daytime) colors; use createThemedStyles outside the component and call useStyles() inside
Why: Hooks only work inside components and other hooks (react-hooks/rules-of-hooks). And top-level code runs once: the phone can switch to dark mode and nothing follows. The kit's run matches the lesson's card (except the path, which is yours).
Q8
SwitchRow.tsx: npx tsc --noEmit prints four of these. What happened?
src/components/SwitchRow.tsx:25:37 - error TS2339: Property 'trackOff' does not exist on type '{ primary: ____ColorValue_Internal; background: ____ColorValue_Internal; card: ____ColorValue_Internal; text: ____ColorValue_Internal; border: ____ColorValue_Internal; notification: ____ColorValue_Internal; }'.
A) The editor imported expo-router's useTheme: the navigator's six colors; import it from @/hooks/useTheme
B) darkColors is missing trackOff
C) SwitchRow needs a ThemeProvider
D) ColorValue cannot hold a string
Why: The type lists primary, background, card, text, border, notification: the navigator's theme. Expo Router exports a useTheme too, and editors auto-import it.
B is wrong: That is TS1360 in colors.ts (Q6).
C is wrong: The provider is for the navigator; it does not change our hook.
D is wrong: The roles are strings; the property does not exist on that type.
Q9
Why does createThemedStyles build both style sets when the file loads, instead of calling StyleSheet.create inside each component?
A) StyleSheet.create cannot run inside a component
B) Hooks cannot return objects
C) It would work, but build new style objects on every render; two ready-made sets cost nothing at run time
D) The dark set must exist before the phone switches
Why: The lesson's answer: inside a component StyleSheet.create would run on every render. createThemedStyles makes the light and the dark set once and returns a tiny hook that picks one.
A is wrong: It can; it is just wasteful.
B is wrong: They can.
D is wrong: Nothing requires that; it is about render cost.
Q10
Sea Teal (#1f6f8b) reads 2.4:1 on the night page. What does the dark set do, and what follows for a filled button's text?
A) Keeps Sea Teal and makes the button bigger
B) Uses pure black for the page
C) Inverts every color
D) A lighter teal (#7cc6d6, 9:1), so onAction flips to dark text (the night page color)
Why: Dark mode is designed, not inverted: lighter, softer accents, the same 4.5:1 and 3:1 rules, no pure black. A light teal button then needs dark words.
A is wrong: Size does not fix contrast.
B is wrong: No pure black: a deep blue-black page, lighter raised surfaces.
C is wrong: Inverting breaks the brand and the badges.
Q11
With React Native's plain useColorScheme, the web preview in dark mode showed a Sand page under dark cards, with no error. Why, and what fixed it?
the page is drawn on a server first (light, it cannot know the browser's setting) and React kept the server's look while hydrating; useColorScheme.web.ts starts as 'light' like the server (useSyncExternalStore's third argument) and switches right after
Why: web.output: server (the template's setting) draws each page on a server; production React silently keeps mismatched class names. Phones do not have this problem (the lesson's quiz Q5).
Q12
On a 1280-wide browser window the cards should stop at 960 and sit in the middle. What does that need?
A) maxWidth: 960, alignSelf: 'center' (and width: '100%') on the content: no window size at all
B) useWindowDimensions and a margin computed from it
C) Platform.select({ web: 960 })
D) A third breakpoint in useColumns
Why: Flex, percentages and maxWidth first: maxWidth with alignSelf: 'center' is max-width + margin: 0 auto. Use the window's size only when the structure changes (one column to two).
B is wrong: Works, but the plain style tools do it without a hook.
C is wrong: Width, not platform, decides layout.
D is wrong: Columns are a structure change; this is only a limit.

import { act, render, screen } from '@testing-library/react-native';
import { Dimensions } from 'react-native';

import { PlatformNote } from './PlatformNote';

// The words a Text shows (its children without false and null, the way React draws them)
const shown = (children: unknown[]) => children.filter((c) => typeof c === 'string' || typeof c === 'number').join('');
const text = () => shown(screen.getByText(/ by /).props.children);

  lines.push('PlatformNote:                  ' + shown(screen.getByText(/back/).props.children));
  const fs = require('fs') as { writeFileSync(file: string, text: string): void }; // Node's, inside Jest

The Lesson Page's Own Quick Quiz

Lesson 2.5 · Responsive, Platform-Specific and Themed UI
  1. C The layout stays as it was when the file loaded: The width was read once, when the file loaded, and never again. useWindowDimensions inside the component re-renders it whenever the window changes, which is what a split screen, a rotation or a resized browser needs.
  2. A The color was fixed when the file loaded; the screen needs themed styles: StyleSheet.create at the top level runs once, when the file loads, with whatever color it was given. Colors in styles have to come through createThemedStyles (one sheet per theme, picked by a hook), and colors for props from useTheme().
  3. D The window's width from useWindowDimensions, compared with 700: Layouts follow the room the window has right now, in density-independent pixels, whatever the device or platform. useColumns reads useWindowDimensions and compares the width with layout.twoColumns.
  4. B tsc reports that trackOff, action and knob do not exist on the navigator's colors: Expo Router's useTheme returns the navigator's theme, whose colors are primary, background, card, text, border and notification. tsc reports that trackOff, action and knob do not exist on that type. Fix the import.
  5. C A useColorScheme.web.ts that starts as 'light', like the server, then switches: The server cannot know the browser's setting and draws the light page. useColorScheme.web.ts starts as light, like the server (the third argument of useSyncExternalStore), then switches after hydration. Phones keep React Native's hook.

Exit Ticket

  1. Stale at load: a StyleSheet color → createThemedStyles; Dimensions.get → useWindowDimensions; a hook at the top of a file → inside the component. Any one.
  2. The window: width decides structure; an Android tablet, a split-screen iPad and a wide browser all need two columns, and a platform check gets them wrong.
  3. A designed night: contrast must still pass (lighter accents, dark text on them), no pure black, raised surfaces lighter; badges and the banner stay on purpose.

Common Wrong Answers and What They Reveal

  • Q1 B or D. Has not separated "when the file loads" from "when the component renders". Show line 3 of the demo again.
  • Q3 B. Expects Jest to be the web preview: each environment runs its own branch.
  • Q5 A. Thinks TypeScript knows the platform; it checks the plain file.
  • Q6 A. Does not see the value of an error at the cause: compare the two error locations.
  • Q9 A or B. Believes the rule is technical; it is about render cost.
  • Q12 B. Reaches for the window first: flex, percentages and maxWidth come first.
