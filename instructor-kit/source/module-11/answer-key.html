Session 11 12 self-check items Confidential

Warm-up

  1. **W1.** Which file answers the address /cleanups/e08, and how does the screen read e08? **Answer:** src/app/cleanups/[id].tsx; useLocalSearchParams<{ id: string }>() (typed params, Lesson 4.1).
  2. **W2.** The tabs live in src/app/(tabs)/. What does the folder name (tabs) add to an address? **Answer:** Nothing: a group's name is not part of the address (/profile is (tabs)/profile.tsx, Lesson 4.2).
  3. **W3.** Before you go is a modal. What does presentation: 'modal' change on a phone, and in the web preview? **Answer:** On a phone the screen slides up over the tabs; the web preview shows it as an ordinary screen with a back arrow (Lesson 4.2).
  4. **W4.** Its Done button calls router.back() only if (router.canGoBack()). Why the check? **Answer:** A modal opened straight from its address has nothing underneath: back would go nowhere, so it replaces itself with the Cleanups tab (Lesson 4.2). Today that question returns twice.

4.3 · Sign-In Flows and Protected Routes: self-check

Q1
After Theo signs in on a phone, what does Shoreline Crew write to secure storage?
A) His email and password, so it can sign in again at the next start
B) The session as JSON: the API's token and the user it belongs to
C) Only his email; the token stays in memory
D) The token, in an EXPO_PUBLIC_ variable
Why: saveCopy writes JSON.stringify(session) (token + user) under shoreline-crew-session; secure storage holds strings, so the object is saved as JSON. The password is sent once and never stored (Lesson 4.3, Never store the password).
A is wrong: A stolen password works everywhere it was reused; a token can be ended.
C is wrong: Then a restart would sign him out: the token is what must survive.
D is wrong: EXPO_PUBLIC_ text is copied into the app's JavaScript when it is built: anyone can read it.
Q2
npx tsc --noEmit prints this after a change to Profile. What is it telling you, and what are the two honest fixes?
src/app/(tabs)/profile.tsx:14:17 - error TS18047: 'session' is possibly 'null'.

14   const token = session.token;
                   ~~~~~~~


Found 1 error in src/app/(tabs)/profile.tsx:14
A guest has no session, so session can be null there: check for null first, or write session?.token when "no token" is a fine answer (as Profile does)
Why: TS18047 is TypeScript doing its job: useSession() returns Session | null. The kit ran it on the app as Lesson 4.3 ends; the output is the lesson's card, word for word.
Q3
What does expo-secure-store 58 do in the web preview?
A) It stores values in localStorage instead
B) It stores values in memory until the page reloads
C) isAvailableAsync() resolves to false, and get/set reject with a TypeError
D) It throws as soon as the module is imported
Why: The lesson measured it: isAvailableAsync() is false; getItemAsync rejects with TypeError: ExpoSecureStore.default.getValueWithKeyAsync is not a function. So loadSession() asks first and keeps the web preview's session in memory only.
A is wrong: That would be the unsafe fallback the lesson rejects on purpose: any script on the page can read localStorage.
B is wrong: The APP keeps it in memory in the web preview; the library itself stores nothing there.
D is wrong: Importing works; only the calls fail.
Q4
A teammate's sign-in screen calls setSession(session) and THEN router.back(). Theo opens it from the Profile tab and signs in. Where does he land?
A) Back on Profile, signed in
B) On the sign-in screen, which stays open
C) On the not-found screen
D) On the Cleanups tab: the guard removed the screen before back() ran
Why: The moment the session is set, Stack.Protected guard={session === null} takes the sign-in route away while it is still open, and Expo Router redirects to the anchor (the first screen). Close first, then set the session (Lesson 4.3, Step 5; measured).
A is wrong: That is what the lesson's order (back, then setSession) gives.
B is wrong: A guarded screen cannot stay: its route no longer exists.
C is wrong: The route did exist when he opened it.
Q5
request() forgets the session on a 401 only if (response.status === 401 && session !== null). Why the second condition?
A) A wrong password is also a 401, and that request carried no token: there is nothing to forget
B) Guests never get a 401
C) The API sends 401 only to signed-in requests
D) Without it, TypeScript reports that session is possibly null
Why: POST /api/auth/sign-in with a wrong password answers 401 "Email or password is incorrect." (the kit's demo). That is a failed try, not an ended session; the sign-in screen shows the API's words.
B is wrong: A guest gets a 401 from a wrong password, and from /api/auth/me ("Sign in first.").
C is wrong: The sign-in endpoint answers 401 to a guest.
D is wrong: setSession(null) compiles either way.
Q6
Why does useSession() pass a third function, () => null, to useSyncExternalStore, and what do you see without it?
The web preview draws each page on a server first, where nobody is signed in; without it Metro prints Missing getServerSnapshot, which is required for server-rendered content on every page load (phones never call it)
Why: The page still appears because React gives up on the server's version and draws it again in the browser; tsc and the linter say nothing (Lesson 4.3, the first Common Mistake; Lab 4.3's useSession.ts).

  "message": "Your session has ended. Sign in again."
}
Why: 401 "Your session has ended. Sign in again." even for a public beach: the API checks a token before routing, because the request claimed to be someone. This is how the Cleanups list can say the sign-in has ended after an API restart.

4.4 · Deep Links: self-check

Q7
In the web preview, what does Linking.createURL('/cleanups/e08') give?
A) shorelinecrew://cleanups/e08
B) exp://192.168.1.42:8081/--/cleanups/e08
C) /cleanups/e08
D) http://localhost:8081/cleanups/e08
Why: A browser needs an ordinary web address, measured in the lesson. In Expo Go the documentation gives the exp://…/--/ form, in a build shorelinecrew://. That is why the app never writes shorelinecrew:// by hand.
A is wrong: Only a build of the app registers that scheme.
B is wrong: That is Expo Go's form, for a phone running the project.
C is wrong: A path alone is not a link anyone can tap.
Q8
npx tsc --noEmit prints this. What does the type want, and what is the fix?
src/app/cleanups/[id].tsx:97:25 - error TS2345: Argument of type '{ title: string; }' is not assignable to parameter of type 'ShareContent'.
  Property 'message' is missing in type '{ title: string; }' but required in type '{ title?: string | undefined; url?: string | undefined; message: string; }'.

97       await Share.share({ title: event.title });
                           ~~~~~~~~~~~~~~~~~~~~~~
ShareContent is "a url, or a message, or both" (two object types joined by |): give it a message (the lesson puts the link inside it)
Why: TypeScript picked the union member with message to complain about. The kit's run on the 4.4 app is the lesson's card, word for word.
Q9
You write export const unstable_settings = { anchor: 'index' } in the root layout. What do npx tsc --noEmit and npx expo lint say?
A) TS2322: 'index' is not assignable to the route names
B) Nothing new: tsc prints nothing, lint only its two env: lines
C) One lint error from expo-router's rules
D) Metro refuses to start
Why: The setting is a plain object, so no checker knows it is wrong (the kit ran both). Expo Router finds out when it builds the stack: a blank web page and "The initial route name "index" was not found in the layout", with the list of the layout's routes. Lab 4.4 Task 3 shows the same message in Jest.
A is wrong: The export is not typed against your routes.
C is wrong: No lint rule reads it.
D is wrong: Metro starts; the error appears when a page is drawn.
Q10
With the anchor in place, the not-found screen still says <Link href="/" replace>. A volunteer presses Back to the cleanups. What is on the page?
A) The Cleanups tab, exactly as before
B) A blank screen
C) Two tab bars: a copy of the tabs on top of the ones underneath
D) The not-found screen again
Why: The tabs were already underneath (the anchor); replacing the not-found screen with / put a second copy on top (measured: two tab bars). Nothing warns you. dismissTo closes screens back to the existing tabs (Step 3).
A is wrong: It looks like it, which is why this bug is sneaky.
B is wrong: Something renders: twice.
D is wrong: The not-found screen was replaced.
Q11
Which of these may a link into Shoreline Crew carry?
A) The volunteer's token, so the friend is signed in at once
B) A password-reset code
C) The id of a cleanup
D) ?join=yes, so the cleanup signs the reader up as it opens
Why: Links end up in message histories and screenshots and can be written by anyone: they carry only public ids, and a link only ever opens a screen (Lesson 4.4; Lab 4.4 Task 3 makes ?join=yes harmless).
A is wrong: Never a token or a password in a link.
B is wrong: shoreline-api has no such codes, and real ones are short-lived and single-use.
D is wrong: A link that acts on its own could be sent to anyone.
Q12
npx uri-scheme list prints Could not find any native URI schemes to list. What does it mean?
A) The project has no ios/ or android/ folders yet: Expo writes the scheme into them at build time
B) app.json has no scheme
C) uri-scheme failed to install
D) The phone is not connected
Why: uri-scheme reads the native projects, and an Expo project has none until a build (Module 9). The scheme lives in app.json until then: the kit's grep found "scheme": "shorelinecrew" in it.
B is wrong: It is there, written by create-expo-app.
C is wrong: It ran and answered.
D is wrong: list does not talk to a phone.

The Lesson Pages' Own Quick Quizzes

Lesson 4.3 · Sign-In Flows and Protected Routes
  1. B In secure storage, with expo-secure-store: expo-secure-store keeps it in the iOS Keychain or encrypted with the Android Keystore, where other apps cannot read it. It is async, so the app waits for it at startup.
  2. D The Cleanups tab, because the guarded route redirects to the stack's first screen: The guard is false while someone is signed in, so the sign-in route is taken out and Expo Router redirects to the root stack's anchor, the tabs, which open on Cleanups.
  3. A The API answers 401, and the app forgets the session and clears the saved copy: The API no longer knows the token and answers 401. The client forgets the session, the listener in session.ts deletes the saved copy, and the screens redraw as signed out.
  4. C Until secure storage answers, the app does not know who is signed in, and screens and guards would act on the wrong answer: Reading secure storage is async. Without the wait, the first frames would say Not signed in, and guards and redirects would act on that wrong answer before the saved session arrived.
  5. B The web preview has no secure storage, so the session lived in memory only: A browser has no keychain: isAvailableAsync() is false, so Shoreline Crew keeps the session in memory only, and a reload starts with nothing. On a phone it is saved.
Lesson 4.4 · Deep Links
  1. D exp://192.168.1.42:8081/--/cleanups/e08: Expo Go owns the exp scheme. The address says which development server to load, and everything after /--/ is the path inside your app. Linking.createURL builds exactly this in Expo Go.
  2. B The Cleanups tab appears, because the tabs were underneath the cleanup: The anchor is always at the bottom of the root stack, so the linked cleanup opens on top of the tabs, and back shows the Cleanups tab.
  3. C The Cleanups tab, because the guarded route redirects to the anchor: The sign-in route does not exist while someone is signed in, so Expo Router redirects to the stack's anchor, the tabs, which show Cleanups. A link from outside follows the same rule as a link inside the app.
  4. A "Join me at Weekend Cove!" without the link: React Native's Android code passes only the title and the message to the share sheet, so the link in url is dropped. Put the link inside the message.
  5. B Sign the volunteer up for the cleanup as soon as it opens: Anyone can write and send a link, so a link only opens a screen. Signing up, cancelling or deleting happens when the volunteer presses a button on that screen.

Exit Ticket

  1. The token: in secure storage (expo-secure-store: the Keychain, or Keystore-encrypted on Android); reading it is async, and until it answers the app cannot know who is signed in, so guards and screens would act on the wrong answer.
  2. The order: on the Cleanups tab. Setting the session made guard={session === null} false while the sign-in screen was open; Expo Router redirected to the anchor before router.back() ran. Close first, then set the session.
  3. Three forms: shorelinecrew://cleanups/e08 in a build; exp://192.168.1.42:8081/--/cleanups/e08 (their own address) in Expo Go; http://localhost:8081/cleanups/e08 in the web preview. Linking.createURL picks.

Common Wrong Answers and What They Reveal

  • Q1 A. Still thinks of a session as remembered credentials. Retell the wristband: the band, never the ID card.
  • Q3 A or B. Mixes up the library and the app. The library stores nothing in a browser; the app chooses memory only.
  • Q4 A. Has not seen the guard act while a screen is open. Run Lab 4.3's last test with and without Task 1.
  • Q7 A. Expects a custom scheme to work everywhere. Point at the three-forms table.
  • Q9 A or C. Trusts the checkers with configuration. Show P4: silence.
  • Q11 D. The security point of the session: a link only opens a screen.
