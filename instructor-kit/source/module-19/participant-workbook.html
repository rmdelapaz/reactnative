Lessons

7.3

Motion Polish

By the end you can
  • Animate views that appear, disappear and move with Reanimated's layout animations (entering, exiting, layout) and keep the first render still with LayoutAnimationConfig
  • Recognize where layout animations misbehave: rows recycled by FlashList, and a resizing container with moving children
  • Play a Lottie animation with lottie-react-native, set up what the web preview needs for it, and check where an animation file comes from before shipping it
  • Follow the phone's Reduce Motion setting while the app runs, with AccessibilityInfo and ReducedMotionConfig, and cover what Reanimated's setting does not reach
  • Decide whether an app needs its own motion switch, and build one that only ever adds to the phone's setting
Key ideas
  • Layout animations are three props on an Animated view: entering (mount), exiting (unmount: Reanimated keeps a copy long enough to animate it away), layout (its place changed). Keys tell them which view is which.
  • The first render is not news: <LayoutAnimationConfig skipEntering> keeps what is there when a screen opens still; later arrivals still animate.
  • Where they misbehave: layout on a box that only gets shorter fights its children's own; FlashList rows are recycled, never mounted or unmounted, so they do not animate in or out.
  • Lottie plays designer-made vector animation from a JSON file; the web preview needs @lottiefiles/dotlottie-react as well; every file has an owner and a license.
  • Reduce Motion, live: AccessibilityInfo's reduceMotionChanged feeds a store; <ReducedMotionConfig> tells Reanimated; Lottie and native screens ask useReduceMotion() themselves. The app's own switch only adds: phone || reduceMotion.
Worked example: the bench, in code

The waiting cards in the finished Logbook: one Animated.View around each SwipeToRemove, with three props. The swipe moves the card inside; the layout animation moves the whole thing:

shoreline-crew/src/app/(tabs)/logbook.tsx
      // A card that leaves slides out the way the swipe points; the cards below glide up
      <Animated.View
        key={log.clientId}
        entering={FadeIn}
        exiting={FadeOutLeft}
        layout={LinearTransition}

Read it as the bench: entering = sitting down (a log that arrives while you watch), exiting = standing up and walking off to the left (the way the swipe points), layout = the others shuffling along. Around the whole screen, <LayoutAnimationConfig skipEntering>: when the crew first sits down, nobody makes a show of it. And the rule that decides whether any of it moves:

shoreline-crew/src/state/motion.ts
export function useReduceMotion(): boolean {
  const phone = usePhoneReducesMotion();
  const { reduceMotion } = useSettings();
  return phone || reduceMotion;

Two sources, one answer, and || means the app can only ever ask for LESS motion.

8.1

Accessible Mobile Apps

By the end you can
  • Explain how VoiceOver and TalkBack move through a React Native screen, and describe an element with its role, label, state, value and (sometimes) hint
  • Audit a whole app systematically: automated checks and the accessibility tree in the web preview, then a screen reader and large text on a phone, knowing what each one can and cannot tell you
  • Hide decoration with aria-hidden, group what belongs together, and make names that start with the words people see
  • Announce changes on an iPhone, where accessibilityLiveRegion does nothing
  • Support the phone's text size: keep allowFontScaling, use maxFontSizeMultiplier only where you can justify it, and switch layouts with fontScale
  • Give every control a touch target of at least 44 by 44 points (48 by 48 in Shoreline Crew)
Key ideas
  • A screen reader meets one element at a time, in order, by ear. Each element is a radio call: label, role, state, value, sometimes a hint.
  • accessible groups a view into one element (never around controls); aria-hidden removes decoration on iPhone, Android and the web preview alike (a boolean, not the string "true").
  • An audit runs every screen and state through the web preview's checks AND a screen reader and the largest text on a phone. A clean web audit is not an accessible app.
  • Names start with the words people see (Label in Name): voice control users say them. iPhone has no live regions: announceForAccessibilityWithOptions(words, { queue: true }).
  • Large text: layouts that grow first, a fontScale layout second, maxFontSizeMultiplier only on big text, allowFontScaling={false} never. Targets: 48 points here, and the obvious thing is the target.
Worked example: one row, one target, one stop

Lesson 8.1's fix for the switch rows, the core of it. Before: the words and the switch were two stops for a screen reader, and only a 40 by 20 switch answered a finger:

shoreline-crew/src/components/SwitchRow.tsx
    <Pressable
      onPress={() => onValueChange(!value)}
      accessible={false} // not a stop of its own for screen readers: the switch is
      tabIndex={-1} // nor for a keyboard (Android, the web preview): Tab goes to the switch
      style={styles.row}
    >
      {/* Seen, not read: the switch's accessibilityLabel says the same words */}
      <AppText style={styles.label} aria-hidden>
        {label}
      </AppText>
      <Switch
        value={value}
        onValueChange={onValueChange}
        accessibilityLabel={label} // a screen reader says the words with the switch

Three moves: the row presses the switch (a tap anywhere flips it once; the switch itself takes no touches, pointerEvents: 'none'), the row is not a stop of its own (accessible={false}, tabIndex={-1}), and the words are seen, not read (aria-hidden), because the switch says them. The radio call is now one: "Reduce motion in this app, switch, off".
