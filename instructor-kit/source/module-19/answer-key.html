Session 19: Motion Polish and Accessible Apps

Answers and reasoning for every Session 19 item: the warm-up, both self-checks, the predict-then-check items, the lab reference outputs, the lesson pages' own quizzes and the exit ticket.

Session 19 12 self-check items Confidential

Warm-up

  1. Tally counts every frame on the UI thread. Why is its number a shared value and not React state? **Answer:** State would re-render the component on the JS thread every frame (60 times a second or more), competing with everything else React does; a shared value changes on the UI thread, and only the number to show reaches React, through scheduleOnRN (Lesson 7.1, the skipper and the helm).
  2. A gesture callback calls a React setter directly. Why does the web preview not catch it? **Answer:** The web preview runs worklets on the JS thread, so the call works there; on a phone the callback runs on the UI thread and needs scheduleOnRN (Lesson 7.1's mistakes; 7.2's callbacks are worklets too).
  3. Why does every waiting card have a visible Remove button when the swipe already removes it? **Answer:** Every gesture needs another way (WCAG 2.5.1): screen-reader users, switch users and anyone who never discovers the swipe press the button (Lesson 7.2). Today's 8.1 audit relies on that.

7.3 · Motion Polish: self-check

Q1
Every time Theo opens the Logbook, all ten cards fade in. Which change stops that and still lets a log that arrives while he watches fade in?
A) Remove entering={FadeIn} from the cards
B) Wrap the content in <LayoutAnimationConfig skipEntering>
C) Render <ReducedMotionConfig mode={ReduceMotion.Always} /> on the Logbook
D) Give each card a new key on every render
Why: skipEntering skips the entering animations of everything inside while the wrapper itself first mounts; views that mount later still animate (Lesson 7.3, The first render is not news).
A is wrong: Then a real arrival does not fade in either.
C is wrong: That stops all motion, for everyone, everywhere.
D is wrong: A new key makes React mount a new view every render: more fading, not less.

Q3
Maya's phone has Reduce Motion on. In Profile she turns "Reduce motion in this app" off, then sends a log. What does she see, with Lesson 7.3's code?
A) The check mark draws itself: the switch is off
B) Nothing at all: no mark and no heading
C) A still check mark: useReduceMotion() is phone || reduceMotion
D) The animation, at half speed
Why: The app's switch only ADDS: the phone's setting is the person's word for every app and always wins. LogSentMark reads useReduceMotion() and shows the still sent icon.
A is wrong: That would be the three-way choice the lesson rejects: never turn motion back on against the phone.
B is wrong: The heading always says it in words; only the mark changes.
D is wrong: No setting slows Lottie down.
Q4
Why does the root Stack get animation: reduceMotion ? 'fade' : 'default', when <ReducedMotionConfig> is already rendered?
A) ReducedMotionConfig only works in development
B) The web preview needs it to slide screens
C) Fades are faster to bundle than slides
D) Screens slide with the phone's native navigation, not with Reanimated, so ReducedMotionConfig never reaches them
Why: The lesson's motion inventory: Reanimated functions and layout animations follow ReducedMotionConfig; Lottie and native screen transitions do not, so useReduceMotion() covers them. Expo Router's types say the option works only on iOS and Android: check it on a phone.
A is wrong: It works in any build; only its warning is development-only.
B is wrong: The web preview has no slide to begin with.
C is wrong: Bundling has nothing to do with it.
Q5
Lab 7.3's starter decides reduceMotionFrom(phoneReduces, appSwitch) with return appSwitch. Who does that hurt, and what is the one-line fix?
A volunteer whose PHONE asks for less motion and whose app switch is off gets full motion back; return phoneReduces || appSwitch
Why: The switch may only add to the phone's setting (Lesson 7.3, An In-App Switch: The Decision). The lab's first test fails on exactly that case: reduceMotionFrom(true, false) must be true.
Q6
A teammate found a lovely free confetti animation on a marketplace for the final project. What do you check before it ships in a store app?
A) Who made it, and that its license allows your use, commercial use included
B) Only that it is a JSON file and not a GIF
C) That it loops, so the celebration lasts
D) Nothing: free files on marketplaces are free to use
Why: A Lottie file is artwork, and artwork has an owner. Each file has its own license (LottieFiles shows one on every animation: read it); keep the source and license next to the file (Lesson 7.3, Where did this animation come from?).
B is wrong: Being JSON says nothing about who owns it.
C is wrong: Play once at the moment that matters, and stop (battery, and motion with a job).
D is wrong: Some "free" files on other sites were simply copied from someone else.

8.1 · Accessible Mobile Apps: self-check

Q7
Lesson 8.1's mental model is the radio call. Name the parts a screen reader says for one element, in order, and the prop (or props) React Native gives you for each.
Label (accessibilityLabel, or the text inside), role (accessibilityRole), state (aria-checked, aria-expanded, aria-disabled…), value (accessibilityValue) and sometimes a hint (accessibilityHint)
Why: A good call is short, never repeats itself, and never makes the listener guess; decoration is radio silence (aria-hidden). The exact words and order belong to each screen reader.

npx tsc --noEmit prints this after a change in Icon.tsx. What fixes it?

A) Change SymbolView to View
B) Write aria-hidden on its own (it means true), not aria-hidden="true"
C) Add // @ts-ignore above the line
D) Remove accessibilityElementsHidden
Why: In HTML, ARIA attributes are strings; in React Native, aria-hidden is a boolean. The kit's run is Lesson 8.1's card word for word; Lab 8.1 shows the same error on a Text.

C is wrong: That hides the error and keeps a string where a boolean belongs.

Q9
Before Lesson 8.1, Maya (VoiceOver) heard nothing when her waiting log was sent; Theo (TalkBack) heard "Log sent. Thank you!". Which change made the iPhone speak?
A) aria-live="polite" instead of accessibilityLiveRegion
B) accessibilityRole="alert" on every text
C) A bigger font for the heading
D) On iOS, AppText calls AccessibilityInfo.announceForAccessibilityWithOptions(words, { queue: true })
Why: accessibilityLiveRegion is Android only (React Native's documentation); iPhone needs to be asked. Because all 21 live texts go through AppText, one effect there covers them; queue: true lets VoiceOver finish what it is saying (Lab 8.1, Task 2 does the same on a new component).
A is wrong: That is the web's attribute: react-native-web makes it from accessibilityLiveRegion; VoiceOver on a phone never sees it.
B is wrong: An alert role on everything would make every text urgent.
C is wrong: Size has nothing to do with being announced.
Q10
At the largest text size, two tide times side by side run into each other. Which fix comes FIRST?
A) allowFontScaling={false} on both times
B) A fixed width and height for each tile
C) When useWindowDimensions().fontScale is large, put the tiles on top of each other
D) A smaller font size for everyone
Why: Layouts that let text grow first, a different layout at a large fontScale second, maxFontSizeMultiplier only on text that is already big, allowFontScaling={false} never (Lesson 8.1, The Phone's Text Size; Lab 8.1, Task 3).
A is wrong: It switches the person's setting off, for exactly the person who needed it.
B is wrong: A fixed size for text is the problem, not the fix ("M ee t").
D is wrong: Everyone loses so that nothing changes shape.
Q11
In Lab 8.1's solution, a test does screen.getByText('☑') on a packed row. Jest prints this. Why?
● the picture of the state, found like a screen reader would
  Unable to find an element with text: ☑
A) The ☑ is aria-hidden, and Testing Library, like a screen reader, skips hidden elements unless a query asks for them
B) Jest cannot render emoji
C) The row was never rendered
D) getByText only finds buttons
Why: React Native Testing Library finds elements the way a screen reader meets them. The picture of the state is decoration: the checkbox's role and aria-checked already say it. { includeHiddenElements: true } finds it anyway, which is how the lab's tests check that it is there.
B is wrong: It is a plain Unicode character, rendered like any text.
C is wrong: The checkbox called Gloves is on the screen in the same test.
D is wrong: getByText finds any text a screen reader could reach.
Q12
The audit found every Profile setting read twice ("Reduce motion in this app", then "…, switch, off"), and only the 40 by 20 switch answered a finger. What did Lesson 8.1 do?
A) Wrapped each row in a View with accessible, so the row and the switch are one element
B) The row became a Pressable that flips the value (not a stop of its own); the words are aria-hidden; the switch keeps its label and takes no touches
C) Removed the words and kept only the switch
D) Made the switch bigger with transform scale
Why: One row, one target, one stop: accessible={false} and tabIndex={-1} on the row, aria-hidden words, the Switch with accessibilityLabel={label} and pointerEvents: 'none' (measured: a tap on the words, the gap or the switch flips it once).
A is wrong: Grouping a control away: an accessible view hides the switch inside it from screen readers as a control of its own.
C is wrong: People need the words; voice control users say them.
D is wrong: A scaled switch is still a small target with words that do nothing.

The Lesson Pages' Own Quick Quizzes

Lesson 7.3 · Motion Polish
  1. B layout={LinearTransition} on the cards that move: A layout transition animates a view whose position or size changed because something else changed. The second card moved up, and LinearTransition on it turned the jump into a glide.
  2. D The first screenful fades in once; rows scrolled into view and removed rows do not animate: FlashList recycles rows instead of mounting and unmounting them. Only the first screenful mounts, so it fades in; rows scrolled into view and removed rows do not animate at all (measured: 38, 0 and 0 animations).
  3. A A still check mark above Log sent. Thank you!: loadMotion subscribed to reduceMotionChanged, so the store already knows. useReduceMotion returns true, and LogSentMark shows the still check mark. No restart is needed, unlike Lesson 7.1.
  4. C Lottie's own player draws the check mark, and it never hears Reanimated's setting: ReducedMotionConfig changes what ReduceMotion.System means for Reanimated's animations. The check mark is drawn by Lottie's own player, which knows nothing about Reanimated, so the component has to decide itself, with the same hook.
  5. A They still show their totals at once: the phone's setting wins: The app's switch only adds: useReduceMotion returns phone OR switch, so the phone's setting still wins, and the note under the switch says so. An app should never turn motion back on against an accessibility setting.
Lesson 8.1 · Accessible Mobile Apps
  1. C The words and the switch were two elements; the words are now hidden and the row presses the switch: The words were a text element and the switch, with the same words as its label, was a second one. Hiding the words with aria-hidden leaves one stop, the switch, and the row as a Pressable makes the whole row the touch target.
  2. A accessibilityLiveRegion is Android only; iPhone needs announceForAccessibility: React Native's documentation lists accessibilityLiveRegion as Android only. On iPhone an app asks VoiceOver to speak with AccessibilityInfo.announceForAccessibility, which AppText now does for every live text.
  3. D A different layout when fontScale is large: two tallies to a row: Change the layout, not the text: with fontScale at 1.5 or more, each tally takes at least 40 percent of the row and the row wraps, so they sit two to a row. A cap like maxFontSizeMultiplier is for text that is already large, and only after the layout works.
  4. B The mechanical problems axe can find are fixed; a screen reader and large text on a phone are still needed: Automated checks catch part of the mechanical problems, and on React Native they check the web translation of the props. Reading order, what the screen readers really say, announcements and large text need a person with a phone.
  5. A "Logbook (2), not sent yet": Label in Name: the accessible name contains the visible words, at the start, so speaking what you see matches. The extra not sent yet helps screen-reader users without getting in the way.

Exit Ticket

  1. The phone wins: no, the tally does not count. useReduceMotion() is phone || reduceMotion, true; ReducedMotionConfig switches to Always and the tally's withTiming jumps to its end. The app's switch can only add.
  2. Beyond Reanimated: the Lottie log-sent mark (LogSentMark shows the still sent icon from useReduceMotion()) or the native screen transitions (the root Stack's animation: 'fade', phones only). The tally's CSS color highlight is kept on purpose (a dissolve in place).
  3. Only a phone: what VoiceOver or TalkBack actually say and in which order; whether announcements arrive (iPhone); how the largest text lays out (the web preview's text size is always 1); whether targets are easy to hit with a thumb; native headers and tab bars (any two).

Common Wrong Answers and What They Reveal

  • Q1 A. Removes motion instead of choosing when it plays. Show the demo: open the Logbook (nothing moves), then Send now (the new entry fades in).
  • Q2 B. Thinks every new package needs a development build. The phone was fine: the stack names a .web.js file.
  • Q3 A. Expects the app's switch to override the phone. Back to the decision table: never turn motion back on against the phone.
  • Q8 C. Silences the checker instead of reading it. Read the LAST line of the error first.
  • Q10 A. The most common real-world "fix". Ask whose setting it switches off.
  • Q12 A. Groups the control away: the lesson's Elements section and the 4.1 decision to keep two buttons on the card.
