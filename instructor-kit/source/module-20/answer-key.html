8.2 · Testing the App's Logic: self-check

Q1
The HQ's test files began with import { describe, it, expect, vi } from 'vitest'. What does a Shoreline Crew test file import instead?
A) import { describe, it, expect, jest } from 'jest-expo'
B) Nothing: describe, it, expect and jest are globals, typed by @types/jest through "types": ["jest"]
C) import { describe, it, expect } from '@testing-library/react-native'
D) import * as vi from 'jest', so the HQ's vi.fn() keeps working
Why: Jest puts its functions on the global object; TypeScript learns about them from @types/jest, which TypeScript 6 loads only when tsconfig.json lists it in types (Lesson 8.2, From Vitest to Jest). vi.fn() becomes jest.fn().
A is wrong: jest-expo is a preset (settings), not a library of test functions.
C is wrong: React Native Testing Library brings render and screen (Lesson 8.3), not describe and it.
D is wrong: There is no vi in Jest: rename the calls to jest.fn(), jest.mock(), jest.mocked().
Q2
A learner types npx jest src/state/sendLogs.test.ts and gets this. What do you tell them?
 FAIL  src/state/sendLogs.test.ts
  ● Test suite failed to run

    Must use import to load ES Module: ~/shoreline/shoreline-crew/node_modules/msw/lib/core/index.js
A) Add msw to transformIgnorePatterns, as the message suggests
B) Upgrade Node to the newest version
C) Run npm test -- --watchAll=false src/state/sendLogs.test.ts: the script starts Node with --experimental-vm-modules
D) Reinstall MSW with npm install msw@2
Why: MSW 3 is ES modules only; Jest loads those from node_modules only with Node's VM-modules feature on, and the flag lives in the package.json test script. Pass extra options after -- (Lesson 8.2, Common Mistakes; the kit ran it: the same message).
A is wrong: The lesson tried it: MSW 3's dependencies ship .mjs files, and transforming does not help.
B is wrong: The kit's run already used Node 24.22, the version the message asks for.
D is wrong: Downgrading MSW leaves the course's handlers and setup behind; the script is the fix.
Q3
After someone tidied package.json and jest.setup.ts, the sender's tests print this (each failure shows "attempts": 1). Where do you look first?
 FAIL  src/state/sendLogs.test.ts
  ✕ sends a waiting log, saves it in the logbook, and takes it out of the queue
  ✓ sends nothing while the phone is offline
  ✕ marks a log the server refuses, with the server's words
  ✓ keeps the log and counts the try when the server does not answer
  ✕ keeps the log for the next sign-in when the sign-in has ended
Test Suites: 1 failed, 1 total
Tests:       3 failed, 2 passed, 5 total
A) At testEnvironment in package.json, jest.environment.js and the useNodeFetch lines: requests are going to Expo's fetch
B) At sendWaitingLogs: its retry rule has a new bug
C) At shoreline-api: it must be running in another terminal
D) At AsyncStorage's mock in jest.setup.ts
Why: Exactly the two tests where no answer was expected pass. When every request "gets no answer" while MSW listens, suspect the fetch, not the app (the lesson's second mistake card, which the kit reproduced by removing the environment and the fetch lines).
B is wrong: The app is unchanged; the setup changed. That is the question to ask first.
C is wrong: No test talks to a real server: MSW answers inside Node.
D is wrong: A missing AsyncStorage mock stops the whole file before any test runs (Q5).
Q4
npm test -- --watchAll=false src/utils/haptics.test.ts fails like this, and the stack points into src/utils/haptics.ts:33. Is the app broken? What do you change?
● buzzes "success" when something went through
  TypeError: Cannot read properties of undefined (reading 'catch')
No: jest.mock('expo-haptics') made notificationAsync an empty jest.fn that returns undefined; give it a Promise with buzz.mockResolvedValue() (in a beforeEach)
Why: On a phone notificationAsync always returns a Promise, so .catch() is safe in the app. When a test fails inside code that works on your phone, check what your stand-ins return first (Lesson 8.2, Common Mistakes; the kit removed the lesson's beforeEach line and got this run).
Q5
A test file that loads the log queue stops before any test runs with the line below. Which kind of stand-in fixes it?
[@RNC/AsyncStorage]: NativeModule: AsyncStorage is null.
A) Nothing to write: jest-expo's automatic stand-ins cover it
B) The library's own Jest mock, once, in jest.setup.ts (jest.requireActual('@react-native-async-storage/async-storage/jest/async-storage-mock'))
C) A factory jest.mock() in every test file that saves anything
D) Running the tests on a phone, where AsyncStorage exists
Why: AsyncStorage is a community module, not an Expo one, so jest-expo has no stand-in for it; its authors ship an in-memory one for Jest. The message's last suggestion is the one for Jest (the kit removed the setup's mock and got this message).
A is wrong: jest-expo covers Expo's native modules only.
C is wrong: It works, but once in the setup file covers every test.
D is wrong: Jest runs in Node on your computer; no phone is involved.
Q6
Why does reminders.test.ts replace expo-notifications with a factory listing seven names, instead of jest.mock('expo-notifications') alone?
A) A factory is faster to type
B) jest-expo forbids automatic mocks of Expo modules
C) The test needs the real scheduler for the soonest-first order
D) The real module cannot even load under Jest (its setNotificationHandler fails), and an automatic mock loads it to build itself
Why: An automatic jest.mock('x') builds the stand-in by loading the real module; expo-notifications sets up listeners as it loads and fails without a phone ("handleSubscription.remove is not a function"). A factory that lists only what reminders.ts uses never loads it (Lesson 8.2, Three Ways to Stand In).
A is wrong: It is longer to type: it is chosen because it is the only one that works.
B is wrong: session.test.ts and haptics.test.ts use automatic mocks of Expo modules.
C is wrong: The order comes from mock.calls of the stand-in; nothing real is scheduled.
Q7
All 28 tests pass, and npx tsc --noEmit prints 113 errors starting with this line. Which change fixes it?
src/api/address.test.ts:3:1 - error TS2593: Cannot find name 'describe'.
...
Found 113 errors in 10 files.
A) Add import { describe } from '@jest/globals' to every test file
B) Delete the test files from the type check
C) Put "types": ["jest"] back in tsconfig.json's compilerOptions
D) Run the tests with --coverage
Why: TypeScript 6 loads no global types unless types names them; without it every describe, it and jest is unknown. Jest stays green because Babel strips the types without checking them (Lesson 8.2, Tests that pass in Jest and fail tsc; the kit's run is the lesson's card).
A is wrong: That would be 28 imports for what one setting does.
B is wrong: Then nothing checks the tests' types.
D is wrong: Coverage counts lines; it does not change what tsc knows.
Q8
Jest is green and npx tsc --noEmit is red on the same files. How can both be true, and which one decides that a task is done?
Jest runs the code after Babel strips the types, without checking them; tsc checks them. Done = both clean (tests, npx tsc --noEmit and npx expo lint)
Why: The same lesson as Session 1: running is not checking. The lesson's Step 6 runs all three, as a build server would.
Q9
npm test -- --watchAll=false -t "refuses" passes, and the same test fails in the full run. What is the most likely cause?
A) Something an earlier test changed in a module (a store, the session, a setting) was never reset in a beforeEach
B) Jest runs the tests in a random order
C) -t switches the mocks off
D) The mock API's sample data changed between the two runs
Why: State lives in modules and a test file does not reload between tests. The kit tried it: without onlineManager.setOnline(true) in the sender's beforeEach, the offline test leaves the phone offline for the three tests after it (Predict P1), and the refused test alone still passes.
B is wrong: Within a file Jest runs tests in the order written: that is why a leak repeats exactly.
C is wrong: -t only skips the other tests; every stand-in still applies.
D is wrong: startMockApi() resets the data before every test (api.reset()).
Q10
Which of these is most worth a test in Shoreline Crew, by the lesson's rule (invisible and costly)?
A) That Zustand stores the value add() sets
B) That Zod rejects a number where a string belongs
C) That the Cleanups screen looks right in dark mode
D) That a note starting with = cannot run as a formula in the exported CSV
Why: Things that leave the app (a file someone opens in a spreadsheet) fail where nobody watches. Skip what the libraries already test, and what a test cannot judge: how a screen looks is the phone's, and Lesson 8.3's.
A is wrong: Zustand's own tests cover that.
B is wrong: Zod's own tests cover that; test YOUR schema's promises instead.
C is wrong: A Jest test cannot judge looks; try it on a phone or in the web preview.
Q11
shoreline-api builds its sample data around today's date, in the mock API too. Which assertion stays true tomorrow?
A) expect(first.content.body).toContain('July 4')
B) expect(scheduledIds()).toEqual(['reminder-e08', 'reminder-e10', 'reminder-e11', 'reminder-e13'])
C) expect(event.date).toBe(new Date().toISOString().slice(0, 10))
D) expect(new Date(event.date).getDay()).toBe(6)
Why: Ids, titles, the API's messages and the order stay the same; the dates move with today. Fixed dates belong only in objects you build yourself, like makeEvent() (Lesson 8.2, Dates in the sample data).
A is wrong: The printed date changes every day.
C is wrong: Only today's cleanup has today's date, and only today.
D is wrong: The weekday moves with the date.
Q12
Name one thing the haptics tests can never tell you, and who or what does.
That the buzz feels right, or that an iPhone with System Haptics off stays still: trying it on a real phone (Lesson 6.5's phone checks)
Why: A stand-in answers what you told it to. Tests prove the app's decisions are right for the answers you imagined; a phone (and Lesson 8.3's end-to-end flows) proves the answers are the ones it really gives.

and alone:

Alone, the refused test passes. The symptom of a leak is a result that depends on which other tests ran (Lesson 8.2, Tests that depend on the test before them).

The Lesson Page's Own Quick Quiz

Lesson 8.2 · Testing the App's Logic
  1. B Requests are going to Expo's fetch, not Node's, so MSW never answers them: Every request got no answer, which is what happens when the global fetch is Expo's again: MSW never answers it. The two tests that expected no answer pass by accident. Check jest.environment.js, the testEnvironment setting and the useNodeFetch lines in jest.setup.ts.
  2. D MSW 3 is ES modules only, and Jest can load those only with Node's VM-modules feature on: MSW 3 is published only as ES modules. Jest runs the app's code as CommonJS, and it can load ES modules from node_modules only when Node's VM-modules feature is on. Running Jest's script through node with the flag works the same in every shell.
  3. A Make the stand-in answer like the real function: jest.mocked(notificationAsync).mockResolvedValue(): An automatic mock turns every function into an empty jest.fn that returns undefined. feel() calls .catch on what notificationAsync returns, so the stand-in must return a Promise like the real one: mockResolvedValue().
  4. C They are shoreline-api's code, kept identical; only React Native's global types disagree with them: The files are shoreline-api's own code, copied unchanged so the phone app's tests get the same rules and data as the real server, and so a new version can be copied over them. They are written for Node and browsers; only React Native's global types disagree. Excluding them, plus the typed require in server.ts, keeps them identical.
  5. A The test is about the sender, not SQLite: the logbook becomes a stand-in whose calls the test can still check: The logbook is SQLite, which needs a phone, and it is not what this test is about. The automatic mock makes saveSentLogs an empty function that records its calls, so the test can still check the sender handed it the saved log.

Exit Ticket

  1. The flag: MSW 3 ships only as ES modules; Jest (with Expo's Babel preset) runs CommonJS and can load ES modules from node_modules only with Node's VM-modules feature on. The flag lives in the test script, so npm test (with options after --), never npx jest.
  2. The stand-in first: jest.mock('expo-haptics') makes notificationAsync an empty jest.fn that returns undefined; .catch() on undefined throws. mockResolvedValue() makes it answer like the real function.
  3. What tests cannot prove: any of: that the real keychain, scheduler or motor answers the way the stand-in does; a permission prompt; a size limit; a platform quirk; how a buzz feels. A phone (and Lesson 8.3's end-to-end flow) catches those.

Common Wrong Answers and What They Reveal

  • Q2 A or B. Trusts the error message over the command they typed. Run both commands side by side.
  • Q3 B. Suspects the app when the setup changed. Ask: what changed since the last green run?
  • Q4 "remove the .catch()". Edits working app code to please a stand-in. Ask: does it work on your phone?
  • Q6 A or B. Picks a stand-in by habit. Show what an automatic mock does first: it loads the real module.
  • Q9 B. Expects randomness where there is a leak. Run Predict P1 for them.
  • Q11 A, C or D. Asserts on what moves. Tie it to makeEvent()'s fixed dates.
