8.4

Performance and Debugging

By the end you can
  • Open React Native DevTools with j, find the Expo CLI's dev tools menu, and say which tool answers which question on a phone and in the web preview
  • Explain why a component renders, measure renders with React DevTools' Profiler, and decide from numbers whether memoization is needed with the React Compiler on
  • Describe the JS thread and the UI thread, frames, release versus development builds, and the common causes of memory leaks in a React Native app
  • Measure what the app's bundle carries with npx expo export and Expo Atlas, and shrink it where the numbers say it pays
  • Debug with a method: reproduce, read the error, narrow it down, fix, and add a test that fails without the fix
Key ideas
  • The toolbox: j opens React Native DevTools for an app running Hermes (Expo Go, a development build): Console, Sources, Components, Profiler, Memory. Shift+M: the element inspector, the performance monitor, plugins (expo-sqlite, Expo Atlas). The web preview uses the browser's DevTools and the React Developer Tools extension.
  • Why a component renders: its state, its parent, a context, a subscription (TanStack Query, Zustand, useWindowDimensions). The React Compiler (on in Expo's template) remembers results for you: Shoreline Crew rendered about five times fewer components per keystroke with it. Memoize by hand only where a measurement says so.
  • Two threads, two frame rates: the JS thread (your components, hooks, handlers) and the UI thread (layout, drawing, scrolling, worklets); 16.7 ms per frame at 60 Hz. Count renders anywhere; judge speed in production mode (npx expo start --no-dev --minify, a build) on a real phone. Leaks: listeners without remove(), timers, big objects kept forever, full-size images.
  • The bundle is Hermes bytecode: 2238 modules and 5.9MB on Android before the lesson, mostly libraries. Expo Atlas shows each package's share. Shoreline Crew removed three unused packages (check with a search and npm ls) and Zod's 40 languages: 2084 modules, 5.5MB.
  • The debugging method: reproduce (a failing test is the best reproduction), read the error (the stack is a path through your imports), narrow it down (API, cache, the screen's logic), fix one thing, keep a test that fails without the fix.
  • Release stack traces point into bytecode: npx expo export --source-maps writes the map that translates them back (crash reporting, Lesson 9.3).

9.1

App Config and Environments

By the end you can
  • Explain what the app config controls, who reads it (Expo Go, prebuild, your build) and how to see exactly what Expo sees with npx expo config
  • Replace app.json with a typed app.config.ts and say what you gain and what tools can no longer do for you
  • Define development, preview and production variants with their own names and app ids, chosen by APP_VARIANT
  • Decide where each setting lives (EXPO_PUBLIC_ variables, the shell, .env.local, a build service's secrets) and keep secrets out of your code
  • Explain why release builds refuse plain http, what that means for shoreline-api, and what a real app does instead
  • Audit what a build asks the phone for: permission sentences, Face ID, push entitlement, notification icon and splash screen
Key ideas
  • The app config is the label on the app: name, version, icon, splash, scheme, ids, and the config plugins that write native settings. Expo Go uses only the public part; prebuild and your build use all of it. It runs in Node on your computer, never on the phone.
  • app.config.ts is a function that returns an ExpoConfig: typed (tsc catches a misspelled key that app.json would ignore), commented, able to read process.env (.env.local is loaded first). The price: npx expo install prints plugin entries for you to add instead of adding them.
  • Three variants, one setting: APP_VARIANT picks development (Shoreline Dev, .dev, the default), preview (Shoreline Preview, .preview) or production (Shoreline Crew). Different ids let all three sit on one phone; a misspelled variant stops every command with your own message.
  • Where settings live: EXPO_PUBLIC_API_URL is in the bundle (not a secret); APP_VARIANT in the shell or the build profile; the Maps key in .env.local or the build service's secrets, never in a committed file, and restricted because it ships in the app. A shell variable beats .env.local.
  • Plain http works in Expo Go and development builds; release builds refuse it (Android cleartext, iOS App Transport Security). Preview may allow it for your own Wi-Fi (expo-build-properties); production needs https, and the config refuses anything else.
  • What a build asks the phone for: permission sentences, no Face ID sentence, no push entitlement, a white notification icon, a dark splash. npx expo config --type introspect shows it today; Lesson 9.2's build shows it on a phone.
Worked example: one variable, three apps

One environment variable, three apps. With Lesson 9.1's app.config.ts, the same command gives different names and ids:

npx expo config --type public
APP_VARIANT=preview npx expo config --type public
name: 'Shoreline Dev',
usesCleartextTraffic: false
bundleIdentifier: 'com.example.shorelinecrew.dev'
package: 'com.example.shorelinecrew.dev',

name: 'Shoreline Preview',
usesCleartextTraffic: true
bundleIdentifier: 'com.example.shorelinecrew.preview'
package: 'com.example.shorelinecrew.preview',

And a mistake stops every Expo command at once, with the config's own message (the stack cut after its first line):

APP_VARIANT=prod npx expo config --type public
env: load .env.local
env: export EXPO_PUBLIC_API_URL
Error: Error reading Expo config at ~/shoreline/shoreline-crew/app.config.ts:

APP_VARIANT must be development, preview or production, not "prod".
Error: APP_VARIANT must be development, preview or production, not "prod".
    at Object.<anonymous> (~/shoreline/shoreline-crew/app.config.js:15:11)

Read the first Error: line: it is almost always enough. A misspelled KEY is different: Expo would ignore it, so npx tsc --noEmit is the check that names it (TS2561, "Did you mean to write 'bundleIdentifier'?").

Glossary for This Session

TermMeaning
React Native DevToolsThe debugger j opens for an app running Hermes: Console, Sources, Components, Profiler, Memory
performance monitorAn overlay on the phone (Shift+M) with the UI and JS frame rates
React CompilerRewrites components at build time so they reuse what they computed; on in Expo's template
JS thread / UI threadWhere your JavaScript runs / where native views are laid out, drawn and scrolled
Hermes bytecode (.hbc)The app's JavaScript compiled ahead of time: what npx expo export writes
Expo AtlasA bundle explorer: each package's share of the bundle, as a treemap
source mapThe file that translates a release build's stack trace back to your files
app configThe app's label: name, ids, icons, splash, scheme, plugins (app.json or app.config.ts)
public configThe part of the config that travels with the app (Expo Go, Constants.expoConfig)
app variant / APP_VARIANTOne of the three apps one project makes / the variable that picks it
bundle identifier / packageThe app id on iOS / on Android: a phone replaces an app with a build of the same id
cleartext traffic / App Transport SecurityPlain http, refused by Android release builds / iOS's https rule
introspectnpx expo config --type introspect: the native settings the plugins would write, in memory
