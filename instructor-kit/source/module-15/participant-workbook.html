Lessons

6.2

Camera and Photos

By the end you can
  • Take a photo with the phone's camera (after Lesson 6.1's permission step) and choose photos from the library (no permission), and read what the picker gives back
  • Keep photos small enough for one bar of signal: compression quality, no EXIF, JPEG instead of HEIC, and the API's limits checked before anything is sent
  • Keep a photo safe while it waits: the cache versus the app's documents, with expo-file-system's File, Directory and Paths, and a .web.ts stand-in for the web preview
  • Upload a photo from a phone to POST /api/photos and say why the old React Native FormData trick fails with SDK 58's fetch
  • Send photos offline first: queued with their log, uploaded before it, each id saved so a retry never uploads a photo twice, with a version bump for the saved queue
Key ideas
  • Two ways to a photo: launchCameraAsync (the camera: Lesson 6.1's permission step) and launchImageLibraryAsync (the library: no permission on current phones). Both answer { canceled, assets }; each asset has a uri (a file on the phone), mimeType, fileSize, width and height.
  • Photos for one bar of signal: quality: 0.6, exif: false, and on an iPhone the "compatible" JPEG instead of HEIC. shoreline-api takes JPEG, PNG or WebP of 5 MB or smaller (415 and 413 otherwise): check when a photo is ADDED.
  • Where a photo lives: the picker's file is in the cache, which the phone may empty; a photo that waits moves into the app's documents (expo-file-system's File, Directory, Paths) and is deleted once the server has it. The web preview gets photoFiles.web.ts.
  • Sending a photo: the photo itself as the body with its Content-Type (an expo-file-system File is a Blob). The old { uri, name, type } FormData part fails with SDK 58's fetch (TS2769; with a cast, "Unsupported FormDataPart implementation" inside fetch).
  • Photos in the dry bag: the queue carries { uri, type, photoId } per photo; the sender uploads photos without an id first, saves each id at once (setPhotoId), then sends the log with photoIds. A 413 or 415 makes the log refused, like a 403.
  • Saved data changes shape: persist's version and migrate give logs saved by version 0 an empty photo list, so they survive the update.
Worked example: the classic upload, and why it fails

The classic React Native upload from older answers, written into postPhoto: a FormData part made of the file's address. The type checker stops it:

// Don't: React Native's old FormData trick (a file address instead of a Blob)
const body = new FormData();
body.append('photo', { uri: photo.uri, name: 'photo.jpg', type: 'image/jpeg' });
await fetch(`${apiBaseUrl()}/api/photos`, { method: 'POST', body });
npx tsc --noEmit
src/api/client.ts:452:8 - error TS2769: No overload matches this call.
  Overload 1 of 3, '(name: string, value: string | Blob): void', gave the following error.
    Object literal may only specify known properties, and 'uri' does not exist in type 'Blob'.
  Overload 2 of 3, '(name: string, value: string): void', gave the following error.
    Argument of type '{ uri: string; name: string; type: string; }' is not assignable to parameter of type 'string'.
  Overload 3 of 3, '(name: string, blobValue: Blob, filename?: string | undefined): void', gave the following error.
    Object literal may only specify known properties, and 'uri' does not exist in type 'Blob'.

452   body.append('photo', { uri: photo.uri, name: 'photo.jpg', type: 'image/jpeg' });
           ~~~~~~

Read the overloads: append takes a string or a Blob, and the object is neither. Casting it away (as unknown as Blob) moves the error to the phone: SDK 58's fetch is Expo's own, and its code turns a FormData into bytes part by part. Run on such a form (Expo's own code, from node_modules), it says:

old way: Error: Unsupported FormDataPart implementation

Inside fetch, so the app reports "Could not reach the server" and the queue waits forever. The fix: send the photo itself as the body, with its kind in Content-Type (an expo-file-system File is a Blob).

6.3

Location and Maps

By the end you can
  • Read a phone's position as it really is: coordinates with an accuracy radius, a time, and a way to be faked, and pick the accuracy a feature needs
  • Design an on-the-day check-in: decide what proves a volunteer was there (the organizer's code, not the phone's location), and say honestly what happens offline
  • Build the check-in as a typed modal route with React Hook Form, a Zod schema and a mutation, and put the API's field message on the right field
  • Show a map with react-native-maps (a pin, a starting region, the blue dot only after a yes) and say what Expo Go, development builds and the web preview each need, including the Google Maps key for Android builds
  • Give the web preview a stand-in for a native-only library with a .web.tsx file, and hand a place to the phone's map app with a link
Key ideas
  • A position is a circle: coords.latitude, longitude and accuracy (the radius in meters), a timestamp, and mocked. The accuracy option (Lowest to BestForNavigation) trades time and battery for precision; under cliffs and between buildings circles of 50 to 500 m are normal.
  • What proves you were there: the organizer's code, checked by the server (on the day, a confirmed spot). The phone's position can be faked or far off and needs a yes to location: a hint, never a rule. Rules belong on the server.
  • Checking in with one bar: a TanStack Query mutation, not the saved queue (a late check-in can never work, a wrong code needs the volunteer now). Offline it pauses in memory and the screen says so. The API's check-in is idempotent.
  • The modal: faces before a form (guest, no confirmed spot, not today, checked in), a schema that keeps the code as text, the API's message for code on the field, and onSettled refreshing ['signups'] so the screen changes by itself.
  • Maps on a phone: react-native-maps' <MapView> with initialRegion (latitudeDelta 0.01 is about 1.1 km) and <Marker>; showsUserLocation makes an iPhone ask, so only after a yes. Expo Go needs no setup; your own Android build needs a Google Maps key (Module 9).
  • The web preview: react-native-maps stops the whole web build when imported: SiteMap.web.tsx stands in. Directions are the map app's job: mapLink per platform, opened with React Native's Linking.openURL (a new tab on the web).
Worked example: a native-only library and the web build

Lesson 6.3's map, imported where the web build sees it (the finished code with SiteMap.web.tsx removed). The web export stops:

npx expo export --platform web

λ Bundled 10857ms node_modules/expo/node_modules/@expo/cli/node_modules/@expo/router-server/node/render.js (1247 modules)
Web Bundled …ms node_modules/expo-router/entry.js (1235 modules)

Metro error: (0 , r(...).codegenNativeComponent) is not a function

  TypeError: (0 , r(...).codegenNativeComponent) is not a function

Read it as "a native component was defined where there is no native": react-native-maps defines native components when it is loaded, and react-native-web has no codegenNativeComponent. Expo Router's web build loads every route to render the pages on the server, so one import stops all of them. The fix is a file name: SiteMap.web.tsx next to SiteMap.tsx, with the same props, never importing react-native-maps.

Glossary

TermMeaning
image picker (expo-image-picker)Opens the phone's own camera or photo library and returns { canceled, assets }
assetOne photo from the picker: uri, mimeType, fileSize, width, height
EXIFData inside a photo (camera, time, often the place); exif: false leaves it out
HEICThe iPhone's photo format; shoreline-api refuses it (415)
cache / documentsThe app's two folders: the phone may empty the cache, it leaves documents alone
BlobRaw data with a type; an expo-file-system File is one, so fetch can send it as a body
raw body versus multipartThe API's two upload forms: the image itself with its Content-Type, or a form with a photo field
persist version / migrateA saved store's version number, and the function that updates data saved by an older version
position accuracyThe radius in meters of the circle a phone's position probably lies in
mock locationA position set by an app or tool instead of measured; mocked catches some
check-in codeThe organizer's four digits for the day; the API checks it
idempotent requestSending it again changes nothing: a second check-in leaves the sign-up attended, with the first time
region / latitudeDeltaWhere a map starts and how much fits on screen (0.01 of latitude is about 1.1 km)
markerA pin on the map (<Marker>), with a title and a description
Google Maps API keyNeeded by your own Android builds (not Expo Go); restricted to your app
.web.tsx stand-inA file the web bundle uses instead of the phone's version, with the same exports
geo: linkAndroid's link for a place, opened by the map app
