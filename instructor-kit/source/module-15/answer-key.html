6.2 · Camera and Photos: self-check

Q1
On his iPhone Theo answered "Don't Allow" to Shoreline Crew's camera question. Which photo feature still works for him, and why?
A) None: photos need the camera permission
B) Take a photo, once he presses Continue again
C) Choose photos: the photo library needs no permission, so a picture he took with the camera app can still go on the log
D) Only uploading photos he chose before
Why: launchImageLibraryAsync opens the system picker, which runs outside the app: no permission on current iPhones and Android phones. That is Lesson 6.1's "a no is an answer": Not now brings the buttons back, and Choose photos is the other way round. (Documentation-based: the course could not run a phone.)
A is wrong: Only the camera needs a yes.
B is wrong: On an iPhone one no is final: the blocked face, Open Settings.
D is wrong: Uploading needs no permission at all; and nothing was uploaded when chosen.
Q2
The classic React Native upload from older answers, written in postPhoto. npx tsc --noEmit prints this (the kit ran it). What is the fix?
src/api/client.ts:452:8 - error TS2769: No overload matches this call.
  Overload 1 of 3, '(name: string, value: string | Blob): void', gave the following error.
    Object literal may only specify known properties, and 'uri' does not exist in type 'Blob'.
  Overload 2 of 3, '(name: string, value: string): void', gave the following error.
    Argument of type '{ uri: string; name: string; type: string; }' is not assignable to parameter of type 'string'.
  Overload 3 of 3, '(name: string, blobValue: Blob, filename?: string | undefined): void', gave the following error.
    Object literal may only specify known properties, and 'uri' does not exist in type 'Blob'.

452   body.append('photo', { uri: photo.uri, name: 'photo.jpg', type: 'image/jpeg' });
           ~~~~~~
A) Silence it: as unknown as Blob
B) Send the photo itself as the body (an expo-file-system File is a Blob), with its kind in Content-Type
C) Install a FormData polyfill
D) Set Content-Type: multipart/form-data by hand
Why: Read the overloads: append takes a string or a Blob, and { uri, name, type } is neither. SDK 58's fetch is Expo's own (expo/fetch) and sends Blobs, not file addresses. postPhoto sends the API's second form: the image as the body, Content-Type: image/jpeg.
A is wrong: The error is right: with the cast, Expo's fetch fails at run time ("Unsupported FormDataPart implementation").
C is wrong: FormData exists; the part is the problem.
D is wrong: The body is still not bytes; and a hand-written multipart type has no boundary.
Q3
Someone adds the cast and ships the old FormData part. What happens on a phone when the queue sends the log?
A) The photo is uploaded as before
B) shoreline-api answers 415
C) tsc catches it at the next build
D) Expo's fetch throws "Unsupported FormDataPart implementation" inside itself: the client reports a NetworkError, and the queue counts a try and waits for a signal that is already there
Why: The kit ran Expo's own convertFormDataAsync (copied from node_modules/expo, as the lesson did): old way: Error: Unsupported FormDataPart implementation, while a Blob part converts. The error never reaches the server, so it looks like no signal. The lesson's advice: when only uploads "cannot reach the server", suspect the body.
A is wrong: Not with SDK 58's fetch: it only turns text and Blobs into bytes.
B is wrong: Nothing reaches the server.
C is wrong: The cast silences tsc for good.
Q4
The kit sent one real JPEG to POST /api/photos labeled image/heic, as an iPhone photo can arrive without the picker's "compatible" option. What did shoreline-api answer, and what does the queue do with the log?
A) 415 "Photos must be JPEG, PNG or WebP images.": refused with the server's words, never sent again by itself
B) 201: the API converts HEIC
C) 413: HEIC files are too big
D) 500: try again later
Why: A 415 (and a 413 for a 9 MB PNG: "Photos must be 5 MB or smaller.") will not change on the next try, so it lands in the sender's 4xx branch, like Lesson 5.5's 403. That is why LogPhotos checks the type and size when a photo is ADDED, while the volunteer can still choose another.
B is wrong: The API takes JPEG, PNG and WebP only.
C is wrong: The bytes were 28,955: size was not the problem.
D is wrong: Nothing went wrong on the server; the answer is final.
Q5
Two decisions in Lesson 6.2's queue: why does each photo move from the cache into the app's documents, and why is each photo's id saved with setPhotoId the moment it arrives?
The phone may empty the cache when storage runs low, and a log can wait for days: in documents its photos survive until the server has them (then forgetPhoto deletes them). Photos have no clientId: shoreline-api stores every upload as a new photo, so if the photos went up and the log's answer was lost, the next try must send the log with the saved ids instead of uploading again.
Why: The four questions of "For your own app": how big, where it waits, when it goes, what a retry may repeat. Lab 6.2 Task 2 has a test for the lost answer: two uploads in all, the item sent twice with the same ids.
Q6
Lesson 6.2 adds photos to every queued log. Theo updates the app with two logs saved yesterday, without a photos list. What keeps them?
A) Nothing is needed: merge keeps everything
B) version: 1 and a migrate that gives each version-0 log photos: [] before the check
C) Clearing AsyncStorage at startup
D) skipHydration: true
Why: persist saves a version number with the data and calls migrate when the saved version is older. Without it, Lesson 5.5's merge check (which now requires photos) throws yesterday's logs away. Lab 6.2's Task 3 fails exactly that way until migrate is there.
A is wrong: merge checks the shape: logs without photos fail it.
C is wrong: That throws the logs away on purpose.
D is wrong: That decides WHEN the queue is read back, not what survives.

Q7

A) 200, still attended, with the same checkedInAt: a retry is safe
B) 409: already checked in
C) 400: the code was used
D) 201 and a second sign-up
Why: The kit's run: Theo at e17 with 6544: 200, status attended, then Again: 200, status attended, same checkedInAt: true. The check-in is idempotent, which is why a paused mutation may simply be sent again when the phone is back online.
B is wrong: 409s are the wrong day and no confirmed spot.
C is wrong: The code is the day's, not single-use.

Q8
Why does Shoreline Crew NOT put check-ins in Lesson 5.5's saved queue?
A) A check-in is too big for AsyncStorage
B) The API has no clientId for check-ins
C) TanStack Query cannot pause a mutation
D) A late check-in can never work (only on the day), a wrong code needs the volunteer now, and the organizer needs to see it now
Why: Offline, the check-in is a paused mutation in memory with the honest line "No connection: your check-in is sent when you are back online. Keep Shoreline Crew open until then." If the app closes, the volunteer checks in again or the organizer marks them present in Shoreline Crew HQ. A debris log, by contrast, is welcome hours later.
A is wrong: It is four digits.
B is wrong: Idempotency comes from the API's rule (attended stays attended), not a clientId.
C is wrong: Pausing is exactly what it does offline (Lesson 5.2).

Q10
An organizer suggests: "Only allow check-in within 300 m of the meeting point." Under the cliff at Otter Creek, Theo's phone reports accuracy: 400. What is the problem?
A) None: 300 m is generous
B) The circle is 400 m wide, so the rule could refuse someone standing on the right spot; and a check on the phone can be changed by whoever holds it
C) accuracy 400 means the phone is 400 m from the pin
D) Accuracy.Highest always fixes it
Why: A position is a circle: accuracy is its radius in meters. Phones report 50 to 500 m under cliffs and in creek valleys, and mocked or edited positions exist. Rules belong on the server; the code is the proof, the location a hint (Exercise 3, Lab 6.3 Task 1).
A is wrong: Not when the circle is wider than the rule.
C is wrong: It is the uncertainty, not the distance.
D is wrong: More accuracy costs time and battery and still depends on the sky; it does not change who controls the phone.
Q11
What does npx expo export --platform web do when a route imports react-native-maps with no .web.tsx stand-in, why the WHOLE web build, and what is the fix?
It stops: "Metro error: (0 , r(...).codegenNativeComponent) is not a function". react-native-maps defines native components when it is loaded, and react-native-web has no codegenNativeComponent. Expo Router's web build loads every route to render the pages on the server, so one import stops all of them. Fix: SiteMap.web.tsx next to SiteMap.tsx, same props, never importing react-native-maps.
Why: The kit removed SiteMap.web.tsx from the finished code and ran the export: the lesson's card, line for line (the bundle sizes aside). Lab 6.3's web check shows the same message for a plain app.
Q12

Why: Measured in the lesson. On a phone both hand the link to the system: maps.apple.com on an iPhone, a geo: link on Android (documentation-based). Platform.select in mapLink picks the link.
A is wrong: It opens them: in the same tab.
B is wrong: The link itself names the map.

  1. B Take a photo, which opens the camera: The camera needs the camera permission, so Take a photo goes through usePermission and PermissionGate. The library picker needs no permission on current phones, and uploading or showing your own files needs none either.

  3.   4. Lesson 6.3 · Location and Maps
  1. B The server checks the code; a position comes from the phone, can be faked or far off, and needs a yes to location: The server checks the code, and the app cannot change its answer.
