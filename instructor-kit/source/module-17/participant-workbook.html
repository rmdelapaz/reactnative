Items A15 to A17: two or three sentences (and a line of code where it helps), 2 points each: a reason is worth more than a keyword. 14 or more of 20 points (70 %) meets the Part 2 assessment.

A1

A) When the volunteer presses the back arrow in the header
B) When the screen was opened straight from its address (or a link from outside): it is the only screen in the stack, so there is nothing to go back to
C) Whenever the API answers 404 for the id

A2
Moving the Cleanups screen into the tab group, a learner copies src/app/index.tsx to src/app/(tabs)/index.tsx and forgets to delete the original. What does the app show? (1 point)
A) Metro stops with an error: two routes claim the address /
B) The tab bar, with the Cleanups tab listed twice
C) The root file wins: the Cleanups screen opens with no tab bar at all and a header titled index, and Metro prints no warning
D) npx tsc --noEmit reports a duplicate route
A3
Shoreline Crew's sign-in modal calls router.back() and only then setSession(session) when the API says yes. Why that order? (1 point)
A) The moment the session is set, Stack.Protected takes the sign-in screen away; if it were still open, Expo Router would send the volunteer to the first tab instead of back to the screen that opened sign-in
B) setSession throws while a modal is open
C) router.back() is what saves the token in SecureStore
D) The order does not matter: it is a style choice
A4
With unstable_settings = { anchor: '(tabs)' } in the root layout, the not-found screen still uses Lesson 4.1's <Link href="/" replace asChild>. A volunteer opens a mistyped address and presses Back to the cleanups. What happens? (1 point)
A) Metro prints an error about the anchor
B) The app closes, because nothing is left in the stack
C) The Cleanups list appears with one tab bar, exactly as intended
D) The list looks right, but the page now holds two tab bars: a copy of the tabs replaced the not-found screen on top of the tabs the anchor put underneath. dismissTo closes screens back to the existing tabs instead
A5
The school's Wi-Fi keeps devices apart, so you start Metro with npx expo start --tunnel. Expo Go now loads Shoreline Crew on your phone, but the Cleanups list says it could not reach the server. Why? (1 point)
A) The tunnel accepts only https addresses, and the API uses http
B) --tunnel switches off every EXPO_PUBLIC_ variable
C) The tunnel carries only Metro's traffic: the app's requests still go to EXPO_PUBLIC_API_URL, an address the phone cannot reach, and shoreline-api has no tunnel
D) shoreline-api must be restarted with --tunnel as well
A6
Theo spends ten minutes on the Cleanups tab, then switches back to My cleanups. In a version WITHOUT useRefreshOnFocus('signups'), what happens to his sign-ups list? (1 point)
A) Nothing asks the API: the tab stayed mounted, and neither the app's focus nor the network changed, so the list shows what was fetched ten minutes ago
B) It is fetched again, because the screen mounts again
C) Query fetches it again, because the window gained focus
D) The list is empty until he pulls to refresh
A7
The settings saved on a phone are {"theme":"sepia"} (written by an older version, or by a bug). Shoreline Crew starts. What happens? (1 point)
A) TypeScript rejects the saved value before the app starts
B) useTheme meets an unknown theme and the app shows a red error screen
C) The app clears everything in AsyncStorage
D) The settings store keeps a theme only if it is one of the three it knows, so it falls back to the default: the app opens with Phone setting chosen
A8
Why does the sign-in screen write const send = handleSubmit(submit) and onPress={() => send()} instead of the web course's habit, onPress={handleSubmit(submit)}? (1 point)
A) handleSubmit works only inside a <form>, which React Native has only on the web
B) handleSubmit(submit) returns a function typed to take a web form event; a press event and the return key's submit event are different types, so tsc rejects it. Called with no event at all, it type-checks
C) onPress cannot take a function that another function returned
D) Calling handleSubmit while rendering sends the form twice
A9
Shoreline Crew saves debris logs in a persisted queue that survives the app, but leaves sign-ups as Lesson 5.2's mutations, which wait in memory. Why? (1 point)
A) A sign-up is decided by the server (a spot or the waiting list), so the volunteer needs the answer now; the queue is for things a person creates (a log, a note, a photo)
B) Sign-ups are too big for AsyncStorage
C) Zustand can persist only one kind of item
D) Sign-ups never fail when the phone is offline
A10
Lesson 6.1's app.json entry for expo-location sets locationAlwaysAndWhenInUsePermission, locationAlwaysPermission, motionUsagePermission and locationFullAccuracyPermission to false. Why? (1 point)
A) To turn location off in the web preview
B) So that Expo Go skips the location question
C) expo-location's plugin runs even when it is not listed, with default words for every string; false removes what Shoreline Crew never uses (Always location, motion, temporary precise location), so the app asks only for what it uses
D) Without them, npx expo install expo-location fails
A11
Shoreline Crew's picker options include preferredAssetRepresentationMode: Compatible. What is it for? (1 point)
A) It asks for the photo-library permission before the picker opens
B) iPhones save photos as HEIC; this option asks iOS for its most compatible version, a JPEG, because shoreline-api answers HEIC with 415 Photos must be JPEG, PNG or WebP images
C) It makes Android photos smaller
D) It removes the location data (EXIF) from the photo

A) It shows You are checked in at once
B) It shows an error, because the answer carries no new data

When a volunteer taps a reminder, useReminderTaps reads url from the notification's content.data. Why does it pass the value through isCleanupPath() before router.push? (1 point)

A16
This is the debris-log form after Lesson 5.5. Why is clientId made once, when the form opens, and not inside send (for example toNewLog(data, randomUUID(), new Date()))? And what does shoreline-api do when the same log arrives twice? (2 points)
shoreline-crew/src/app/log/[id].tsx
function DebrisLogForm({ event, viewer }: { event: CleanupEvent; viewer: string }) {
  // One id per log, made on the phone the moment the form opens: if the same log is sent twice
  // (a retry after a lost answer), the API recognizes it and keeps one
  const [clientId] = useState(() => randomUUID());
  ...
  // Checked by the schema first; the time is when Send was pressed, not when the form opened.
  // The log goes into the queue (saved on the phone at once), and the queue sends it if it can.
  const send = handleSubmit((data) => {
    const log = toNewLog(data, clientId, new Date());
    addLog(viewer, { event, log });
    setHandedOver(log);
    void sendWaitingLogs(viewer);
  });
A17
Read permissionStep (Lesson 6.1). On an Android phone, Maya answered no to the location question once, and the Hook reads { status: 'denied', granted: false, canAskAgain: true }. Which step does the function return, and what does the panel offer her? After a second no, canAskAgain is false: which step then, and what can the panel offer? (2 points)
shoreline-crew/src/hooks/usePermission.ts
export function permissionStep(response: PermissionResponse | null): PermissionStep {
  if (response === null) {
    return 'checking';
  }
  if (response.granted) {
    return 'granted';
  }
  if (response.status === 'undetermined') {
    return 'not-asked';
  }
  // The web preview's answers always say canAskAgain: true, but a browser never asks again after
  // a "Block": treat a no there as blocked
  if (!response.canAskAgain || Platform.OS === 'web') {
    return 'blocked';
  }
  return 'denied';
}
