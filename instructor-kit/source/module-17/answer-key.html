A15
A teammate says: "My cleanups shows guests a sign-in face, so GET /api/me/signups does not need to check the token." In two or three sentences: why is that wrong, and what does Shoreline Crew do when the API answers 401 to a request that carried a token? (2 points)
A screen's guard or guest face only hides screens: anyone can call the API without the app (curl, an old version, another program), so the API must check the token on every request, and it does (401). When a request that carried a token gets a 401, the client clears the session (setSession(null)), and the query and mutation caches' onError marks the sign-in as ended, so the app shows "Your sign-in has ended. Sign in again." and its guest face.
Marking (2 points: 2 / 1 / 0): 1 point: the API can be reached without the screen, so hiding is not protection ("the guard hides screens; the API protects data"). 1 point: the 401 path: the session is cleared (the client's rule) and/or the sign-in-ended message through the caches' onError, back to the guest face. "The API is secure anyway" without a reason: 0 for the first point.
Source: Lesson 4.3 (the guard and the 401 rule) and Lesson 5.2 (one place for 401: the caches' onError).
A16
This is the debris-log form after Lesson 5.5. Why is clientId made once, when the form opens, and not inside send (for example toNewLog(data, randomUUID(), new Date()))? And what does shoreline-api do when the same log arrives twice? (2 points)
shoreline-crew/src/app/log/[id].tsx
function DebrisLogForm({ event, viewer }: { event: CleanupEvent; viewer: string }) {
  // One id per log, made on the phone the moment the form opens: if the same log is sent twice
  // (a retry after a lost answer), the API recognizes it and keeps one
  const [clientId] = useState(() => randomUUID());
  ...
  // Checked by the schema first; the time is when Send was pressed, not when the form opened.
  // The log goes into the queue (saved on the phone at once), and the queue sends it if it can.
  const send = handleSubmit((data) => {
    const log = toNewLog(data, clientId, new Date());
    addLog(viewer, { event, log });
    setHandedOver(log);
    void sendWaitingLogs(viewer);
  });
On a bad connection the first send can reach the server while its answer is lost, so the queue (or the volunteer) sends the log again. Made once per log, the clientId is the same on every try. shoreline-api recognizes it: the first send answers 201 with the saved log, a resend with the same clientId answers 200 with the log it already has, so there is exactly one log. An id made inside send would be new on every try: two logs, and the bottles counted twice.
Marking (2 points: 2 / 1 / 0): 1 point: the reason: a retry after a lost answer must carry the same id (the phone cannot know whether the first try arrived). 1 point: the API's behavior: 201 the first time, 200 with the saved log for the same clientId, never a duplicate ("it recognizes it and keeps one" is enough).
Source: Lesson 5.4 made the id once per log; Lesson 5.5's queue saves it with the log, which is what makes every retry safe.
A17
Read permissionStep (Lesson 6.1). On an Android phone, Maya answered no to the location question once, and the Hook reads { status: 'denied', granted: false, canAskAgain: true }. Which step does the function return, and what does the panel offer her? After a second no, canAskAgain is false: which step then, and what can the panel offer? (2 points)
shoreline-crew/src/hooks/usePermission.ts
export function permissionStep(response: PermissionResponse | null): PermissionStep {
  if (response === null) {
    return 'checking';
  }
  if (response.granted) {
    return 'granted';
  }
  if (response.status === 'undetermined') {
    return 'not-asked';
  }
  // The web preview's answers always say canAskAgain: true, but a browser never asks again after
  // a "Block": treat a no there as blocked
  if (!response.canAskAgain || Platform.OS === 'web') {
    return 'blocked';
  }
  return 'denied';
}
'denied' (not granted, not undetermined, the phone may still ask, and it is not the web): the panel says that everything else works without it and offers Ask me again (Android allows one more question). After the second no: 'blocked': the phone will not ask again, so asking is useless; the panel says so and offers Open Settings (Linking.openSettings()), and the answer is read again when she comes back to the app.
Marking (2 points: 2 / 1 / 0): 1 point: 'denied' with a way to ask again (and the app still usable). 1 point: 'blocked' with Open Settings, not another request. Naming only the steps, without what the panel offers: 1 point in all.
Source: Lesson 6.1's five rules: a no is an answer, and say when only Settings can help.

C is wrong: Photos go with the log, when the queue sends it.
D is wrong: Nothing writes to the browser's downloads.
Q11
tsc prints this for an older reminder example. What does trigger need in expo-notifications 58?
src/notifications/reminders.ts:120:9 - error TS2322: Type 'Date' is not assignable to type 'NotificationTriggerInput'.

Q12
When does Shoreline Crew use React Native's Share.share, and when expo-sharing's shareAsync? Why not pass a link to shareAsync?
Share.share for words and links (the cleanup's link, Lesson 4.4); shareAsync for one local file (the logbook CSV). shareAsync wants a local file address: given https://… it type-checks, but on Android it refuses ("Only local file URLs are supported")
Why: Lesson 6.5: React Native's Share takes a message and a title (no file on Android); expo-sharing shares one file from the app's own folders.

Common Wrong Answers and What They Reveal

  • A6 B or C (the screen mounts again, or the window focus refetches). Still thinks in web pages: Lesson 4.2's tabs stay mounted; Lesson 5.2's table of browser and phone signals.
