Session 23: Development Builds and EAS Build

Answers and reasoning for every Session 23 item: the warm-up, the self-check, the predict-then-check items, the lab reference outputs, the lesson page's own quiz and the exit ticket.

Session 23 12 self-check items Confidential

Warm-up: Lesson 9.1

  1. APP_VARIANT (development when it is not set): app.config.ts turns it into the name, the ids, the cleartext setting. Today each build profile in eas.json sets it.
  2. A dynamic config can pick values per variant and read the environment. The price: tools cannot write into it (npx expo install and plugins in 9.1; eas init and the project id today).
  3. A production config without an https:// EXPO_PUBLIC_API_URL. Release builds block plain http, and anyone on the same Wi-Fi could read it. Today the same guard stops a production build on your computer before anything is uploaded.

9.2 · Development Builds and EAS Build: self-check

Q1
Which of these can Shoreline Crew NOT get while it runs in Expo Go?
A) Fast Refresh when you save a screen
B) Its own name, icon and app id on the home screen
C) Data from shoreline-api on your computer
D) The developer menu with m
Why: Expo Go is one app that opens many projects and keeps its own label: it runs as host.exp.Exponent with Expo Go's name and icon. Your name, ids, permission sentences and notification icon need a build of your own (the lesson's "When Expo Go Is Not Enough" table).
A is wrong: Fast Refresh works in Expo Go and in a development build alike.
C is wrong: Expo Go loads data the same way your build does (Lesson 5.1's address).
D is wrong: Both Expo Go and a development build have the developer menu.
Q2
After npx expo install expo-dev-client, npx expo start prints these lines. What does the QR code open now, and what do you press until Shoreline Dev is installed?
› Scan the QR code above to open in a development build. (Learn more: https://expo.fyi/start)
› Metro: exp+shoreline-crew://?__expo_url=http%3A%2F%2F192.168.1.42%3A8081
› Using development build
› Press s │ switch to Expo Go
Your development build (Shoreline Dev), not Expo Go; press s to switch the QR code back to Expo Go
Why: With expo-dev-client installed, Metro offers the project to a development build through the new exp+shoreline-crew scheme. Until Step 8 nobody has one, so s switches to Expo Go, which works exactly as before (the kit's demo ran both banners: before the package › Using Expo Go, after it › Using development build).
Q3
Shoreline Dev is installed. Which change needs a NEW development build?
A) A new sentence on the Logbook screen
B) A new Zod rule in src/api/schemas.ts
C) npx expo install expo-camera to scan a check-in code
D) A new address in .env.local, then Metro restarted with --clear
Why: A package with native code must be compiled into the app; the old build has no native half for it and shows a red screen about a missing native module. Screens, schemas and the EXPO_PUBLIC_ values Metro inlines travel from Metro (the lesson's Exercise 1; Lab 9.2 Task 3 writes the rule as code).
A is wrong: JavaScript: Fast Refresh shows it.
B is wrong: JavaScript: Metro sends it.
D is wrong: A development build reads the inlined value from Metro; a PREVIEW build would need a new build.
Q4
npm test -- --watchAll=false app.config prints this. What fixes it?
● builds Shoreline Preview from the preview profile, with an API address
  APP_VARIANT must be development, preview or production, not "prevue".
A) Change "prevue" back to "preview" in the preview profile's env in eas.json
B) Add prevue to the variants in app.config.ts
C) Set APP_VARIANT=preview in .env.local
D) Delete app.config.test.ts: EAS checks eas.json anyway
Why: The message is Lesson 9.1's own guard, reached through the preview profile's env. EAS's own eas.json check would pass it (it cannot know your variants): that is why the test exists. Caught in a fraction of a second instead of minutes into a cloud build.
B is wrong: That would make a fourth app nobody planned.
C is wrong: A cloud build never reads .env.local, and the test removes it on purpose.
D is wrong: EAS checks keys and allowed values, not what your variants are called.
Q5
Read the config the way EAS does for the production profile. What is happening?
$ EXPO_NO_DOTENV=1 APP_VARIANT=production npx expo config --type public
Error: Error reading Expo config at <folder>/app.config.ts:
A production build needs an https:// EXPO_PUBLIC_API_URL, not "".
Error: A production build needs an https:// EXPO_PUBLIC_API_URL, not "".
A) The build server rejected the upload
B) Expo's servers are down
C) Your Expo account has no production plan
D) Lesson 9.1's guard refused the config on your computer, so no build is used up
Why: EAS CLI evaluates app.config.ts on your computer with the profile's env and without .env.local (EXPO_NO_DOTENV=1). The production profile sets no address, so the guard stops it before anything is uploaded: by design, until Shoreline Crew has an https server (Lesson 9.4).
A is wrong: Nothing was uploaded: the config was read locally.
B is wrong: No server was contacted at all.
C is wrong: Production builds work on the free plan; the guard is your own code.
Q6
Name Shoreline Crew's three build profiles and what each one makes.
development: Shoreline Dev, a debug build with the dev client (internal); preview: Shoreline Preview, a release build with the JavaScript and the API address inside (internal); production: Shoreline Crew for the stores
Why: Each profile's env sets APP_VARIANT, and app.config.ts turns that one value into the name, the ids and the cleartext setting: eas.json is the packing list, app.config.ts the label.
Q7
Where should the Google Maps key for Android builds live?
A) In eas.json's preview env, committed with the code
B) In an EAS environment variable with sensitive visibility
C) In .env.local, which EAS uploads with the project
D) Hard-coded in app.config.ts
Why: npx eas-cli@latest env:set ... --visibility sensitive: hidden in build logs while EAS CLI can still read it when it evaluates the config. secret is for values only the build itself uses; a key that ends up inside the app is readable there anyway (Lesson 9.1).
A is wrong: eas.json is committed: fine for an address, not for a key.
C is wrong: .env.local is gitignored and never uploaded.
D is wrong: A key in a source file is in every copy of the repository.
Q8
npx eas-cli@latest init creates the project, warns about dynamic app configuration and stops with "Cannot automatically write to dynamic config at: app.config.ts". What now?
A) Rename app.config.ts to app.json
B) Run init again until it works
C) Paste the printed id and your username into easProject in app.config.ts, then run init once more
D) Delete the project on expo.dev and start over
Why: With a dynamic config EAS cannot edit your code, exactly like npx expo install and plugins in Lesson 9.1. The project exists; only the id is missing. With projectId and owner pasted, the second init reports the project as linked.
A is wrong: You would lose every variant Lesson 9.1 built.
B is wrong: It repeats the same message.
D is wrong: The project is fine: only your file is missing its id.
Q9
What does "distribution": "internal" give you for Android?
A) An APK that installs from a link, without a store
B) An App Bundle for Google Play
C) A build only the Android emulator can run
D) A build that needs a paid Google Play account
Why: Internal means installed directly, not from a store: EAS makes an APK (read in EAS CLI's source for the lesson). The phone asks to allow installing apps from the browser and may show a Play Protect warning: allow it for your own builds only.
B is wrong: The App Bundle is the store format (the production profile).
C is wrong: An APK installs on phones and emulators alike.
D is wrong: Android builds install free; the Play account is for publishing (Lesson 9.4).
Q10
Your first preview build fails on the free plan after six minutes. What is true?
A) Failed builds are free
B) The free plan stops you after one failure a day
C) Expo fixes and restarts it for you
D) It still counts against the month's builds: test the profiles on your computer first
Why: A build counts against the monthly limit whether it succeeds or fails. Read the first red line on the build's page, fix one thing, check it locally (the profile test, npx expo config, npx expo-doctor), then build again.
A is wrong: It counts.
B is wrong: There is a monthly limit, not a daily failure rule.
C is wrong: Nobody fixes your build for you: the log names the problem.
Q11
A teammate wants to build Shoreline Dev without the queue. What does npx expo run:android need on their computer, and does it need an Expo account?
Android Studio with its SDK and Java, several GB of disk, the emulator or a USB phone; no Expo account (only eas build --local needs a login)
Why: Local builds trade setup time and disk for queue time. run:android runs prebuild (creates the gitignored android/), compiles a debug build, installs it and starts Metro; eas build --local runs the cloud's steps on macOS or Linux and needs a login.
Q12
What does EXPO_NO_DOTENV=1 change in EXPO_NO_DOTENV=1 APP_VARIANT=preview npx expo config --type public?
A) It hides the config's secrets
B) Expo skips .env.local, so you see the config as a cloud build sees it
C) It deletes .env.local
D) It makes the output JSON
Why: EAS CLI evaluates the config with EXPO_NO_DOTENV=1 and the profile's env: .env.local never takes part. The kit ran the preview profile's variables this way: Shoreline Preview, the .preview id, cleartext on for Android, owner and projectId still undefined until Step 5.
A is wrong: Nothing is hidden: the public config is printed.
C is wrong: The file stays where it is.
D is wrong: The format comes from --type public/--json, not from this variable.

9.2 · Development Builds and EAS Build: predict, then check

P1
Predict, then run it.
npm test -- --watchAll=false app.config
● builds Shoreline Preview from the preview profile, with an API address
Matcher error: received value must be a string
Received has value: undefined
...
Tests:       1 failed, 2 passed, 3 total
Why: The preview test still builds Shoreline Preview (the name and id come from APP_VARIANT), and its third check fails: the profile has no address. Without the test, the build would succeed and the installed app would say EXPO_PUBLIC_API_URL is not set on every screen (Common Mistakes).
P2
Predict, then run it.
EXPO_NO_DOTENV=1 APP_VARIANT=preview EXPO_PUBLIC_API_URL=http://192.168.1.42:4000 npx expo config --type public
  name: 'Shoreline Preview',
  owner: undefined,
          usesCleartextTraffic: true
    bundleIdentifier: 'com.example.shorelinecrew.preview'
    package: 'com.example.shorelinecrew.preview',
      projectId: undefined
Why: Six lines of the real public config: the preview name and ids, cleartext on for this variant only (Android may reach plain http on your Wi-Fi), and owner and projectId undefined until Step 5 pastes them into easProject. env: load .env.local is missing from the output: EXPO_NO_DOTENV=1 skipped it, as EAS CLI does.

The Lesson Page's Own Quick Quiz

Lesson 9.2 · Development Builds and EAS Build
  1. B Fast Refresh shows the new text, as it did in Expo Go: A development build loads JavaScript from Metro, like Expo Go, so Fast Refresh shows the change. Only native changes, such as a new native package or a config plugin setting, need a new build.
  2. D The address was in .env.local only, which a cloud build never sees: .env.local is gitignored, so it is not uploaded, and EAS CLI does not load it either. A build with its JavaScript inside gets EXPO_PUBLIC_API_URL only from the profile env or an EAS environment variable. Add it to the preview profile and build again; the profile test catches this before a build.
  3. A The preview profile sets APP_VARIANT in its env, and app.config.ts picks the name and ids from it: eas.json is the packing list and app.config.ts the label: the preview profile sets APP_VARIANT, and app.config.ts turns that one value into the name, the ids and the cleartext setting.
  4. C Install the Android builds in the Android emulator on their computer, and keep using Expo Go on the iPhone: Builds for real iPhones need the Apple Developer Program, and simulator builds need a Mac. The Android emulator runs on Windows, macOS and Linux, so the classmate can install the Android builds there and keep using Expo Go on the iPhone for JavaScript work. Paying is never required for the course.
  5. B Make a new development build, which compiles the new native code in: The installed build was compiled before the library existed in the project, so it has no native half for it. A new development build (cloud or local) includes it. JavaScript-only changes never need this.

Exit Ticket

  1. A native package: a new development build; the installed one has no native half for it (a red screen about a missing native module). JavaScript-only changes never need one.
  2. Variables: the profile's env in eas.json and EAS environment variables (the profile's env wins when both set a name); never .env.local (gitignored, and EAS CLI does not load it).
  3. A real iPhone: the paid Apple Developer Program (Expo's docs name $99 a year): an ad hoc build for registered iPhones, or TestFlight (Lesson 9.4). Not required for the course; Android builds and the emulator are free.

Common Wrong Answers and What They Reveal

  • Q1 A or D. Thinks a development build loses Expo Go's conveniences. Show the table row "Developer menu, Fast Refresh: yes, yes, no".
  • Q3 D. Mixes up the development build (Metro inlines the value) with a preview build (baked in). Exercise 1's fourth change.
  • Q4 C. Still expects .env.local to reach a build. Ask which files the build server gets.
  • Q5 A or C. Reads every error as Expo's. Point at <folder>/app.config.ts: the guard is their own code, running on their computer.
  • Q9 B. Mixes up internal distribution with the store format; the production profile makes the App Bundle.
  • Q10 A. Treats failed builds as free; plan on testing profiles first.
