10.1 · Final Project: self-check

Q1
Lab 10.1: the kayak shop added 'cancelled' to RentalStatus, and npx tsc --noEmit says this. What is it telling you?
src/rentals/labels.ts:11:14 - error TS2741: Property 'cancelled' is missing in type '{ booked: string; out: string; returned: string; }' but required in type 'Record<RentalStatus, string>'.
src/rentals/labels.ts:18:14 - error TS2741: Property 'cancelled' is missing in type '{ booked: "out"[]; out: "returned"[]; returned: never[]; }' but required in type 'Record<RentalStatus, readonly RentalStatus[]>'.
Found 2 errors in the same file, starting at: src/rentals/labels.ts:11
A) RentalStatus must become an enum
B) Two Record tables keyed by RentalStatus have no entry for cancelled: each is a decision to make (its words, its moves)
C) labels.ts has a syntax error on line 10
D) Remove 'cancelled' from the union until the screens exist
Why: A Record keyed by a union must list every value, so a new status turns into a to-do list: its label, and which moves lead to it and from it. An array of statuses would have stayed silent (Lesson 10.1, Common Mistakes: adding a status without its tables).
A is wrong: An enum changes nothing: the tables still need the entry.
C is wrong: Each error is TS2741, a missing property: the file parses fine.
D is wrong: The status is the client's decision; hiding it postpones the same two decisions.
Q2
Which of Saltwick Kayak Hire's rules can only the server (the mock API) check?
A) The customer's first name is not empty
B) The return time is after the start
C) The kayak is not already booked for part of that time
D) The status is one of the four words
Why: Only the server sees every booking from every phone; it answers 409 with the message under the field. Field rules belong in the form's schema AND the API's body check, but the form can check them alone (the starter's duplicate-name rule is the same kind as the overlap).
A is wrong: A form schema checks that on the phone (and the API checks it again).
B is wrong: Also a field rule: the form can check it.
D is wrong: A type guard checks that anywhere; no other bookings are needed.

Q4
Milestone 1 is done. What does Milestone 2, the walking skeleton, ask for?
A) Every screen in the worksheet exists and is reachable, the main list and detail show the (mock) data, and the example Item is deleted
B) The device features and their permission paths
C) The accessibility pass and screen tests
D) A store build on Google Play internal testing
Why: The thinnest whole app, ugly but real, before any polish: it shows the problems that appear only when the pieces meet (a navigation shape that does not fit the brief) while they are cheap. Device features come after the main journey, on purpose.
B is wrong: That is Milestone 4: a camera button on a screen that saves nothing proves nothing.
C is wrong: That is Milestone 5.
D is wrong: Never required: store testing is only one optional route to "strong" in row 10.
Q5
A learner has an Android phone, no Apple or Google developer account, and a brief whose main journey uses the camera. Which launch meets rubric row 10?
A) Screenshots of the web preview
B) None until they pay for Google Play
C) Only TestFlight counts as shipped
D) A free EAS internal-distribution preview build on testers' phones (or a recorded demo in Expo Go on a real phone), with a README and a peer review given and received
Why: "Nothing in this rubric needs money": a preview build from an internal distribution link (a free Expo account; Android installs from the link) or a recording on a real phone is a full launch. The web preview is a launch only for an app without device features.
A is wrong: A camera journey cannot be shown in the web preview.
B is wrong: No row needs a paid account.
C is wrong: TestFlight needs the paid Apple membership and is optional.
Q6
With EXPO_PUBLIC_API_URL=demo, where does the starter's data live?
A) In each phone's memory, in the mock API: two phones never see each other's changes, and it starts again when the app restarts
B) In shoreline-api on your computer
C) In AsyncStorage, kept between restarts
D) On Expo's servers
Why: client.ts calls handle() inside the app after a short pause; no server, no Wi-Fi. The first screen says so ("Demo data: changes are kept until the app restarts."). Honest for a demo and for testers, not a back end: the production guard refuses it.
B is wrong: That is Shoreline Crew's setup; the starter needs no server.
C is wrong: Nothing is stored: a restart brings the sample data back.
D is wrong: Expo never sees your app's data.

10.2 · Working on Real Mobile Projects: self-check

Q7
The check-in photo, estimated in parts: 5.5, 10 and 19 hours (the lesson's example numbers). The three-point formula gives this. What do you tell the client?
node -e "console.log((5.5 + 4 * 10 + 19) / 6)"
10.75
A) About two working days for the app, possibly three, once the server can accept the photo; the server part is not included and the store privacy answers change first
B) 10.75 hours
C) Two hours: it is one button
D) It cannot be estimated until it is finished
Why: A range, the assumptions and what you depend on (Lesson 10.2, Estimating Mobile Work). The formula's number is for you; the gap between optimistic and pessimistic is what you discuss.
B is wrong: A single number with two decimals sounds certain and hides the dependency on the server.
C is wrong: The happy path only: the server, permissions, two platforms, tests and privacy are where the time goes.
D is wrong: A spike of an hour or two, then a range, is the professional answer.
Q8
A teammate ran npm install react-native-gesture-handler@latest; the check says this. The same command runs in CI after npm ci. What happens there?
env: load .env.local
env: export EXPO_PUBLIC_API_URL
The following packages should be updated for best compatibility with the installed expo version:
  react-native-gesture-handler@3.5.0 - expected version: ~3.3.0
Your project may not work correctly until you install the expected versions of the packages.
✔ Fix dependencies? … no
Found outdated dependencies
A) It waits for someone to answer the question
B) It fixes the package and passes
C) It passes with a warning
D) It prints the mismatch and exits with code 1: the pull request turns red and names the package
Why: In CI there is nobody to answer "Fix dependencies?": with CI set, npx expo install --check asks nothing, prints the mismatch and "Found outdated dependencies" and exits 1 (measured in Lesson 10.2, Exercise 3). The repair is npx expo install --fix, committed.
A is wrong: With CI set the prompt is skipped.
B is wrong: Only --fix (or answering Y) changes anything.
C is wrong: A mismatch is an error exit, which is the point of putting it in CI.
Q9
npm outdated in shoreline-crew lists TypeScript 7.0.2 as Latest. What is the right reading?
Package                                    Current  Wanted   Latest  Location                                                Depended by
typescript                                   6.0.3   6.0.3    7.0.2  node_modules/typescript                                 shoreline-crew
A) Update it now: Latest has the most fixes
B) npm outdated is broken for TypeScript
C) Leave it: SDK 58 pins TypeScript 6.0 (7.0 breaks npx expo lint, Lesson 1.3); "Latest" does not know about Expo, so wait until an SDK moves
D) Remove TypeScript and use JavaScript
Why: Expo tests each SDK with specific versions; "what npx expo install picks" is the right version for an Expo package. For plain JavaScript packages Expo does not know (Zod, TanStack Query), npm outdated is the right guide: release notes, a branch, CI.
A is wrong: The newest is not the one the SDK was tested with.
B is wrong: It reports npm's facts correctly; it simply does not know Expo's.
D is wrong: Never the answer to a version table.
Q10
Which step of the platform ladder is Shoreline Crew on?
A) Expo Go only, forever
B) Committed native folders, edited by hand
C) Continuous Native Generation: android/ and ios/ are generated from app.config.ts and plugins (by EAS Build), never edited or committed
D) Ejected
Why: You never committed native folders; EAS Build generated them from your config each time. That is the step most teams should stay on; committed native folders are a choice with a lasting cost (every SDK upgrade merged by hand).
A is wrong: Lesson 9.2 made development and preview builds.
B is wrong: There is no android/ or ios/ folder in the repository.
D is wrong: "Eject" is the old word for committing native folders once and maintaining them by hand.
Q11
The release train's cut-off was yesterday. Today a fix that changes a permission sentence in app.config.ts is merged. When can it reach users?
A) Tonight, as an EAS Update
B) On the next train: a permission sentence is native config, so it needs a new build, review and rollout
C) Right away, by editing the store listing
D) Only after the next Expo SDK
Why: Updates carry JavaScript and assets to the same runtime version; anything native (a package, a config plugin, a permission, app.config.ts) waits for a build. Ask the pull request template's question before promising a time: native change or not?
A is wrong: An update cannot change native configuration.
C is wrong: The listing is not the app.
D is wrong: SDK upgrades have nothing to do with it.
Q12
Your decision record docs/decisions/001-expo-go-or-dev-build.md has a "Revisit when" line. Why is it the most important line?
It turns the decision into a condition you check (for example "when we add a native package Expo Go does not include"), so the decision is reopened when the facts change instead of being defended or forgotten.
Why: Lesson 10.2, Step 4: decision records tell the next person (often you, a year later) why; the revisit condition says when the why stops holding.

Exit Ticket

  1. Brief and no-signal behavior: a specific person and action ("a rider marks a stop delivered, and it is sent once later"). A feature list ("offline support") is a sign the charter needs another pass.
  2. The must-never-break rule: a rule the mock API keeps whatever a phone sends ("a delivery never skips a step and never changes once finished"), tested in src/mock-api/<resource>.test.ts, named so in the test.
  3. A range: two numbers and a dependency ("two to three days, once the camera permission path from Shoreline Crew is copied in").

Common Wrong Answers and What They Reveal

  • Q1 A or D. Sees the tables as boilerplate rather than decisions. Rerun the demo's new-status step and read each error as a question for the client.
  • Q2 A or B. Mixes field rules (the form can check them) with rules that need every record. Ask: "what would the phone need to know to check it?"
  • Q5 A. Thinks the web preview is a launch for any app. Only for an app without device features.
  • Q7 B. Gives the formula's number to a client. The number is for you; the range and the dependency are for them.
  • Q9 A. Trusts npm's Latest for an Expo package. Show the SDK's version table (Lab 10.2 Task 2).
  • Q11 A. Thinks updates carry anything. A permission sentence is native configuration: a build.
