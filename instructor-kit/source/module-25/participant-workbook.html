10.1

Final Project

By the end you can
  • Choose a client brief (or size your own idea) by its people, must-haves, device features and data, and write a charter with a clear "out of scope"
  • Plan a phone app before coding it: types, screens, data, storage, offline behavior, permissions, privacy and the release, from your journal's notes
  • Set up the course's verified starter and explain what each of its parts does and which lesson it comes from
  • Build Milestone 1: your types next to the example, sample data, and the mock API's rules with a test for each one
  • Plan the rest of the project in milestones with honest hours, and pick a launch that needs no paid account
Key ideas
  • The kit (final-project-kit.zip): briefs.md (seven fictional clients and the size rules for an own idea), worksheet.md (17 sections, each fed by your journal's "For your own app" notes), rubric.md (10 rows, 0 / 1 / 2), peer-review.md (about 90 minutes, both ways) and starter/.
  • Every brief says who the people are and where, three to six must-haves, what the client already has (your sample data), what is out of scope, which device features are in scope and how the data is served (the brief's own mock API, or local-only).
  • The starter is an SDK 58 project made the way Lesson 1.2 made Shoreline Crew, with the course's conventions (theme, Screen, AppText, Button, the client and its errors, TanStack Query, React Hook Form + Zod, Jest + RNTL + MSW, three variants, eas.json, CI) and none of Shoreline Crew. Tabs, sign-in, storage, device features and motion come from your Shoreline Crew, pattern by pattern, when a milestone needs them.
  • The data source: EXPO_PUBLIC_API_URL=demo makes the app answer from its own mock API (src/mock-api, in memory, per phone, reset on restart, and the first screen says so). The tests use the same rules through MSW. A production build refuses demo data.
  • Milestone 1 = types first: your types next to Item, every union with Record tables, 6 to 12 sample records with one awkward one, every rule of the mock API with a test (the must-never-break rule named so), a green CI run. Then a walking skeleton (2), the main journey (3), phone features and offline (4), quality (5), ship (6), review (7): about 30 hours.
  • Done = no rubric row at "not yet", a peer review given and received, every point answered. Shipped = real people used it on real phones: a preview build from an internal link or a recording on a phone. Nothing in the rubric needs money.

10.2

Working on Real Mobile Projects

By the end you can
  • Estimate a mobile feature as a range, from a task breakdown that includes the work only phones add (two platforms, permissions, offline, builds, store review)
  • Choose between Expo Go, a development build, Continuous Native Generation and committed native folders, and explain when a local native module (Expo Modules API) is worth it
  • Work in a team with short branches, a phone-aware pull request template, CI and a release train that plans for store review
  • Keep an Expo app current: read npx expo install --check, npx expo-doctor and npm outdated, repair version drift with npx expo install --fix, and upgrade one SDK at a time
  • Write a learning plan for the months after the course, with your final project at its center
Key ideas
  • Estimates are ranges from a task breakdown. The work phones add: the happy path, the server, permissions, offline, two platforms, tests, privacy and the stores, shipping (update or build?). Three numbers per part; (optimistic + 4 × likely + pessimistic) ÷ 6; tell the client the range, the assumptions and what you depend on. Your time log is how your estimates improve.
  • Time that is not yours: build queues, store review (a rejection restarts the clock), a new Google Play account's closed test, other people. Plan it; check the stores' current pages before promising a date.
  • The platform ladder: Expo Go → development build → Continuous Native Generation (native folders generated from app.config.ts, never committed: where Shoreline Crew is) → committed native folders. A local native module (Expo Modules API, Swift and Kotlin) is a development-build feature.
  • Teams: short branches, a phone-aware pull request template (tested on which phones? native change or not? does it change what the app collects?), CI, kind and specific review, questions in four parts (goal, expected, actual word for word, tried). Release trains leave on time; JavaScript-only fixes can go out as updates between trains; native changes wait.
  • Keeping an app healthy: Expo releases several SDKs a year and Expo Go supports only the newest; the stores raise their rules every year. Health check: npx expo install --check, npx expo-doctor, npm outdated. "Latest" is not the right version for a native package; npx expo install --fix repairs drift. Upgrade at least yearly, one SDK at a time.
  • Dependency hygiene: fewer packages; native ones through npx expo install; read audits, never npm audit fix --force; commit the lockfile (CI uses npm ci); a calendar, not a mood.
