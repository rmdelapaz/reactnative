Start Here · Part 1 Refresher

Not graded. Each reason names the Part 1 lesson to reread.

R1
A card shows {title} straight inside a <View>. What happens on a phone?
A) It renders like a span
B) A red screen: text must be inside a Text
C) tsc reports it
D) The title is skipped silently
Why: Every piece of text sits in a <Text>; tsc allows any child in a View, so only running it shows the error. Lesson: Native components (2.1).
R2
styles.tagLine is used, but the StyleSheet defines tagline. Who tells you?
A) The phone, with a red screen
B) Metro, while bundling
C) npx tsc --noEmit (TS2551, Did you mean)
D) Nobody can
Why: Metro removes the types without checking them and the phone ignores an undefined style; StyleSheet.create is typed, so tsc names it. Lesson: StyleSheet (2.1).
R3
Three Views inside a View with no flex styles. How are they laid out?
A) In a column, top to bottom
B) In a row, left to right
C) On top of each other
D) In a wrapping grid
Why: React Native's flexDirection defaults to column (the web's is row). Lesson: Flexbox (2.2).
R4
Which prop makes a <Pressable> react to a finger?
A) onClick
B) onTouch
C) onTap
D) onPress
Why: onClick type-checks and does nothing on a Pressable: React Native's touch prop is onPress. Lesson: Touch (2.4).
R5
In a FlashList, an open "details" panel shows up on another card after scrolling. Why?
A) The keyExtractor is missing
B) Recycling: useState in a recycled item keeps its value; use useRecyclingState
C) FlashList cannot show state
D) The list needs key={columns}
Why: FlashList reuses item components; state tied to the old item comes along unless it is reset per item (useRecyclingState). Lesson: Lists (3.2).
R6
A screen under a header bar keeps the 'top' edge. What does a notched iPhone show?
A) Nothing different
B) The header hidden behind the notch
C) An empty band of about 50 points above the content
D) A red screen
Why: The header already covers the status bar; keeping 'top' adds its height again. The web preview has no insets, so it cannot show this. Lesson: Safe areas (2.3).

4.1 · File-Based Routing: self-check

Q1
Which address does a file src/app/cleanups/index.tsx get?
A) /cleanups
B) /cleanups/index
C) /index/cleanups
D) None: index files are layouts
Why: index means "this folder's own address", like index.html on the web: src/app/index.tsx is /, src/app/cleanups/index.tsx is /cleanups (Lesson 4.1, Files Are Screens).
B is wrong: The word index never appears in an address.
C is wrong: The folder comes first, as in the path.
D is wrong: Layouts are _layout.tsx; index is a screen.
Q2
npx tsc --noEmit prints this in shoreline-crew. Which change fixes it?
src/components/EventCard.tsx:76:23 - error TS2820: Type '"/cleanup/[id]"' is not assignable to type '"/" | … | "/cleanups/[id]"'. Did you mean '"/cleanups/[id]"'?
Found 1 error in src/components/EventCard.tsx:76
A) Rename src/app/cleanups to src/app/cleanup
B) Write '/cleanups/[id]' in EventCard.tsx's Link
C) Edit .expo/types/router.d.ts to add the address
D) Cast the href with as Href
Why: Typed routes list every address the app has; '/cleanup/[id]' is not one, and TypeScript even suggests the right one. The kit ran it: the output is the lesson's card, word for word.
A is wrong: The folder is right: every other link and the screen itself use /cleanups.
C is wrong: router.d.ts is generated by Metro; never edit it.
D is wrong: A cast hides the bug: the volunteer would land on the not-found screen.
Q3
A Link passes params: { id: 8 }. What does useLocalSearchParams give the screen for id?
A) The number 8
B) undefined: params must be strings
C) The string '8'
D) ['8'], an array
Why: Params come from the address, and an address is text: you may pass a number when you link, but the screen always receives a string (Lesson 4.1, Params and Typed Routes).
A is wrong: The address turns it into text.
B is wrong: Numbers are allowed as input; they arrive as strings.
D is wrong: An array only comes from a repeated value or a catch-all route.
Q4
Why does the not-found screen's button use <Link href="/" replace> instead of a plain Link?
A) A plain Link cannot go to /
B) replace loads the list faster
C) replace is required inside +not-found.tsx
D) So back does not return to the dead end
Why: replace puts the list in the dead end's place. The course measured it: without replace, the browser's back button went straight back to /cleanup/e08.
A is wrong: Any Link can go to /.
B is wrong: Speed is the same.
C is wrong: Expo Router requires nothing of the kind.
Q5
The cleanup's title is only known once the API has answered. Where do you set the header's title?
A) <Stack.Screen options={{ title: event.title }} /> inside the screen
B) In <Stack screenOptions> in the root layout
C) <Stack.Screen name="cleanups/[id]"> in the layout
D) With navigation.setOptions from useNavigation()
Why: The third level of screen options: rendered inside a screen, Stack.Screen draws nothing and updates that screen's options from data. The layout gives the starting title "Cleanup".
B is wrong: screenOptions apply to every screen and cannot see this screen's data.
C is wrong: Good for what is known in advance ("Cleanup"), not for loaded data.
D is wrong: The older React Navigation way; in an Expo Router app use Stack.Screen.
Q6
You stopped Metro, added a route file, and now tsc says a link to it is not assignable to "/" | RelativePathString | ExternalPathString | "/_sitemap". What do you do before changing any code?
Start npx expo start: Metro rewrites the route types (.expo/types/router.d.ts), then run npx tsc --noEmit again
Why: The list of addresses is generated by Metro and refreshed while it runs; a stopped Metro leaves stale types. Nothing is wrong with the code (Lesson 4.1, Common Mistakes).

4.2 · Tabs, Nesting and Modals: self-check

Q7
What is the address of src/app/(tabs)/logbook.tsx?
A) /(tabs)/logbook only
B) /logbook
C) /tabs/logbook
D) It has none: files in a group are tabs, not routes
Why: A folder in parentheses is a group: it shares a layout and adds nothing to the address. Typed routes accept both forms; the course writes the short one.
A is wrong: Accepted by typed routes, but the address a volunteer sees is /logbook.
C is wrong: There is no folder called tabs.
D is wrong: Each file in the group is a route with an address.
Q8
Metro prints this after a change to (tabs)/_layout.tsx, and npx tsc --noEmit prints nothing. What does a volunteer see?
λ  WARN  [Layout children]: No route named "my-cleanup" exists in nested children: [ 'index', 'logbook', 'my-cleanups', 'profile' ]
A) A red error screen
B) Nothing different: it is only a warning
C) A tab bar without the My cleanups tab
D) A header titled "(tabs)"
Why: The course measured it: the tab with the misspelled name vanishes from the bar. Screen names are plain strings, not typed routes, so tsc is silent; the kit ran tsc on the same change and it printed nothing. The warning lists the names that exist.
A is wrong: Navigation mistakes rarely stop the app.
B is wrong: The bar loses a tab.
D is wrong: That comes from a root layout that still names "index".
Q9
Before you go has presentation: 'modal'. How does the web preview show it?
A) As a card sliding up from the bottom
B) As a half-height sheet
C) In a separate browser window
D) As an ordinary screen with a back arrow
Why: The course measured it: the web preview draws a modal (and a sheet) like any other stack screen. The card that slides up is a phone thing, described from the documentation; Done works the same everywhere.
A is wrong: That is an iPhone, per the documentation.
B is wrong: That is formSheet on a phone.
C is wrong: No new window is ever opened.
Q10
The Cleanups list has no header and sits above the tab bar. Which edges does it keep clear of the phone's insets?
A) ['top', 'left', 'right']
B) ['left', 'right']
C) ['bottom', 'left', 'right']
D) All four, the default
Why: Leave out every edge a bar already covers: the tab bar covers the bottom (it adds the home indicator's inset itself), nothing covers the top (Lesson 4.2's edges table).
B is wrong: That is a tab screen WITH a header (My cleanups, Logbook, Profile).
C is wrong: That is a screen under a stack header: a cleanup, the modal, not found.
D is wrong: The bottom inset would be added twice: an empty strip above the tab bar.
Q11
A screen is opened from several tabs and from links sent in messages. Where does its file go?
A) Inside one tab's own stack
B) As a fifth tab
C) In the root stack, next to (tabs)
D) In src/components, rendered by each tab
Why: One address, one place: in the root stack it opens on top of the whole tab navigator, and a link from outside (Lesson 4.4) always opens the same screen. That is where Shoreline Crew's cleanup screen lives.
A is wrong: Then it belongs to one tab, and other tabs would need copies.
B is wrong: Tabs are places a volunteer returns to all the time, three to five of them.
D is wrong: Only route files in src/app have addresses.
Q12
Why does Before you go's done() check router.canGoBack() instead of always calling router.back()?
Opened from its address (a link, the address bar) nothing is underneath, so back cannot go anywhere: it uses router.replace('/') then
Why: The same pattern as 4.1's leave(). Lab 4.2 Task 3 shows it: the starter's Done, opened at /tide-safety, stays on /tide-safety.

The solution's site screen:

import { router, Stack, useLocalSearchParams } from 'expo-router';
import { Pressable, StyleSheet, Text, View } from 'react-native';

import { findSite } from '../../src/sites';

// One beach on a screen of its own: /sites/driftwood-cove shows the site with the id driftwood-cove.
// (Shoreline Crew names the route instead, useLocalSearchParams<'/cleanups/[id]'>(), because Metro writes
// its typed routes; a lab has no Metro running, so the params' shape is written out.)
export default function SiteScreen() {
  // The [id] part of the address: always a string, it comes from the address
  const { id } = useLocalSearchParams<{ id: string }>();
  const site = findSite(id);

  // Back where the volunteer came from; opened from a link, there may be nothing to go back to
  function leave() {
    if (router.canGoBack()) {
      router.back();
    } else {
      router.replace('/');
    }
  }

  if (!site) {
    return (
      <View style={styles.screen}>
        <Text>No beach site has the id {id}.</Text>
        <BackButton onPress={leave} />
      </View>
    );
  }

  return (
    <View style={styles.screen}>
      {/* Options for this screen, set from inside it: the header shows the site's name */}
      <Stack.Screen options={{ title: site.name }} />
      <Text>{site.town}</Text>
      <Text>{site.description}</Text>
      <Text>Parking: {site.parking}</Text>
    </View>
  );
}

The solution's root layout:

import { Stack } from 'expo-router';

// The root stack: the tabs are ONE screen of it (with their own headers), a site opens on top of them,
// and the tide safety card is presented as a modal
export default function RootLayout() {
  return (
    <Stack
      screenOptions={{
        // Left alone, a back button shows the previous screen's title, and under the tabs that is "(tabs)"
        headerBackTitle: 'Back',
      }}
    >
      <Stack.Screen name="(tabs)" options={{ headerShown: false }} />
      <Stack.Screen name="sites/[id]" options={{ title: 'Site' }} />
      <Stack.Screen name="tide-safety" options={{ presentation: 'modal', title: 'Tide safety' }} />
    </Stack>

The Lesson Pages' Own Quick Quizzes

Lesson 4.1 · File-Based Routing
  1. B cleanups/[id].tsx: The folder cleanups gives the first part of the address, and the square brackets match any one segment and name it id, so e11 arrives as the id param.
  2. C ['bottom', 'left', 'right']: The header covers the top, so the screen leaves top out; the bottom still meets the home indicator, and the sides matter in landscape. Keeping top would add the status bar height again under the header on a notched iPhone.
  3. A Start npx expo start so it rewrites the route types, then run tsc again: The route types in .expo/types/router.d.ts are written by Metro. Started again, it sees the new file and adds its route; tsc then passes without any change to the code.
  4. D The string 'e08': Params come from the address, so they are text; naming the route types id as a plain string. The screen then asks the API for that id, and handles a 404 if it names no cleanup.
  5. B router.replace('/'): the list takes the dead end's place: Nothing is underneath, so canGoBack() is false and router.replace puts the Cleanups screen in place of the dead end. Back will not return to it.
Lesson 4.2 · Tabs, Nesting and Modals
  1. C src/app/(tabs)/my-cleanups.tsx, at /my-cleanups: A folder in parentheses is a group: it lets the files share a layout, the tab bar, and adds nothing to the address.
  2. A The cleanup screen belongs to the root stack, which holds the whole tab navigator as one screen underneath it: The root stack holds the whole tab navigator as one screen. The cleanup is pushed onto that stack, on top of it, so the tab bar is covered until the volunteer goes back.
  3. D ['left', 'right']: The header covers the top and the tab bar covers the bottom, each with its own inset, so only the sides are left for the screen to keep clear.
  4. B headerBackTitle: 'Back' in the root stack's screenOptions: The label falls back to the route name of the screen underneath, the tab group. headerBackTitle in the root stack's screenOptions gives every back button plain words instead.
  5. A The safety briefing a volunteer reads before a cleanup and then closes: A modal is a short detour with a clear end: read or do one thing, then close it and be back where you were. The briefing fits; lists people come back to are tabs.

Exit Ticket

  1. The file and its param: src/app/cleanups/[id].tsx; { id: 'e08' }: a string, because it comes from the address, typed from the route's name.
  2. Nothing underneath: router.replace('/'): the list takes the dead end's place. The full pattern: router.canGoBack() ? router.back() : router.replace('/') (4.1's leave(), 4.2's done()).
  3. The tree: the root Stack containing (tabs) (a Tabs navigator: Cleanups, My cleanups, Logbook, Profile), cleanups/[id], before-you-go (presented as a modal) and +not-found. The tab bar shows only inside (tabs).

Common Wrong Answers and What They Reveal

  • Q1 B. Thinks in file names, not addresses. Show /_sitemap.
  • Q2 C or D. Treats generated types as something to edit or silence. Run the demo's step again and read the Did you mean.
  • Q3 A. Expects params to keep their type. An address is text.
  • Q8 B. Reads warnings as noise. Show the three-tab bar from the lesson.
  • Q10 B or C. Mixes up the three rows of the edges table: ask "which bars cover this screen?"
  • Q11 A. Thinks per tab. The cleanup must have one address for Lesson 4.4's links.
