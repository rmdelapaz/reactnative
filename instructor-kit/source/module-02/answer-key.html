1.3 · From the HQ to the Phone: self-check

Q1
Which piece of Shoreline Crew HQ is REWRITTEN for the phone, not copied?
A) The type guard isCleanupEvent
B) formatDate with Intl.DateTimeFormat
C) The session kept in sessionStorage
D) The ApiError class
Why: Code that only works with data copies over; code that touches the browser gets rewritten. A phone has no sessionStorage: the session goes to the device's keychain with SecureStore (Lesson 4.3).
A is wrong: A type guard checks unknown data: plain TypeScript, copied.
B is wrong: Intl is part of JavaScript and Hermes has it: copied.
D is wrong: The same API sends the same error bodies: copied.
Q2
This line, copied from a web app, sits in a shoreline-crew file. Does npx tsc --noEmit complain? What happens on a phone?
// The HQ's demo build asked the browser where the site runs:
export const origin = window.location.origin;
export const pageTitle = document.title;
tsc prints nothing (Expo's settings load the DOM types); on a phone it fails while the app runs (the lesson: a TypeError and the red screen)
Why: Expo's tsconfig includes "lib": ["DOM", "ESNext"] for the web preview, so browser APIs type-check. The kit ran it: tsc printed nothing. Search copied code for window, document, Storage and import.meta yourself.
Q3
npx tsc --showConfig in shoreline-crew prints this. Which entry explains why sessionStorage type-checks in phone code?
        "lib": [
            "dom",
            "esnext"
        ],
        "module": "preserve",
A) "dom" in lib
B) "esnext" in lib
C) "module": "preserve"
D) Nothing: it is a bug in TypeScript 6.0
Why: The DOM library is loaded so the same project also type-checks for the web preview, where window and sessionStorage are real. On a phone they are not.
B is wrong: ESNext is the language itself (Promise, Array methods), no browser APIs.
C is wrong: That leaves imports to the bundler (Metro).
D is wrong: It is a deliberate setting, the same in TypeScript 7.
Q4
You copy the HQ's whole client.ts and npx tsc --noEmit reports five errors. Which problem is NOT among them?
A) The missing ../utils/debris.ts
B) import.meta.env.VITE_API_URL
C) The session read and saved with sessionStorage
D) A parameter that implicitly has an any type
Why: TS2307 (debris.ts), two TS7006 that follow from it and two TS2339 (import.meta.env) are all tsc finds. The same file reads, saves and removes the session with sessionStorage and asks window.location for the page's address: tsc accepts every line (the kit's grep found them). Fixing only what tsc reports leaves a client that crashes on a phone.
A is wrong: TS2307, the first error.
B is wrong: TS2339, twice.
D is wrong: TS7006, twice: category has no type once debris.ts is missing.
Q5
The API is not running and the app's request gets no answer at all. What does Expo's fetch on a phone reject with?
A) A TypeError with "Failed to fetch", like a browser
B) A FetchError, a plain Error whose message starts with "fetch failed:"
C) An ApiError with status 503
D) Nothing: the promise never settles
Why: SDK 58 replaces the global fetch on phones with expo/fetch, which throws its own FetchError (node_modules/expo/src/winter/fetch). The HQ's instanceof TypeError branch never matches it, so the phone's request() wraps any failed fetch in a NetworkError (Lab 1.3 Task 2).
A is wrong: That is the browser's (and the web preview's) error.
C is wrong: No server answered, so there is no status at all.
D is wrong: It rejects; the screen then shows describeError's words.
Q6
Why does the phone's request() build the URL BEFORE the try around fetch?
A) So that a missing EXPO_PUBLIC_API_URL is not reported as "Could not reach the server"
B) Because fetch accepts only a string
C) TypeScript requires variables outside a try
D) So the request starts faster
Why: apiBaseUrl() throws a plain Error ("EXPO_PUBLIC_API_URL is not set") when the variable is missing. Outside the try it stays that error; inside, it would be wrapped as a NetworkError and blamed on the network.
B is wrong: fetch accepts a URL object too; that is not the reason.
C is wrong: No such rule.
D is wrong: It makes no difference to speed.
Q7
const { EXPO_PUBLIC_API_URL: url } = process.env; type-checks. npx expo lint prints this. What is the fix?
133:9  error  Unexpected destructuring. Cannot destructure url from process.env  expo/no-env-var-destructuring
A) Rename the variable to VITE_API_URL
B) Add // eslint-disable-next-line above it
C) Move the value into .env.example
D) Write process.env.EXPO_PUBLIC_API_URL in full, with a dot
Why: Metro copies the value into the bundle only where it finds the full text process.env.EXPO_PUBLIC_API_URL. The kit exported the app both ways: with destructuring the address is not in the bundle at all, and the app says "Something unexpected went wrong". Expo's linter rule catches it (the lesson says it lints cleanly; it does not).
A is wrong: VITE_ is Vite's prefix; Expo reads EXPO_PUBLIC_.
B is wrong: Silencing the rule leaves the address out of the app.
C is wrong: .env.example only documents the variable; .env.local is what Metro reads.
Q8
Which value is fine to keep in an EXPO_PUBLIC_ variable?
A) A paid map service's secret key
B) The shoreline-api's address
C) The database password
D) An organizer's sign-in token
Why: Every EXPO_PUBLIC_ value is copied into the app as plain text: anyone can unpack a downloaded app and read it. An address is public anyway; secrets stay on a server.
A is wrong: Secret keys belong on a server that uses them on the app's behalf.
C is wrong: Never in an app.
D is wrong: A token is per person and changes: SecureStore at run time (Lesson 4.3).
Q9
Pasted from the HQ, export const apiUrl = import.meta.env.VITE_API_URL; gives this. What is the phone's version?
src/vite-habit.ts:2:35 - error TS2339: Property 'env' does not exist on type 'ImportMeta'.
Found 1 error in src/vite-habit.ts:2
A) Add vite/client to the tsconfig's types
B) Put // @ts-ignore above the line
C) Rename the file to .mts
D) process.env.EXPO_PUBLIC_API_URL, from .env.local
Why: Expo has the same idea with other names: EXPO_PUBLIC_ variables in .env files, read as process.env.EXPO_PUBLIC_…. This one tsc does catch (TS2339), unlike the DOM APIs.
A is wrong: There is no Vite in an Expo project.
B is wrong: The line would still read nothing on a phone.
C is wrong: The file type is not the problem.
Q10
Right after copying the API's types.ts, npx expo lint prints four array-type warnings in it. What is the right move?
A) npx expo lint --fix
B) Add src/api/types.ts to the ignores in eslint.config.js
C) Change each Array<T> to T[] by hand
D) Delete the file and write the types again
Why: types.ts is the API's contract and stays identical to shoreline-api/core/types.ts, so the next copy is a one-line job. The file is not yours to lint: ignore it (Project Step 1).
A is wrong: --fix edits the contract.
C is wrong: The same edit by hand: the copy no longer matches the API.
D is wrong: A second, drifting copy of every type is the mistake the lesson warns about.
Q11
.env.local says http://localhost:4000. The web preview lists the cleanups. What does Expo Go on a phone show today?
A) The same list
B) A red error screen
C) "Could not reach the server. Check that shoreline-api is running, then try again."
D) "Nothing was found at this address. Check the link."
Why: On a phone, localhost is the phone itself: the request gets no answer, request() throws a NetworkError, describeError picks the words. Expected until Lesson 5.1 gives the phone your computer's address.
A is wrong: Only a browser on your computer reaches the API as localhost.
B is wrong: The error is caught and shown as text.
D is wrong: That is a 404 from an API that did answer.
Q12
A teammate tried TypeScript 7, then ran npx expo install typescript (no --dev) to undo it. What did the course measure?
A) TypeScript 6.0 replaced 7.0 in devDependencies
B) npm refused to install an older version
C) Nothing changed: Expo ignores typescript
D) A second typescript entry under dependencies, with 7.0 left in devDependencies
Why: Use npx expo install --dev typescript: it puts the SDK's ~6.0.3 back as a dev dependency. Keep the SDK's version: expo lint's TypeScript support stops at 6.0.
A is wrong: That is what --dev does.
B is wrong: npm installs older versions without complaint.
C is wrong: expo install picks the SDK's version and writes it.

The Lesson Page's Own Quick Quiz

Lesson 1.3 · From the HQ to the Phone
  1. C It fails at run time, because a phone has no sessionStorage: Expo's tsconfig loads the DOM types for the web preview, so tsc accepts browser APIs. A phone has no sessionStorage, so the code fails while the app runs. Search copied code for browser APIs yourself; Lesson 4.3 stores the session with SecureStore.
  2. A src/api/types.ts: types.ts is the API's contract, identical to shoreline-api/core/types.ts. It holds only types, so nothing in it depends on the platform, and keeping it identical means a new copy from the API shows every place that has to change.
  3. D The old value was copied into the bundle; restart Metro with --clear: EXPO_PUBLIC_ values are copied into the bundle as text when Metro builds it. Stop Metro and start it with npx expo start --clear so it rebuilds with the new value.
  4. B On a phone, Expo's fetch fails with its own error, not a TypeError: On phones, Expo replaces fetch with its own implementation, which fails with a FetchError rather than the browser's TypeError. Wrapping every failed fetch in one NetworkError gives the same message on Android, iOS and the web preview.
  5. C Keep 6.0: the SDK pins it, and expo lint's TypeScript support stops at 6.0: SDK 58 pins TypeScript 6.0. The code checks the same with 7.0, but npx expo install --check flags it and npx expo lint crashes, because typescript-eslint supports TypeScript only up to 6.0. Keep the SDK's version and let SDK upgrades move it.

Exit Ticket

  1. Copy or rewrite: data code copies (types.ts, the guards, ApiError, describeError, formatDate, getAvailability); browser code is rewritten (the address from import.meta.env and window.location, the session in sessionStorage, components and CSS). Accept any rule that says this in the learner's words.
  2. What tsc accepts: window, document, sessionStorage, localStorage (the DOM types are loaded for the web preview). Find them by searching copied files for window, document, Storage, import.meta.
  3. .env.local changed: Ctrl+C, then npx expo start --clear: the value was copied into the bundle when Metro built it; a reload keeps the old one.

Common Wrong Answers and What They Reveal

  • Q2 "tsc catches it" / Q4 A, B or D. A clean type check taken as proof: run demo 1's search next to tsc.
  • Q5 A. Expects the browser's error everywhere: the lab's Task 2 test throws the phone's.
  • Q7 B. Silences a linter that is right: export and count the address in the bundle (demo 2).
  • Q8 A or D. "Environment variable" heard as "secret": an EXPO_PUBLIC_ value is plain text in the app.
  • Q10 A or C. Treats the contract as their own file: the next copy from the API would undo it.
  • Q11 A. The localhost trap again: Lesson 5.1 is where it is solved.
