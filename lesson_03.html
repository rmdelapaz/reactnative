🚚 Lesson 1.3: From the HQ to the Phone

You have already written a lot of Shoreline Crew's code. The organizers' web app, Shoreline Crew HQ, knows exactly what a cleanup looks like, how to check data from the API, how to explain a failed request and how to print a date on the crew's calendar. None of that knowledge cares whether it runs in a browser or on a phone, and some of it is tied to the browser in ways that are easy to miss. In this lesson you sort one from the other like a professional: you copy what carries over, rewrite what does not, set up the folders the app's shared code lives in, and make the app's first real request to the shoreline-api.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Decide which code from a React web app carries over to React Native unchanged, which must be rewritten, and explain why
  • Spot browser-only code (the DOM, sessionStorage, window.location, import.meta.env) that the type checker may not catch
  • Read Expo's TypeScript settings and explain how they and TypeScript 6.0 differ from the web project's
  • Give the app its API address with an EXPO_PUBLIC_ environment variable, and explain when the value is read
  • Set up the shared-code folders and make a typed, checked request whose result appears on the screen
  • ⏱️ Time 140 minutes
  • 📋 Prerequisites Lesson 1.2: Your Toolchain
  • 🛠️ You will build Shoreline Crew's shared code (src/api/types.ts, src/api/client.ts, src/utils/), its .env files, and a temporary home screen that lists the upcoming cleanups from the shoreline-api
  • 🧩 Stack Expo SDK 58 (React Native 0.88, React 19.3, Expo Router 58, TypeScript 6.0), the shoreline-api (the versions this lesson was checked with)
  • 📱 Where it runs the web preview on your computer, with shoreline-api in a second terminal (a phone reaches the API in Lesson 5.1)

👋 Welcome: Two Apps, One Crew

Shoreline Crew now has two apps. The organizers plan cleanups at a desk in Shoreline Crew HQ, the web app from the React + TypeScript course. The volunteers carry Shoreline Crew, the phone app you started in Lesson 1.2. Both talk to the same shoreline-api, so both need to agree on what a cleanup, a site and an error look like.

The tempting shortcut is to copy the HQ's whole src/ folder into the phone app and fix whatever breaks. The opposite mistake is to start from nothing and write a second, slightly different version of every type and helper. Real teams do neither: they move the code that is about the data and rewrite the code that is about the platform. Telling those apart is the skill of this lesson.

  • Why it matters for your work: companies rarely start a mobile app from zero. They already have a website, an API and its types. Developers who can say "these four files come across as they are, these two get rewritten, and here is why" save weeks, and avoid the bugs that come from two copies drifting apart.
  • Why it matters for the volunteers: when a volunteer's phone and an organizer's laptop show the same cleanup, they must show the same date, the same spots left and the same message when something goes wrong. Shared code is how you get that for free.

Did not take the React + TypeScript course? You can follow every step. The shared types come with the shoreline-api you downloaded in Lesson 1.2, every other file is shown in full on this page, and the places where the lesson compares with the web app explain what the web app did.

📦 What Carries Over, and Why

Here is the decision for every part of the HQ that the phone app needs. The rule behind it is short: code that only works with data copies over; code that touches the browser gets rewritten.

src/api/types.ts (the API's types)Copied, byte for byteIt is the contract with the API, written once in shoreline-api/core/types.ts. Only types: nothing in it runs anywhere.

ApiError, describeErrorCopied, plus one new error classThe same API sends the same error bodies. One thing differs: how a request fails when there is no answer at all (next section).
formatDate, getAvailabilityCopiedDates and spots are the same on every screen. Intl exists in the phone's JavaScript engine, Hermes.
The fetch calls (getEvents, getEvent …)Same shape, new addressThe base URL came from Vite's import.meta.env and the page's own address; neither exists in Expo, and localhost on a phone is the phone.
The session in sessionStorageRewritten (Lesson 4.3)There is no sessionStorage. A token belongs in the device's keychain (SecureStore), which is asynchronous.

💡 Mental model: the same tide chart, a different boat

A tide chart is just as true on a kayak as in the harbor office: the tides do not care who reads them. The API's types, the checks and the date rules are Shoreline Crew's tide chart, so they travel with you. The office's filing cabinet, its wall map and its front door (the browser's storage, its address bar, its page) stay behind; the kayak has its own dry bag and its own compass. When you look at a piece of code, ask: is this a tide chart, or is it part of the building?

Moving code this way also tells you where the code should live. The HQ already kept its data code in src/api/ and src/utils/, apart from its components. That separation is what makes today possible. A web app whose components called fetch and formatted dates inline would have nothing clean to copy.

📱 What Changes on a Phone

Lesson 1.1 showed the big three: no DOM (views are native, written as View and Text), no CSS (styles are JavaScript objects with no cascade), and no URL bar (Expo Router still has URLs, but the person holding the phone never types one). For shared code, those three turn into concrete things to search for in every file you copy:

In the HQOn the phoneDoes tsc warn you?

The type checker does not know you are on a phone

Here is the surprise in that table. This code from a web app type-checks cleanly in your Expo project:

// The HQ's demo build asked the browser where the site runs:
export const origin = window.location.origin;
export const pageTitle = document.title;

Why? Expo's TypeScript settings load the browser's type library ("lib": ["DOM", "ESNext"], see the next section), because the same project also runs in the web preview, where window.location is real. On a phone, the same line fails while the app runs: window exists, but has no location, so reading .origin throws a TypeError ("Cannot read property 'origin' of undefined", in Hermes' wording) and the red error screen appears. The web preview, of course, works perfectly. That is the trap: a clean type check and a working web preview do not prove the code runs on a phone. Your defense is a habit: when you copy a file from the web, search it for document, window, Storage and import.meta before you trust it. (The course's page checker even warns about these words in phone code.)

Same fetch, different failures

The fetch you call in Shoreline Crew is not the browser's. In SDK 58, Expo replaces the global fetch on phones with its own implementation (from expo/fetch, built on the platform's networking code). It takes the same arguments and returns the same kind of Response, so the HQ's request code works as it is. The difference is the error when there is no answer at all. In a browser, a fetch that cannot reach the server rejects with a TypeError ("Failed to fetch"), and the HQ's describeError relies on that:

  if (error instanceof ApiError) {
    return `The server had a problem (${error.status}). Try again in a moment.`
  }
  if (error instanceof TypeError) {
    return 'Could not reach the server. Check that shoreline-api is running, then try again.'
  }
  return 'Something unexpected went wrong. Try again in a moment.'
}

Expo's phone fetch throws its own FetchError instead, a plain Error whose message starts with "fetch failed:" (you can read it in node_modules/expo/src/winter/fetch/fetch.ts). Copied unchanged, describeError would tell a volunteer on a beach with no signal "Something unexpected went wrong" instead of "Could not reach the server". So the phone's client turns any failed fetch into one error of its own, NetworkError, in the one place where requests are sent, and describeError checks for that. It works the same in the web preview and on both phone platforms, and it is the reason the table above says "copied, plus one new error class".

✅ Not a failure, a finding

None of this means the web course taught you wrong. The HQ's code was right for a browser. Finding where its assumptions end is exactly the kind of thinking senior developers are paid for, and you will get faster at it with every file you move. If a copied file ever surprises you on a phone, that is not a dead end: it is the next item on this lesson's checklist that you had not met yet.

One HQ habit you can drop: the HQ wrote imports with the .ts extension ('../api/types.ts'), which Vite's settings allowed. They also type-check in this project, but Expo's own code and every example you will read write imports without extensions, often with the @/ alias. Shoreline Crew follows that style: '@/api/types'.

🧩 Version note: TypeScript 6.0 here, 7.0 in the HQ

Shoreline Crew HQ used TypeScript 7.0, the new compiler rewritten in Go. Expo SDK 58 pins "typescript": "~6.0.3", the last version of the original compiler written in TypeScript. For the code you write, nothing changes: 6.0 was made as the bridge to 7.0, with the same defaults (strict on, for example) and the same error codes; the course's checks found the same results with both. Two things do differ, and they explain the pin:

  • Speed. 7.0 is much faster. On the HQ's code, a full tsc --noEmit took about 0.3 seconds with 7.0 and 1.7 seconds with 6.0 when this course was checked. On Shoreline Crew's few files you will not notice.
  • Tools that use TypeScript from the inside. ESLint's TypeScript support (typescript-eslint, which npx expo lint uses) reads your code with TypeScript's JavaScript API, and the version Expo installs supports TypeScript only up to 6.0. That is also why the HQ linted with oxlint instead of ESLint. With TypeScript 7 installed, npx expo install --check says typescript@7.0.2 - expected version: ~6.0.3, and npx expo lint stops with Oops! Something went wrong! :( and a TypeError from inside ts-api-utils.

So keep the SDK's version. Expo tests each SDK with one TypeScript version and moves to a newer one when the tools around it are ready. When you upgrade the SDK later, npx expo install --fix brings TypeScript along.

🔐 The API Address: EXPO_PUBLIC_ Variables

The HQ read its API address from import.meta.env.VITE_API_URL. Expo has the same idea with different names: variables in .env files whose names start with EXPO_PUBLIC_ reach your code as process.env.EXPO_PUBLIC_….

Shoreline Crew HQ (Vite)Shoreline Crew (Expo)
Name prefixVITE_EXPO_PUBLIC_
Read in code asimport.meta.env.VITE_API_URLprocess.env.EXPO_PUBLIC_API_URL
Files.env.example (in Git, documents the variables), .env.local (your machine, not in Git: the template's .gitignore lists .env*.local)
When the value is readWhen the bundler builds the JavaScript: the value is copied into the bundle as text
A typo in the namea type error (the HQ described its variable)not a type error: Expo types any process.env name as string | undefined

"Copied into the bundle" has three consequences you should know by heart:

  1. Change .env.local, restart Metro. The running app keeps the old value. Stop Metro and start it with npx expo start --clear, so it rebuilds without its cache.
  2. Write the name out in full, with a dot. Metro replaces the exact text process.env.EXPO_PUBLIC_API_URL. Destructuring (const { EXPO_PUBLIC_API_URL } = process.env) is not replaced, and the value is undefined when the app runs (see Common Mistakes).
  3. Nothing in it is secret. Exactly as with VITE_ variables, but more so: anyone can download your app from a store and unpack its bundle. An API address is fine; a private key or password never is.

Because a misspelled name only shows up as undefined, the client checks the value when it uses it and throws an error that says what to do, the same pattern as the HQ. The screen only shows describeError's general words for it; when the list does not load, console.log the error to read the details (Metro's terminal for a phone, the browser's console for the web preview).

Which address?

For now, the address is http://localhost:4000, and you use the web preview: the browser runs on the same computer as the API, so localhost means your computer. On a phone, localhost is the phone itself (Lesson 1.2's warning), so Expo Go would show "Could not reach the server". That is expected today. Lesson 5.1 is all about reaching the API from a phone, an emulator and a simulator, with node server.ts --host and your computer's network address.

🛑 Never put secrets in EXPO_PUBLIC_ variables

Every EXPO_PUBLIC_ value ends up as plain text inside the app you ship. Keep keys for paid services, database passwords and anything you would not print on a flyer on a server, which uses them on the app's behalf, exactly as shoreline-api does for the crew.

types.ts: one contract, three copies

The API's types are written once, in shoreline-api/core/types.ts, and its first lines say so: every app that talks to the API copies it as src/api/types.ts. The HQ's copy, the API's original and Shoreline Crew's copy are identical, byte for byte. Never edit your copy. If the API changes, you copy the new file again, and the type checker shows you every place in the app that has to follow. (A monorepo with a shared package would remove the copying; that is a bigger setup than this course needs, and the idea is the same.)

One consequence: the API's file has its own style, and Expo's ESLint rules prefer T[] to Array<T>. Linting the copy gives four warnings, in a file you must not change:

But notice what is not on the list: the same file reads, saves and removes the session with sessionStorage and asks window.location for the page's address, and TypeScript accepts all of it. ⚠️ Destructuring process.env

const { EXPO_PUBLIC_API_URL: url } = process.env; type-checks, but npx expo lint reports it (expo/no-env-var-destructuring), and if you run it anyway the app shows "Something unexpected went wrong". Behind it is the error from apiBaseUrl(), "EXPO_PUBLIC_API_URL is not set" (add console.log(error) to the screen's catch and Metro's terminal shows it on a phone; the browser's console in the web preview). Metro only replaces the full expression process.env.EXPO_PUBLIC_API_URL; the course checked the bundle Expo builds, and with destructuring the address simply is not in it. Write the variable out in full every time you read it.

⚠️ Editing .env.local and expecting the app to notice

The value was copied into the bundle when Metro built it. Stop Metro (Ctrl+C) and start it again with npx expo start --clear. And check the file's name: .env.local with a leading dot, in the shoreline-crew folder (not in src/, not in shoreline/). When Metro has found it, its first lines say so:

Expected output (the top of npx expo start)

env: export EXPO_PUBLIC_API_URL
Starting project at ~/shoreline/shoreline-crew
...

⚠️ "Fixing" types.ts

Running npx expo lint --fix before types.ts is ignored rewrites Array<T> as T[], and adding a field "the phone needs" is worse: your copy no longer matches the API, and the next time you copy the API's file your change silently disappears. If the phone needs a type the API does not have, write it in another file and build it from the API's types.

⚠️ "Upgrading" TypeScript to 7

It is tempting, since the HQ used it. npx expo lint then crashes with Oops! Something went wrong! :( and TypeError: Cannot read properties of undefined (reading 'Intrinsic'). Put it back with npx expo install --dev typescript, which installs the version SDK 58 expects as a dev dependency. Without --dev, the course measured a trap: Expo adds a second "typescript": "~6.0.3" under dependencies and leaves ~7.0.2 in devDependencies.

Step 2: The utilities: format.ts and availability.ts (10 min)

Create src/utils/ and these two files. With the HQ: copy its two files and change only the import line from '../api/types.ts' to '@/api/types'. The course's versions also end statements with semicolons, the Expo template's style; the code is otherwise the HQ's, comment for comment.

shoreline-crew/src/utils/format.ts
import type { DateString } from '@/api/types';

// Made once, used for every date: weekday, month name, day and year
const dateFormat = new Intl.DateTimeFormat('en-US', {
  weekday: 'short',
  month: 'short',
  day: 'numeric',
  year: 'numeric',
});

// The API's dates are days on the crew's calendar ("YYYY-MM-DD"). JavaScript reads a date
// alone as midnight UTC, which is still the day before on the US west coast; with a time
// and no time zone it reads the local midnight instead.
export function formatDate(date: DateString): string {
  return dateFormat.format(new Date(`${date}T00:00`));
}

// Today (or any moment) as a "YYYY-MM-DD" day on this device's calendar
export function toDateString(date: Date): DateString {
  const month = String(date.getMonth() + 1).padStart(2, '0');
  const day = String(date.getDate()).padStart(2, '0');
  return `${date.getFullYear()}-${month}-${day}`;
}
shoreline-crew/src/utils/availability.ts
import type { CleanupEvent } from '@/api/types';

// What an event card says about spots. Each kind carries only the data that kind needs.
export type Availability =
  | { kind: 'open'; spotsLeft: number }
  | { kind: 'full' }
  | { kind: 'closed' };

export function getAvailability(event: CleanupEvent): Availability {
  if (event.status !== 'scheduled') {
    return { kind: 'closed' };
  }
  const spotsLeft = event.capacity - event.spotsTaken;
  return spotsLeft > 0 ? { kind: 'open', spotsLeft } : { kind: 'full' };
}

Read them with a phone in mind: no document, no window, no storage. Intl.DateTimeFormat is part of JavaScript itself, and Hermes includes it on Android and iOS. The comment about time zones matters even more on a phone, which changes time zone when its owner travels: formatDate reads the API's day as a day, never as a moment, so a cleanup on a given Saturday stays on that Saturday.

  'meetingPoint', 'description', 'leadOrganizerId', 'createdAt', 'updatedAt',

export function isCleanupEvent(value: unknown): value is CleanupEvent {
  return (
    isRecord(value) &&
    eventTextFields.every((key) => typeof value[key] === 'string') &&
    isEventStatus(value.status) &&
    typeof value.capacity === 'number' &&
    typeof value.spotsTaken === 'number' &&
    isStringArray(value.suppliesProvided)
  );
}

const terrains: Terrain[] = ['sand', 'rocky', 'marsh', 'mixed'];
const siteTextFields: (keyof Site)[] = ['id', 'name', 'town', 'parking', 'description'];

export function isSite(value: unknown): value is Site {
  return (
    isRecord(value) &&
    siteTextFields.every((key) => typeof value[key] === 'string') &&
    terrains.some((terrain) => terrain === value.terrain) &&
    typeof value.accessible === 'boolean' &&
    typeof value.latitude === 'number' &&
    typeof value.longitude === 'number' &&
    isRecord(value.image) &&
    typeof value.image.url === 'string' &&
    typeof value.image.alt === 'string' &&
    typeof value.image.width === 'number' &&
    typeof value.image.height === 'number'
  );
}

/** A cleanup as GET /api/events/:id sends it: a CleanupEvent plus its whole site
 * (and, for organizers, the code volunteers type to check in on the day) */
export function isCleanupEventDetail(value: unknown): value is CleanupEventDetail {
  return (
    isCleanupEvent(value) &&
    'site' in value &&
    isSite(value.site) &&
    (!('checkInCode' in value) || typeof value.checkInCode === 'string')
  );
}

/** A check for one item becomes a check for a list of them */
function isListOf<T>(isT: (value: unknown) => value is T) {
  return (value: unknown): value is T[] => Array.isArray(value) && value.every(isT);
}

function isApiErrorBody(value: unknown): value is ApiErrorBody {
  return isRecord(value) && typeof value.error === 'string' && typeof value.message === 'string';
}

// ---------------------------------------------------------------- errors

/** The API answered, but with an error status (404, 500, ...) (copied) */
export class ApiError extends Error {
  readonly status: number;
  readonly code: ErrorCode;
  readonly fieldErrors: Record<string, string[]> | undefined;

  constructor(status: number, body: ApiErrorBody) {
    super(body.message);
    this.name = 'ApiError';
    this.status = status;
    this.code = body.error;
    this.fieldErrors = body.fieldErrors;
  }
}

/** The request never got an answer: no network, a wrong address, or the API is not running (new) */
export class NetworkError extends Error {
  constructor(cause: unknown) {
    super('Could not reach the API', { cause });
    this.name = 'NetworkError';
  }
}

/** What to tell people when a request failed */
export function describeError(error: unknown): string {
  if (error instanceof ApiError && error.status === 401) {
    return 'Your sign-in has ended. Sign in again.';
  }
  if (error instanceof ApiError && error.status === 404) {
    return 'Nothing was found at this address. Check the link.';
  }
  if (error instanceof ApiError) {
    return `The server had a problem (${error.status}). Try again in a moment.`;
  }
  if (error instanceof NetworkError) {
    return 'Could not reach the server. Check that shoreline-api is running, then try again.';
  }
  return 'Something unexpected went wrong. Try again in a moment.';
}

// ---------------------------------------------------------------- talking to the API

function apiBaseUrl(): string {
  // Expo copies EXPO_PUBLIC_ variables into the bundle when Metro builds it (rewritten)
  const url = process.env.EXPO_PUBLIC_API_URL;
  if (url === undefined || url === '') {
    throw new Error('EXPO_PUBLIC_API_URL is not set: copy .env.example to .env.local');
  }
  return url;
}

/** Send a request to a path under /api. Throws ApiError on an error status, NetworkError without an answer. */
async function request(path: string, init: RequestInit = {}): Promise<Response> {
  const url = `${apiBaseUrl()}/api${path}`;
  let response: Response;
  try {
    response = await fetch(url, init);
  } catch (error) {
    // In the browser a failed fetch is a TypeError; on a phone, Expo's fetch throws its own error
    throw new NetworkError(error);
  }
  if (!response.ok) {
    const body: unknown = await response.json().catch(() => null);
    throw new ApiError(
      response.status,
      isApiErrorBody(body) ? body : { error: 'server_error', message: `HTTP ${response.status}` },
    );
  }
  return response;
}

/** GET a path and check the JSON with a type predicate before anyone uses it */
export async function getJSON<T>(
  path: string,
  isT: (value: unknown) => value is T,
  signal?: AbortSignal,
): Promise<T> {
  const response = await request(path, { signal });
  const data: unknown = await response.json();
  if (!isT(data)) {
    throw new Error(`Unexpected data from GET /api${path}`);
  }
  return data;
}

/** One page of a list, and where it sits in the whole list */
export interface Page<T> {
  items: T[];
  page: PageInfo;
}

/** GET a list: the items are in the body, the page numbers in the response headers */
export async function readPage<T>(
  path: string,
  isItem: (value: unknown) => value is T,
  signal?: AbortSignal,
): Promise<Page<T>> {
  const response = await request(path, { signal });
  const items: unknown = await response.json();
  if (!isListOf(isItem)(items)) {
    throw new Error(`Unexpected data from GET /api${path}`);
  }
  // page and perPage are what we asked for (or the API's defaults, 1 and 10)
  const url = new URL(response.url);
  return {
    items,
    page: {
      page: Number(url.searchParams.get('page') ?? '1'),
      perPage: Number(url.searchParams.get('perPage') ?? '10'),
      total: Number(response.headers.get('X-Total-Count')),
      totalPages: Number(response.headers.get('X-Total-Pages')),
    },
  };
}

export function getSites(signal?: AbortSignal): Promise<Site[]> {
  return getJSON('/sites', isListOf(isSite), signal);
}

/** Cleanups; query is a search string such as 'when=upcoming&perPage=20' */
export function getEvents(query: string, signal?: AbortSignal): Promise<Page<CleanupEvent>> {
  return readPage(`/events?${query}`, isCleanupEvent, signal);
}

/** One cleanup with its site. An unknown id (or a draft) is an ApiError with status 404. */
export function getEvent(id: string, signal?: AbortSignal): Promise<CleanupEventDetail> {
  return getJSON(`/events/${encodeURIComponent(id)}`, isCleanupEventDetail, signal);
}

import { useEffect, useState } from 'react';
import { ScrollView, StyleSheet, Text } from 'react-native';

import { describeError, getEvents } from '@/api/client';
import type { CleanupEvent } from '@/api/types';
import { getAvailability } from '@/utils/availability';
import { formatDate } from '@/utils/format';

// Temporary: proves the shared code works on a phone. Lesson 2.1 turns this into a real screen.
type Load =
  | { status: 'loading' }
  | { status: 'failed'; message: string }
  | { status: 'loaded'; events: CleanupEvent[] };

function spotsText(event: CleanupEvent): string {
  const availability = getAvailability(event);
  switch (availability.kind) {
    case 'open':
      return availability.spotsLeft === 1 ? '1 spot left' : `${availability.spotsLeft} spots left`;
    case 'full':
      return 'Full';
    case 'closed':
      return 'Closed';
  }
}

export default function Index() {
  const [load, setLoad] = useState<Load>({ status: 'loading' });

  useEffect(() => {
    const controller = new AbortController();
    getEvents('when=upcoming', controller.signal)
      .then((page) => setLoad({ status: 'loaded', events: page.items }))
      .catch((error: unknown) => {
        if (!controller.signal.aborted) {
          setLoad({ status: 'failed', message: describeError(error) });
        }
      });
    return () => controller.abort();
  }, []);

  return (
    <ScrollView contentContainerStyle={styles.container}>
      <Text accessibilityRole="header" style={styles.title}>
        Shoreline Crew
      </Text>
      <Text style={styles.tagline}>Many hands, cleaner sands.</Text>

      {load.status === 'loading' && <Text>Loading cleanups…</Text>}
      {load.status === 'failed' && (
        <Text accessibilityRole="alert" style={styles.error}>
          {load.message}
        </Text>
      )}
      {load.status === 'loaded' &&
        load.events.map((event) => (
          <Text key={event.id} style={styles.event}>
            {event.title} · {formatDate(event.date)} · {spotsText(event)}
          </Text>
        ))}
    </ScrollView>
  );
}

  container: {

Everything in it is from the web course, in phone clothes:

  • The Load union and the useEffect with an AbortController are the fetching pattern from Lesson 4.1 of the React + TypeScript course: the cleanup function aborts the request if the screen goes away, and an aborted request does not set state.
  • spotsText switches over the copied Availability union; TypeScript knows every case returns.
  • ScrollView replaces the centered View, so a long list can scroll (a View never scrolls on a phone; the page itself is not scrollable as it is in a browser).
  • accessibilityRole="alert" on the error text asks screen readers to announce it when it appears, like role="alert" on the web.
  • @/api/client and the other @/ imports work from any folder.

❓ Common Questions at This Stage

Why copy files instead of sharing one folder or an npm package?

Sharing is better for a team that maintains both apps every day: a monorepo with a shared package (npm, pnpm or yarn workspaces) keeps one copy, and Metro supports monorepos. It also adds setup that has nothing to do with learning React Native. The course copies, keeps types.ts identical so a new copy is a one-line job, and leaves the monorepo as a next step you will recognize when you meet one at work.

Why not use Zod to check the API's data, instead of hand-written type guards?

Either works on a phone; Zod 4 runs in Hermes. The HQ used guards for API data and Zod for forms, and the phone app keeps that split so the copied code stays copied. Lesson 5.4 brings Zod in for the phone's forms.

Why does the screen use useEffect when the web course moved to TanStack Query?

Because this screen is temporary, and Query on a phone has its own lesson. On a phone, "the window got focus" and "the network came back" mean different things than in a browser, and Lesson 5.2 sets that up properly. Until then, the effect pattern from the web course's Lesson 4.1 is enough to prove the pipe works.

The API's dates show the weekday, but in which time zone?

None, on purpose. A cleanup's date is a day on the crew's calendar (the API says the crew is in America/Los_Angeles), and formatDate prints that day as it is. A volunteer who flies to another time zone still sees the right Saturday. Times of day are just text ("09:00") for the same reason.

Do I need the HQ project from the web course at all?

No. Everything Shoreline Crew needs is in the shoreline-api download and on this page. If you have the HQ, it is a useful reference whenever a lesson says "as in the web course".
