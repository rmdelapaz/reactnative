🧱 Lesson 2.1: View, Text and StyleSheet

You know CSS well enough to style a web app without thinking about it. On a phone, the same instincts are about eighty percent right, and the other twenty percent is where the surprises live: there is no stylesheet that flows down the page, no class names, no px, and text follows its own rules. In this lesson you learn exactly where the line runs, and you use it to turn the plain list from Lesson 1.3 into Shoreline Crew's first real screen, with the crew's colors in a theme file and a card for every upcoming cleanup.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Build screens from View and Text, and say which HTML habits they replace
  • Write styles with StyleSheet.create: camelCase names, numbers instead of px, no shorthands, and know which mistakes the type checker catches
  • Explain why styles do not cascade in React Native, and use the one place they do: a Text inside a Text
  • Combine styles with style arrays, where later entries win and false entries are skipped
  • Describe how fonts, font weights, line heights and the person's text size differ between Android, iOS and the web preview
  • Keep the app's colors and spacing in a theme file and build reusable, typed AppText and EventCard components
  • ⏱️ Time 140 minutes
  • 📋 Prerequisites Lesson 1.3: From the HQ to the Phone
  • 🛠️ You will build Shoreline Crew's theme files (src/theme/colors.ts, spacing.ts), an AppText component, an EventCard, and the first real Cleanups screen
  • 🧩 Stack Expo SDK 58 (React Native 0.88, React 19.3, Expo Router 58, TypeScript 6.0), the shoreline-api (the versions this lesson was checked with)

👋 Welcome: CSS Instincts, Phone Rules

At the end of Lesson 1.3, Shoreline Crew could talk to the API, but its home screen looked like a debug log: one line of text per cleanup. Volunteers deserve better. They glance at this screen on a beach, in bright sun, with a bag of litter in one hand, so it has to be clear at a glance: which cleanup, when, where to meet, and whether there is still room.

In Shoreline Crew HQ you built that kind of card with an <article>, a CSS Module and a few CSS variables. None of those exist here. Lesson 1.1 told you the headline ("no DOM, no CSS"); this lesson gives you the details that make the difference between fighting React Native and working with it.

  • Why it matters for your work: styling is where web developers lose the most time in their first React Native weeks, mostly to things that silently do nothing. Knowing which habits carry over and which are ignored without a word is what makes you productive on a mobile team quickly.
  • Why it matters for the volunteers: a screen that respects the phone's own fonts and the person's text size reads well in the sun and for people who need larger text. You get that mostly for free, as long as you do not fight it.

✅ Expect a few "why is nothing happening?" moments

Everyone who comes from the web writes a style that React Native quietly ignores, and then stares at the screen. That is not a sign you are bad at this: it is the exact moment this lesson is for. When it happens, ask two questions from this page: "is this style on the right kind of component?" and "is this a value React Native understands?" Most puzzles end there.

🧱 View and Text: Two Building Blocks

A web page is built from dozens of HTML elements. A React Native screen is built mostly from two components, and almost everything else is a specialized version of them:

  • View is a box: it holds other components, has a size, a background, a border and padding, and lays out its children (with flexbox, Lesson 2.2). On Android it becomes a native android.view.View; on iOS a UIView. It cannot show text by itself.
  • Text shows text, and only Text can. On Android and iOS it becomes the platform's own native text view. It has text styles (font, size, color, weight, line height) that a View does not have.

Here is where the HTML you know goes:

There is no semantic zoo of elements: a heading is a Text that says it is a heading, through accessibilityRole, so a screen reader can announce it. You will set that role on every heading you build today.

The one rule you already know

Lesson 1.1 showed it: a string directly inside a View is an error on a phone ("Text strings must be rendered within a <Text> component"), and the red error screen appears. One more detail you should know now: the web preview forgives it. When the course put <View>raw words</View> in an exported web build, the browser simply showed "raw words", with no message in the console. So the web preview is not proof that a screen works on a phone. When something looks fine on the web, the rules on this page still apply.

🎨 Styles Are Objects

In React Native, a style is a plain JavaScript object passed to a component's style prop. You already wrote some in Lessons 1.2 and 1.3 with StyleSheet.create. Here is how the HQ's CSS habits translate:

import { StyleSheet } from 'react-native';

// The HQ's CSS habits, written the React Native way
export const styles = StyleSheet.create({
  card: {
    padding: 16, // padding: 1rem
    paddingHorizontal: 24, // padding-left and padding-right
    borderWidth: 1, // border: 1px solid #e4dccb
    borderColor: '#e4dccb',
    borderRadius: 12,
    width: '50%', // a percentage is a string
  },
  label: {
    fontSize: 14,
    lineHeight: 20, // a size, not a multiplier like 1.5
    fontWeight: '600',
    textTransform: 'uppercase',
    letterSpacing: 0.5,
  },
});

border: 1px solid #e4dccbborderWidth: 1, borderColor: '#e4dccb'No shorthands that pack several values into one string
padding: 8px 16pxpaddingVertical: 8, paddingHorizontal: 16Same reason; Vertical and Horizontal exist instead

Colors: #0b3954, rgb(), whiteThe same stringsOne thing that really does carry over

Density-independent pixels. Phones have very different screens: one may pack two physical pixels into the space where another has three. If fontSize: 16 meant 16 physical pixels, text would be tiny on the sharper screen. So React Native's numbers are in units of about the same physical size on every phone (Android calls them dp, iOS calls them points): 16 becomes 32 physical pixels on a "2x" screen and 48 on a "3x" one. That is also what the web's px really is on a phone browser, so your sense of "16 is body text, 32 is a big heading" carries over.

Why StyleSheet.create?

You can pass an object straight to style (style={{ padding: 16 }}), and it works. StyleSheet.create gives you three things for one line of code: every style has a name you can read in the JSX, the styles live in one place at the bottom of the file like a CSS Module, and TypeScript checks each style against everything a View, Text or Image accepts. Lesson 1.2's exercise showed one side of that check: a misspelled style name such as styles.tagLine is a type error (TS2551). A misspelled or invented property inside StyleSheet.create is one too, as the next table shows.

What the type checker catches, and what it does not

That check is good, but not complete. The course tried the classic web habits in Shoreline Crew's own files, with npx tsc --noEmit:

🧩 Version note: string sizes in React Native 0.88

React Native 0.88's types allow any string for sizes such as padding and width (its DimensionValue type is number | string | "auto" | null), so '16px' type-checks. The web preview hands the string to the browser, which understands px. React Native's native layout code, which the course read for this version, understands only numbers, 'auto' and percentages such as '50%', and treats anything else as "not set". So padding: '16px' should look right in the web preview and have no padding on a phone. The rule that keeps you safe on every version: sizes are numbers, or percentages as strings.

🌊 No Cascade: Text Inherits from Text Only

On the web you set color and font-family once on :root or a container, and every paragraph below inherits them. The HQ's index.css did exactly that. Try the same in React Native:

import { StyleSheet, Text, View } from 'react-native';

// The web habit: set the color and size once, on the container
export function Heading() {
  return (
    <View style={styles.box}>
      <Text>Upcoming cleanups</Text>
    </View>
  );
}

const styles = StyleSheet.create({
  box: {
    padding: 16,
    color: '#0b3954', // type-checks, but a View draws no text: the Text below stays black
    fontSize: 20,
  },
});

It type-checks and lints, and "Upcoming cleanups" appears in the default text style (size 14 in the system font), not in Deep Tide at 20. In the web preview the course measured exactly that: the View got a color of its own, and the Text inside it was black at 14 pixels. Two rules explain it:

  1. Styles stay on the component you put them on. There are no selectors and no cascade: a style object belongs to one component. A View has no text to color, so color on a View does nothing at all.
  2. The one exception is a Text inside a Text. A nested Text inherits the text styles of the Text around it and can change some of them, like a <strong> inside a <p>. That is how you style part of a line.
graph TD A["View: color, fontSize"] -.->|"not passed on"| B["Text: 14, black"] C["Text: color, size"] -->|"inherited"| D["Text inside it: + bold"]

You will write this in the project's EventCard: the spots line is one Text, and only the number inside it is bold. The inner Text gets the line's color, size and line height for free:

shoreline-crew/src/components/EventCard.tsx
{availability.kind === 'open' && (
  <AppText>
    {/* A Text inside a Text inherits its color and size: only the weight changes */}
    <Text style={styles.strong}>{availability.spotsLeft}</Text> of {event.capacity} spots left
  </AppText>
)}

💡 Mental model: tide pools, not a creek

CSS is a creek: pour color in at the top of the page and everything downstream gets wet. React Native is a beach of tide pools. Each Text holds only the water you pour into it; a View is a rock, and water poured on a rock runs off. The one shortcut: a small pool inside a bigger pool (a Text inside a Text) shares its water. So when you want the same text style in many places, you do not pour it at the top; you give every pool the same bucket. That bucket is a component, AppText, and you build it in the project.

This is also why React Native apps nearly always have their own text component. Without one, every Text in the app needs its color, size and line height repeated, and a change to the body text means editing every screen.

🧩 Style Arrays: Combining Styles

Without classes, how do you give one element a base style plus a variation? You pass an array to style. React Native merges it from left to right, so later entries win, and it skips false, null and undefined, which makes conditions easy:

import { StyleSheet, Text } from 'react-native';

type SpotsProps = { full: boolean; label: string };

// A style array: later entries win, and false, null or undefined entries are skipped
export function Spots({ full, label }: SpotsProps) {
  return <Text style={[styles.line, full && styles.full]}>{label}</Text>;
}

const styles = StyleSheet.create({
  line: { fontSize: 16, color: '#1f2a37' },
  full: { fontWeight: 'bold', color: '#b23a22' },
});

When full is false, the array is [styles.line, false] and only line applies; when it is true, full's bold and coral win over line's color. This replaces three web patterns at once: className={`${a} ${b}`}, a modifier class, and the clsx helper.

Arrays also make components flexible. Shoreline Crew's AppText will combine three layers: a base style, a variant (title, heading, body, muted, error) and whatever a screen passes in. Here is how the banner's title ends up white, bold and 32 units tall:

graph TD A["styles.base: 16, Ink"] --> B["styles.title: 32, bold"] B --> C["the screen's style: white"] C --> D["drawn: 32, bold, white"]

Every layer only says what it changes. The base sets the color, size and line height; the title variant replaces the size and line height and adds bold; the screen replaces the color. Nothing else in the app has to know.

🔤 Text on Android, iOS and the Web

A Text with no fontFamily uses the platform's own system font: San Francisco on an iPhone and Roboto on most Android phones. The web preview asks the browser for its system font (the course measured the list react-native-web uses: -apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, Helvetica, Arial, sans-serif), so the same screen looks a little different on your computer, an iPhone and an Android phone. That is a feature: each app feels at home on its phone. Custom fonts, such as the crew's heading font Outfit, arrive in Lesson 2.3.

  • Font weights. fontWeight accepts 'normal', 'bold', '100' to '900' (as strings or numbers) and names such as 'semibold'. A font may not have every weight; the comment on fontWeight in React Native's own type definitions says that in that case "the closest one is chosen". So '600' can look like bold on one phone and like semibold on another. Use a few weights and look at them on a real device.
  • Line height. lineHeight is a size in the same units as fontSize. For body text, about one and a half times the font size reads well: fontSize: 16 with lineHeight: 24. The course measured what happens with the CSS habit lineHeight: 1.5: the line in the web preview was 1.5 pixels tall.
  • The person's text size. Android and iOS let people make all text larger in their settings, and React Native follows that setting by default (allowFontScaling is true). A 16 can become 20 or much more. Do not turn it off, and do not give a box with text in it a fixed height: let text grow and wrap. Lesson 8.1 tests the extremes.

📱 On your phone

Open the finished screen in Expo Go and compare it with the web preview: the headings and body text should appear in San Francisco on an iPhone and in Roboto on an Android phone, and the bold weights may differ slightly. Then make the phone's text larger (iPhone: Settings > Display & Brightness > Text Size; Android: Settings > Display > Font size, the exact names vary by maker) and return to Expo Go: the cards should grow taller with the text. Until Lesson 5.1, Expo Go shows "Could not reach the server" instead of the cards, but the banner and heading already show the effect.

🎨 A Theme File for the Crew's Colors

Lessons 1.2 and 1.3 typed the crew's colors straight into index.tsx: '#0b3954' for the title, '#1f6f8b' for the tagline. With one screen that was fine. With cards, banners and soon a dozen screens, a hex code in every file is how apps end up with eleven slightly different blues.

The HQ solved this with CSS custom properties (--deep-tide, --text, --surface). React Native has no CSS variables, but it has something just as good: a TypeScript module that exports constants. Shoreline Crew's theme has two layers, the same two the HQ's index.css had:

  • brand: the crew's named colors (Deep Tide, Sea Teal, Sand, Coral…), copied from the HQ.
  • colors: what each color is for (page, surface, text, heading, error…). Screens use only these.

Naming colors by their job is what makes dark mode possible later: in Lesson 2.5, colors.page becomes Sand in light mode and a deep night blue in dark mode, and no screen has to change. Until then the app is light only, on purpose; if your phone is in dark mode, the screen stays light.

Two TypeScript details make the theme pleasant to use. as const makes every value a read-only literal, so colors.page is exactly '#fbf6ec' (hover over it in VS Code) and nobody can assign to it by accident. And because the theme is ordinary code, a typo such as colors.pgae is a type error, which a misspelled var(--pgae) in CSS never was.

⚠️ Common Mistakes

⚠️ Units in sizes

fontSize: '16px' is caught. TypeScript says:

Expected output (shortened)

src/components/AppText.tsx:20:5 - error TS2322: Type 'string' is not assignable to type 'number'.

20     fontSize: '16px',
       ~~~~~~~~

  node_modules/react-native/types_generated/Libraries/StyleSheet/StyleSheetTypes.d.ts:811:3
    811   fontSize?: number | undefined;
          ~~~~~~~~
...

Found 1 error in src/components/AppText.tsx:20

Read it from the top: the file and line, the type that was expected (number), the line with the tildes under the problem, and where the rule comes from (React Native's own style types). padding: '16px' is not caught (see the version note above), so drop units everywhere, not only where the checker complains.

⚠️ CSS shorthands

border: '1px solid #e4dccb' produces one of TypeScript's longest messages. Its first line begins src/components/EventCard.tsx:44:5 - error TS2345: Argument of type and runs on for hundreds of characters; the words that matter are further in: 'border' does not exist in type. Skip to the code frame, which points at the property:

Expected output (shortened)

...
  Property 'card' is incompatible with index signature.
...

44     border: '1px solid #e4dccb',
       ~~~~~~

Found 1 error in src/components/EventCard.tsx:44

Write borderWidth, borderColor and, if you need it, borderStyle. Long error messages are not a sign of a big problem; look for the line number and the property name, then read the rest only if you need it.

⚠️ className out of habit

Your fingers will type it at least once, and nothing will stop you. Once Metro has started (Lesson 1.2), Expo's generated expo-env.d.ts loads Expo's own types, which add a className prop to View and Text for the web. So npx tsc --noEmit prints nothing, and the card simply does not get its look: no stylesheet defines card, and a phone ignores the prop. Use style={styles.card}. (Libraries such as NativeWind turn className into real Tailwind styles; that is a choice a team makes, and the course does not use it.)

⚠️ Text styles on a View

A color, fontSize or fontWeight in a View's style passes the type check and does nothing. When text does not change, check which component the style is on, and move it to the Text (or give the Text a variant of AppText).

⚠️ lineHeight as a multiplier

lineHeight: 1.5 type-checks and squeezes every line into 1.5 units: lines overlap or vanish. Multiply yourself: font size 16, line height 24.

⚠️ Trusting the web preview with a stray string

A string left directly inside a View (for example after deleting a <Text> tag but not its words) looks fine in the web preview, while a phone shows the red error screen. When you edit JSX, keep every word inside a Text or an AppText, and look at the phone now and then.

Step 2: AppText, the app's text component (15 min)

Create src/components/AppText.tsx. It is a Text with Shoreline Crew's text styles built in:

shoreline-crew/src/components/AppText.tsx
import { StyleSheet, Text, type TextProps } from 'react-native';

import { colors } from '@/theme/colors';

// Every piece of text in Shoreline Crew goes through AppText, so the app has one set of text styles
export type TextVariant = 'title' | 'heading' | 'body' | 'muted' | 'error';

type AppTextProps = TextProps & {
  variant?: TextVariant;
};

export function AppText({ variant = 'body', style, ...rest }: AppTextProps) {
  // Later styles win: the base, then the variant, then whatever the screen passes in
  return <Text style={[styles.base, styles[variant], style]} {...rest} />;
}

const styles = StyleSheet.create({
  base: {
    color: colors.text,
    fontSize: 16,
    lineHeight: 24,
  },
  title: {
    fontSize: 32,
    lineHeight: 40,
    fontWeight: 'bold',
  },
  heading: {
    color: colors.heading,
    fontSize: 20,
    lineHeight: 28,
    fontWeight: '600',
  },
  body: {},
  muted: {
    color: colors.textMuted,
  },
  error: {
    color: colors.error,
  },
});

What each part does:

  • TextProps & { variant?: TextVariant }: AppText accepts every prop a Text accepts (accessibilityRole, numberOfLines, style…) plus one of its own. This is the "extend the props of the element you wrap" pattern from the web course, with React Native's TextProps instead of ComponentProps<'p'>. type TextProps in the import brings in only the type.
  • { variant = 'body', style, ...rest }: the screen's own style is taken out so it can go last in the array; everything else goes straight to Text.
  • styles[variant]: TypeScript knows variant is one of five names and that styles has all five, so the lookup is checked. Exercise 3 shows what happens when they disagree.
  • body: {} is empty on purpose: body text is just the base. Keeping it as a named variant means a screen can say what it means, and a later lesson can give body text its own font without touching any screen.
  • Every variant has a lineHeight about one and a half times its fontSize, and none sets a fixed height, so larger text from the phone's settings still fits.

Step 3: EventCard (20 min)

If you have Shoreline Crew HQ, open its src/components/EventCard.tsx beside the phone version. The HQ's card is an <article> with an <h3>, a <time>, and a SpotsLine that says "5 of 12 spots left" or "Full: new sign-ups join the waiting list". The phone's card keeps those words and that order, and rebuilds the markup from View and AppText. Create src/components/EventCard.tsx:

shoreline-crew/src/components/EventCard.tsx
import { StyleSheet, Text, View } from 'react-native';

import type { CleanupEvent } from '@/api/types';
import { AppText } from '@/components/AppText';
import { colors } from '@/theme/colors';
import { radius, spacing } from '@/theme/spacing';
import { getAvailability } from '@/utils/availability';
import { formatDate } from '@/utils/format';

type EventCardProps = {
  event: CleanupEvent;
};

// One cleanup in a list: the phone's version of the HQ's EventCard
export function EventCard({ event }: EventCardProps) {
  const availability = getAvailability(event);

  return (
    <View style={styles.card}>
      <AppText variant="heading" accessibilityRole="header">
        {event.title}
      </AppText>
      <AppText>
        {formatDate(event.date)}, {event.startTime} to {event.endTime}
      </AppText>
      <AppText variant="muted">Meet at: {event.meetingPoint}</AppText>
      {availability.kind === 'open' && (
        <AppText>
          {/* A Text inside a Text inherits its color and size: only the weight changes */}
          <Text style={styles.strong}>{availability.spotsLeft}</Text> of {event.capacity} spots left
        </AppText>
      )}
      {availability.kind === 'full' && (
        <AppText style={styles.strong}>Full: new sign-ups join the waiting list</AppText>
      )}
    </View>
  );
}

const styles = StyleSheet.create({
  card: {
    gap: spacing.xs,
    padding: spacing.md,
    borderWidth: 1,
    borderColor: colors.border,
    borderRadius: radius.card,
    backgroundColor: colors.surface,
  },
  strong: {
    fontWeight: 'bold',
  },
});
  • The card is a View with the HQ card's look: a white surface, a one-unit border, rounded corners (the HQ's 0.75rem is 12) and padding. gap spaces the lines, as in Lesson 1.3's screen; Lesson 2.2 explains how gap and flexbox lay things out.
  • The title is a heading for screen readers (accessibilityRole="header"), the HQ's <h3>.
  • The spots line uses the copied getAvailability. For an open cleanup, a nested Text makes only the number bold (no cascade, but inheritance inside Text). A full cleanup gets the whole line bold by passing style={styles.strong} to AppText, the last entry in its array. A closed cleanup shows no spots line, like the HQ's.
  • The HQ's card also showed the site's name, a status badge and a "Show details" button. The badge comes in Lesson 2.2, buttons in Lesson 2.4, and the details move to their own screen in Lesson 4.1.

  | { status: 'failed'; message: string }
  | { status: 'loaded'; events: CleanupEvent[] };

// The Cleanups screen: the crew's banner, then one card per upcoming cleanup
export default function Index() {
  const [load, setLoad] = useState<Load>({ status: 'loading' });

  useEffect(() => {
    const controller = new AbortController();
    getEvents('when=upcoming', controller.signal)
      .then((page) => setLoad({ status: 'loaded', events: page.items }))
      .catch((error: unknown) => {
        if (!controller.signal.aborted) {
          setLoad({ status: 'failed', message: describeError(error) });
        }
      });
    return () => controller.abort();
  }, []);

  return (
    <ScrollView style={styles.screen} contentContainerStyle={styles.content}>
      <View style={styles.banner}>
        <AppText variant="title" accessibilityRole="header" style={styles.bannerTitle}>
          Shoreline Crew
        </AppText>
        <AppText style={styles.bannerTagline}>Many hands, cleaner sands.</AppText>
      </View>
      <AppText variant="heading" accessibilityRole="header">
        Upcoming cleanups
      </AppText>
      {load.status === 'loading' && <AppText variant="muted">Loading cleanups…</AppText>}
      {load.status === 'failed' && (
        <AppText variant="error" accessibilityRole="alert">
          {load.message}
        </AppText>
      )}
      {load.status === 'loaded' &&
        load.events.map((event) => <EventCard key={event.id} event={event} />)}
    </ScrollView>
  );
}

const styles = StyleSheet.create({
  screen: {
    backgroundColor: colors.page,
  },
  content: {
    gap: spacing.md,
    padding: spacing.md,
  },
  banner: {
    gap: spacing.xs,
    padding: spacing.lg,
    borderRadius: radius.card,
    backgroundColor: colors.banner,
  },
  bannerTitle: {
    color: colors.onBanner,
  },
  bannerTagline: {
    color: colors.onBannerAccent,
    fontSize: 18,
  },
});
  • style and contentContainerStyle on ScrollView are two different boxes. style is the scrolling window itself: its Sand background fills the screen. contentContainerStyle is the long strip of content that scrolls inside it: its padding and gap travel with the cards. (Padding on the window would stay put while the cards slide under it.)
  • The banner is a View with Deep Tide behind white and Seafoam text. White on Deep Tide (about 12:1), Seafoam on Deep Tide (about 8.8:1) and Ink on white (about 14.5:1) all pass the WCAG contrast ratio for small text, 4.5:1, with room to spare; the muted gray on white is about 5.9:1.
  • The title passes style={styles.bannerTitle}, which only changes the color: the size and weight still come from the title variant (the diagram in Style Arrays).
  • There are no hex codes left in the screen: every color comes from colors, every gap from spacing. spotsText from Lesson 1.3 is gone; the card says it better.

🏋️ Hands-on Exercises

Optional, but recommended: each one takes five to fifteen minutes.

🏋️ Exercise 1: Translate a CSS rule

The HQ's badges used this CSS: padding: 0.125rem 0.625rem; border-radius: 999px; font-size: 0.875rem; font-weight: 600;. Write it as one React Native style object (assume 1rem is 16). Which parts belong on a View and which on a Text?

💡 Hint

Multiply each rem by 16. The two-value padding becomes two properties. Then sort the properties: which ones are about the box, and which about the letters?

✅ Solution

{ paddingVertical: 2, paddingHorizontal: 10, borderRadius: 999, fontSize: 14, fontWeight: '600' }. On a phone, the box styles (paddingVertical, paddingHorizontal, borderRadius, and a background) usually go on a View and the text styles (fontSize, fontWeight, color) on the Text inside it. A Text can also take padding and a background itself, so a very simple badge can be a single styled Text. Lesson 2.2 builds the badge row.

🏋️ Exercise 2: Part of a line

In EventCard, make only the words "Meet at:" bold, and keep the meeting point itself in the muted style.

💡 Hint

Same trick as the spots number: a Text inside the AppText, with only the style that changes.

✅ Solution

<AppText variant="muted"><Text style={styles.strong}>Meet at:</Text> {event.meetingPoint}</AppText>. The nested Text inherits the muted color, the size and the line height, and adds only bold. Keep the space outside the inner Text, between </Text> and {event.meetingPoint}, so it is part of the line.

🏋️ Exercise 3: A new variant, and the type error that guards it

Add a 'small' variant (size 14, line height 20) to AppText. First add it only to the TextVariant type and run npx tsc --noEmit. Read the error, then finish the job and use the variant for the meeting-point line.

💡 Hint

The error points at styles[variant]. Which name in the type has no style yet?

✅ Solution

tsc reports error TS7053: Element implicitly has an 'any' type because expression of type 'TextVariant' can't be used to index type … and, on its second line, Property 'small' does not exist on type …, pointing at styles[variant] in AppText.tsx line 14. Add small: { fontSize: 14, lineHeight: 20 }, to the styles and the error is gone; then <AppText variant="small"> works. The type and the styles can never drift apart: that is the benefit of looking the variant up in a typed object instead of a chain of ifs. (Muted and small together? A variant is one choice; pass style={…} for the extra color, or make 'small' muted if that is what your design needs.)

🏋️ Exercise 4: Mark the full cleanups (Stretch)

Give the card of a full cleanup a thick Sunrise stripe on its left edge, using a style array on the card's View.

💡 Hint

borderLeftWidth and borderLeftColor override the card's border on one side. Add them in a second style and include it only when availability.kind === 'full'.

✅ Solution

A style cardFull: { borderLeftWidth: 6, borderLeftColor: brand.sunrise } (import brand as well as colors, or add a role such as colors.attention, which is the better long-term habit), and <View style={[styles.card, availability.kind === 'full' && styles.cardFull]}>. The color alone is not enough for everyone (some people cannot tell colors apart, and a screen reader cannot see it), which is why the words "Full: new sign-ups join the waiting list" stay on the card.

❓ Common Questions at This Stage

Are inline styles like style={{ padding: 16 }} bad?

No, they work and are fine for a one-off. The course prefers StyleSheet.create for named styles in one place and the stricter check on each style. Old articles also claim a big speed difference; in a current app that is not a reason to worry, and the React Compiler (on in Expo's template, Lesson 8.4) already memoizes much of what a component creates.

What about NativeWind, styled-components or other styling libraries?

They exist and some teams love them: NativeWind brings Tailwind's className strings to React Native, and others offer CSS-like syntax or design-system themes. Every one of them turns into the same style objects in the end, so what you learn here is what they do underneath. Learn the plain way first; pick a library later for a reason you can name.

How do I add a shadow to a card?

The card uses a border, which looks the same everywhere. React Native's types for this version also accept a CSS-like boxShadow string (for example boxShadow: '0 1px 3px rgba(0, 0, 0, 0.15)'), which the React Native documentation describes as supported on Android and iOS with the New Architecture; older tutorials use shadowColor/shadowOpacity (iOS) and elevation (Android). Shadows look different on each platform, so check them on a phone.

My phone is in dark mode, and the app stays light. Is something wrong?

No, that is expected for now. The theme has only light values today. Lesson 2.5 adds the dark palette and switches between them; because the screens use roles such as colors.page, none of them will need changing.

Why does the header bar say "index"?

Expo Router's Stack uses the route's file name as the title until you give it one. Lesson 4.1 is about routes and titles. The banner in the screen is part of the content, not the header bar.

📝 Lesson Summary

🎓 Key Takeaways

  • View is a box and Text shows text. Headings are Text with accessibilityRole="header"; every string lives in a Text (the web preview forgives a stray one, a phone does not)
  • Styles are objects: camelCase, numbers in density-independent pixels, percentages as strings, no shorthands, no classes, no CSS variables
  • StyleSheet.create names and type-checks styles, but padding: '16px', text styles on a View and lineHeight: 1.5 pass the check and fail quietly
  • No cascade: styles stay on their component; only a Text inside a Text inherits. A shared text component (AppText) replaces the page-wide font settings of the web
  • Style arrays merge left to right, later entries win, false is skipped: base, variant, then the caller's style
  • System fonts differ by platform, weights fall back to the closest available, and text grows with the person's settings: never fix the height of text
  • Colors and spacing live in src/theme/, named by their job, ready for dark mode in Lesson 2.5
