🌊 Shoreline API Reference

Everything the Shoreline Crew phone app can ask shoreline-api, what it answers, and how a phone, an emulator or the web preview reaches it.

🧭 About the API

shoreline-api is the course's mock back end, the same one the React + TypeScript course uses for Shoreline Crew HQ: the cleanups, sites, volunteers, sign-ups, debris logs and photos of Shoreline Crew, a fictional beach-cleanup group. It needs no install and has no dependencies: with Node.js 24 or newer, run node server.ts in its folder. The data lives in memory and is rebuilt around today's date each time it starts. Lessons never change the API; you only download it. This page describes it from the phone's point of view.

Download shoreline-api.zip (Lesson 1.2 sets it up). Its README.md is the short version of this page. For the words used here, see the Glossary; for error messages in the app, Troubleshooting.

▶️ Run It

Open a terminal in the folder, start the server and keep that terminal open while you work (a second terminal runs Metro). Stop it with Ctrl+C. Lesson 1.2.

cd shoreline-api
node server.ts

Expected output

Shoreline Crew API running at http://localhost:4000/api
  sample sign-in: maya.okafor@example.com (organizer) or theo.nakamura@example.com (volunteer), password shoreline-demo
Press Ctrl+C to stop.

For a phone on your Wi-Fi, start it with --host instead. It then also prints the address the phone uses (Lesson 5.1):

node server.ts --host

Expected output

Shoreline Crew API running at http://localhost:4000/api
  on your network:  http://192.168.1.42:4000/api
  sample sign-in: maya.okafor@example.com (organizer) or theo.nakamura@example.com (volunteer), password shoreline-demo
Press Ctrl+C to stop.

Your address will differ, and a computer with several network connections prints one line for each. Open http://localhost:4000/api in a browser for the list of every endpoint.

An unknown option stops the server with the list of valid ones. If the port is taken it says port 4000 is already in use. Is the API already running in another terminal? Or start it with --port=4100. In the folder, npm start runs node server.ts, npm run dev restarts it when a file changes (node --watch), and npm test runs the API's own tests; none of them needs npm install.

⚠️ --host shares the API with your network

--host lets every device on your Wi-Fi reach the API (that is the point). It is sample data with demo passwords, but use it on a network you trust and stop the API when you are done.

Windows with WSL, firewalls and guest Wi-Fi

Inside WSL 2 with its default networking (NAT), Linux gets its own private address, often starting 172., that only Windows can reach: the API's "on your network" line and Metro's QR code both show it, and a phone can reach neither. Lesson 5.1 gives three ways out: run Node in Windows (PowerShell, a Windows folder); turn on mirrored networking (Windows 11 22H2 or newer) with networkingMode=mirrored under [wsl2] in %UserProfile%\.wslconfig, then wsl --shutdown; or use the Android emulator on Windows, which reaches your computer at 10.0.2.2 whatever WSL does. wslinfo --networking-mode says which mode you have. A firewall may also need to allow Node.js (ports 8081 for Metro and 4000 for the API) on private networks, and guest, school or café Wi-Fi often keeps devices apart (a phone hotspot gets around it). See Troubleshooting: WSL.

Plain http works in Expo Go and development builds. Release builds refuse it (Android) or allow only local addresses (iPhone); Lesson 9.1 allows it for the preview variant only.

🌐 CORS and Pictures That Follow

CORS is a browser rule, so it matters only in the web preview (Lesson 5.1). shoreline-api adds Access-Control-Allow-Origin for pages on http://localhost, http://127.0.0.1 or http://[::1] on any port, plus the origins named with --cors, and for those it also sends Access-Control-Expose-Headers: X-Total-Count, X-Total-Pages, Link, Location, so the page can read the pagination headers. It answers every OPTIONS preflight with 204 (methods GET, POST, PUT, PATCH, DELETE, OPTIONS, headers Authorization, Content-Type).

The request comes fromOrigin sentAllow-Origin in the answerResult

Pictures follow the address. The API builds each site picture's URL (site.image.url) and each photo's url from the address the request arrived at. Asked at http://192.168.1.42:4000, it answers http://192.168.1.42:4000/images/sites/pelican-point.jpg; asked at localhost, http://localhost:4000/images/…. So every device gets picture addresses it can open (Lesson 2.3 shows them). The site pictures are served with Cache-Control: max-age=3600.

🐢 Slow and Failing Answers

Phones live on slow and dropped connections. Two server options change every answer; two query parameters change one request without a restart. To practice being offline, stop the API (or turn on airplane mode).

SwitchScopeEffect
--latency=MS or MIN-MAXevery requestwaits before answering. /api/health and /api/_reset are never slowed down.
--fail-rate=0-1every requestthat share answers 500 with Simulated server error (the server was started with --fail-rate). Health and reset never fail.
?_delay=2000this requestwaits that many milliseconds (at most 10000) instead of the --latency wait
?_status=500this requestanswers that status (any 400 to 599) with the usual error body, such as { "error": "server_error", "message": "Simulated 500 response (the _status parameter)." }; a 401 gets unauthorized, a 404 not_found, and so on

The app's answers to these: loading and failed states in Lesson 3.1, retries and the online manager in Lesson 5.2, the debris-log queue in Lesson 5.5.

🧠 Memory, Restarts and the 401 on Public Endpoints

Everything the API knows lives in memory. Restarting it (or POST /api/_reset) rebuilds the sample data and forgets everything since: your sign-ups and cancellations, check-ins, debris logs, uploaded photos, and every sign-in token except the two test tokens.

⚠️ An old token gets 401 even where no token is needed

The API checks the token before it looks at the address. A request carrying a token it does not know answers 401 Your session has ended. Sign in again., even GET /api/events, GET /api/sites or POST /api/auth/sign-out, because the request claimed to be someone. The same request without a token gets 200. A phone meets this far more than a web page: its secure storage still holds the token from before the restart (Lesson 4.3).

  • The client forgets the session. In request(), a 401 to a request that carried a token calls setSession(null), and describeError says Your sign-in has ended. Sign in again. (Lesson 4.3).
  • One place tells the volunteer. The query cache's error handler marks the sign-in as ended wherever the 401 happened, and the public lists fetch again as a guest (Lesson 5.2).
  • Queued work after a restart. A queued debris log whose photoIds name photos from before the restart is refused with 400 (fieldErrors.photoIds: Upload each photo first and send the ids it returned.), and a clientId the API saw before the restart counts as new again (Lesson 5.5, Lesson 6.2).
  • The sample data moves with the calendar. It is built around today in the group's time zone (America/Los_Angeles), so "today's cleanup" is always today. See Troubleshooting when your changes seem to vanish.

// src/api/client.ts (the finished app): the photo itself is the body
export async function postPhoto(photo: Blob, contentType: string): Promise<Photo> {
  const response = await request('/photos', {
    method: 'POST',
    headers: { 'Content-Type': contentType },
    body: photo,
  });
  const data: unknown = await response.json();
  if (!isPhoto(data)) {
    throw new Error('Unexpected data from POST /api/photos');
  }
  return data;
}

📄 Lists and Pages

GET /api/events and GET /api/volunteers are paged. They take page (from 1) and perPage (1 to 50, default 10), answer a JSON array of that page's items, and say the rest in headers:

HeaderSays
X-Total-Counthow many items match, on all pages
X-Total-Pageshow many pages there are (at least 1, even for an empty list)
Linkthe addresses of the first, prev, next and last pages (prev and next only when they exist)

A page past the end answers an empty array, not an error; a perPage over 50 or a page of 0 is 400. Lesson 3.2 asks for the second page of upcoming cleanups, five at a time:

curl -s -D - -o /dev/null "http://localhost:4000/api/events?when=upcoming&page=2&perPage=5"

Expected output

HTTP/1.1 200 OK
cache-control: no-store
content-type: application/json; charset=utf-8
link: <http://localhost:4000/api/events?when=upcoming&page=1&perPage=5>; rel="first", <http://localhost:4000/api/events?when=upcoming&page=1&perPage=5>; rel="prev", <http://localhost:4000/api/events?when=upcoming&page=2&perPage=5>; rel="last"

x-total-count: 8
x-total-pages: 2
...

Header names come out in lowercase, which HTTP allows (x-total-pages is X-Total-Pages). On Windows PowerShell, type curl.exe and NUL instead of /dev/null.

The app's readPage returns a Page<T>: the items plus page and perPage (read from the request's address) and total and totalPages (from the headers). The Cleanups list asks for perPage=5 and loads the next page with onEndReached while page < totalPages, by hand in Lesson 3.2 and with useInfiniteQuery in Lesson 5.2. The other lists (/api/sites, /api/me/signups, logs, the roster) are plain arrays with no paging headers.

📅 Cleanups

A volunteer (or a guest) sees only scheduled, completed and cancelled cleanups; a draft answers 404 No cleanup event with that id., exactly like an id that does not exist (Lesson 4.1 handles that 404). A cleanup has id, title, siteId, status, date (YYYY-MM-DD), startTime and endTime (HH:MM, the group's local time), capacity, spotsTaken (confirmed plus attended sign-ups), meetingPoint, description, suppliesProvided, leadOrganizerId, createdAt and updatedAt (ISO timestamps in UTC). GET /api/events/:id adds the whole site (with latitude and longitude, used by the map in Lesson 6.3), and checkInCode for organizers only.

Query parameterEffect
when=upcoming / when=pasttoday or later / before today (the API's today)
qwords in the title, description or site name (all must match)
status, siteId, from, toone status; one site; dates from and to (YYYY-MM-DD)
sortdate (default, soonest first), -date, title
updatedSinceonly cleanups whose updatedAt is later than this ISO time

A wrong value is 400 with a message per parameter, such as fieldErrors.when: when must be upcoming or past.

ℹ️ updatedSince: what it covers

A cleanup's updatedAt changes only when an organizer edits it (PATCH) or reports its impact (PUT …/impact). Sign-ups change spotsTaken without touching updatedAt, so a delta sync with updatedSince misses them, and a deleted draft simply stops appearing. Shoreline Crew's Cleanups list therefore does not use it: Lesson 5.5 explains why in its Common Questions and leaves a delta sync to its Bonus Challenge.

🙋 Sign-ups and Check-in

A sign-up has id, eventId, volunteerId, status (confirmed, waitlisted, cancelled, attended or no-show), note, createdAt and checkedInAt (a timestamp or null). Lesson 5.2 uses three endpoints:

RequestThe API decides
GET /api/me/signupsyour sign-ups, each with its cleanup (event), the latest cleanup first, canceled ones included
POST /api/events/:id/signups (body {}, or { "note": "…" } up to 280 characters)201 with confirmed while spots are left, else waitlisted. 409 You are already signed up for this cleanup. PATCH /api/signups/:id with { "status": "cancelled" }200 with the sign-up. If it held a spot, the first person on the waiting list gets it. A volunteer may only cancel (any other status is 403 Volunteers can only cancel their own sign-up.) and only their own (someone else's is 404)

A second sign-up sent by a retry is harmless: the API refuses it with 409, which is why Lesson 5.2 does not need a clientId for sign-ups.

Check-in with the organizer's code

POST /api/events/:id/check-in with { "code": "6544" } proves you were there (Lesson 6.3). The organizer reads the code from the cleanup (organizers get checkInCode); nobody else sees it. The answer is your sign-up, now attended with checkedInAt. The API checks, in this order:

ProblemAnswer
No sign-up, a canceled one, or a waitlisted one409 You need a confirmed spot to check in.
Not the cleanup's date (the API's today), or the cleanup is not scheduled409 Check-in opens on the day of the cleanup.
The code does not match400 with fieldErrors.code: That code does not match. Ask the organizer for today's code.
All good200, the sign-up as attended

Check-in is idempotent: a second check-in with the right code leaves the sign-up attended and keeps the first checkedInAt. That makes a retry safe, so Shoreline Crew lets a check-in pressed without signal wait in memory and send when the connection returns, but never queues it for later, because a late check-in can only get the "day of the cleanup" 409 (Lesson 6.3).

curl -i -X POST http://localhost:4000/api/events/e17/check-in -H "Authorization: Bearer dev-volunteer" -H "Content-Type: application/json" -d "{\"code\":\"6544\"}"

🧾 Debris Logs

A debris log is what one volunteer recorded at a cleanup, sent from the phone, possibly much later. POST /api/events/:id/logs takes a NewCleanupLog:

export interface NewCleanupLog {
  clientId: string        // made on the phone, 8 to 64 characters, once per log
  items: DebrisCount[]    // { category, count }: a known category, a whole count 0 to 100000
  bags: number            // a whole number 0 to 500
  weightKg: number        // 0 to 5000
  note?: string           // up to 500 characters
  photoIds?: string[]     // ids from POST /api/photos, uploaded first
  recordedAt: Timestamp   // when the volunteer recorded it (ISO)
}

The saved CleanupLog adds id, eventId, volunteerId and createdAt. The ten debris categories are plastic-bottles, plastic-bags, food-wrappers, bottle-caps, cigarette-butts, fishing-gear, glass, metal, foam and other (labels in GET /api/meta).

The phone makes the clientId (with expo-crypto's randomUUID()) when the form opens, so a resend after a dropped connection carries the same id and the season's totals never count a log twice (Lesson 5.4). The queue that resends it, and the table above, are Lesson 5.5's. The API recognizes a resend by your sign-in plus the clientId, and checks it before the spot and date rules.

GET /api/events/:id/logs lists your own logs for one cleanup (an organizer gets everyone's), as an array. The logbook fills itself from it for every cleanup you held a spot at (Lesson 5.3).

📷 Photos

POST /api/photos (signed in) accepts a photo in either of two forms (Lesson 6.2):

  • The image itself as the body, with its type in Content-Type (image/jpeg, image/png or image/webp). This is what Shoreline Crew sends: on a phone an expo-file-system File (a Blob), in the web preview the browser's Blob.
  • A multipart/form-data form with the image in a field named photo. This is what the HQ's browser form sends.

🚫 The old { uri, name, type } form part fails on SDK 58

Older answers append { uri, name, type } to a FormData. In Expo SDK 58 the global fetch on a phone is expo/fetch, which sends Blobs, not file addresses: TypeScript rejects the call (No overload matches this call.), and forced through with a cast, the fetch throws Unsupported FormDataPart implementation, which the app reports as "Could not reach the server". Send the Blob as the body instead (Lesson 6.2).

AnswerWhen
201 with { id, url, contentType, bytes, uploadedBy, createdAt } and a Location headersaved; put the id in the log's photoIds
415 unsupported_media_typePhotos must be JPEG, PNG or WebP images. (a HEIC or GIF, for example)
413 payload_too_largePhotos must be 5 MB or smaller.
400an empty body (fieldErrors.photo: The image is empty.), or a multipart form without a photo file
 
curl -i -X POST http://localhost:4000/api/photos -H "Authorization: Bearer dev-volunteer" -H "Content-Type: image/jpeg" --data-binary @photo.jpg

GET /api/photos/:id serves the photo back to anyone, with no sign-in. Its url is built from the address you used, like the site pictures. Photos live in the API's memory: restart it and they are gone. Upload the photos before the log that names them, and save each id as it arrives, so a retry never uploads a photo twice (Lesson 6.2).

⚠️ Errors

Every error answer has the same JSON body: { error, message, fieldErrors? }. fieldErrors appears only on a 400 validation_failed and lists messages per field. The app's ApiError carries all three; describeError turns them into words for the screen (Lesson 1.3).

{
  "error": "validation_failed",
  "message": "Some fields need attention.",
  "fieldErrors": {
    "code": ["That code does not match. Ask the organizer for today's code."]
  }
}

🧪 In Tests (MSW)

shoreline-api ships msw/handlers.ts, which runs the API's own core/api.ts inside Mock Service Worker, so tests get the same data, rules and headers with no server. Shoreline Crew copies core/ and msw/ into src/mocks/ unchanged. Because React Native's global types disagree with a few of its lines, tsconfig.json excludes src/mocks/ and src/test/server.ts loads the handlers with a typed require(); Node's fetch is put back in place of expo/fetch for the tests (Lesson 8.2). Its core/types.ts is the app's src/api/types.ts, copied byte for byte (Lesson 1.3).
