🔐 Lesson 4.3: Sign-In Flows and Protected Routes

A volunteer opens Shoreline Crew on the beach at seven in the morning, gloves already on. The app should know who they are without asking for a password again, it should never leave that password or its token lying where another app can read it, and it should quietly ask them to sign in again when the server no longer recognizes them. Today you build exactly that: a real sign-in against shoreline-api, a session locked in the phone's secure storage, screens that exist only for the right people, and a clean way out.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Store a session token in the phone's secure storage with expo-secure-store, explain why it is async, and say what the web preview does instead
  • Restore a saved session at startup while the splash screen stays up, so the first screen already knows who is signed in
  • Guard routes with Expo Router's Stack.Protected, and predict where the app goes when a guard changes or someone opens a guarded address
  • Build a sign-in modal that shows the API's own error messages, never keeps a failed password, and closes back to the screen that opened it
  • Sign out, and handle a 401 from the API by forgetting the session and asking the volunteer to sign in again

  • 🛠️ You will build Shoreline Crew's sign-in: a Sign in modal for guests, a session kept in secure storage and restored at startup, a Profile tab that shows who you are and signs you out, a My cleanups tab that asks guests to sign in, and a sign-in that ends gracefully when the API forgets it
  • 🧩 Stack Expo SDK 58 (React Native 0.88, React 19.3), Expo Router 58.0.31 (Stack.Protected), expo-secure-store 58.0.3, react-native-web 0.21 for the web preview (the versions this lesson was checked with)

👋 Welcome: Who Is Holding the Phone?

Since Lesson 4.2, Shoreline Crew has two tabs that say "coming soon": My cleanups and Profile both need to know who the volunteer is. shoreline-api already knows how to answer that. You met its sign-in in the React + TypeScript course: POST /api/auth/sign-in with an email and a password returns a token and the user, and every later request that carries Authorization: Bearer <token> is made as that person. By the end of today:

  • A Sign in modal for guests, opened from Profile or My cleanups, that shows the API's own words when something is wrong ("Email or password is incorrect.") and closes back to where you were.
  • A session that survives a restart. On a phone, the token goes into secure storage (the iOS Keychain, or storage encrypted with the Android Keystore), and the app reads it back while the splash screen is still up.
  • A guarded route. The sign-in screen exists only while nobody is signed in, using Expo Router's Stack.Protected.
  • Profile and My cleanups that know you: your name, email and role, a Sign out button, and for guests, a clear way to sign in.
  • A graceful ending. shoreline-api keeps its sessions in memory, so restarting it forgets every token. When the API answers 401, the app forgets the session too and says "Your sign-in has ended. Sign in again."

Why it matters for your work: nearly every app you will be paid to build has accounts, and sign-in is where security reviews, app store reviewers and angry users all look first. A token in the wrong place, a password kept in memory after a failed try, or an app that crashes when a session expires are classic bugs. Getting the shape right once gives you a pattern you can reuse in every app.

Why it matters for the volunteers: phones are shared, lost and handed around at a cleanup. The session has to be hard for anything else on the phone to read, and easy for the volunteer to end with one tap.

The web version of this was Lesson 6.3 of the React + TypeScript course: the HQ kept its session in sessionStorage, read it with useSyncExternalStore, sent it with every request, and forgot it on a 401. Most of that code carries over unchanged. What changes on a phone is where the session is stored, the fact that reading it is async, and how screens are guarded.

🗝️ Where a Session Lives on a Phone

A phone app has three places to keep data between launches, and Lesson 5.3 compares them in depth. For a sign-in token, only one is right:

PlaceWhat it isA token there?
expo-secure-storeThe iOS Keychain; on Android, values encrypted with a key from the Android Keystore. Strings only, small values, asyncYes. This is what it is for
AsyncStorageAn unencrypted key-value file in the app's folder (Lesson 5.3)No: fine for a theme choice, not for secrets
An EXPO_PUBLIC_ variableText copied into the app's JavaScript when it is built (Lesson 1.3)Never: anyone who has the app can read it

Compared with the HQ, three things change:

  • It is async. sessionStorage.getItem() answered at once; SecureStore.getItemAsync() returns a Promise, because the operating system has to unlock and decrypt the value. So the app cannot know who is signed in during its very first render. Shoreline Crew keeps the splash screen up until the answer arrives (Step 4), the same way it already waits for its fonts.
  • It survives a restart. sessionStorage was gone when the browser tab closed. Secure storage keeps the token until the app deletes it or the app is removed (the Expo documentation notes that on iOS, Keychain items can even outlive an uninstall). That is why Sign out must delete it.
  • Strings only, and keys with simple names. The session is an object, so it is saved as JSON; the key, shoreline-crew-session, may contain only letters, numbers, ., - and _ (the library checks).

What the web preview does

A browser has no keychain. The course measured what expo-secure-store 58.0.3 does in the web preview, with a small test screen that tries each call:

So the library tells you honestly that it is not available, and fails if you use it anyway. Shoreline Crew asks first: when isAvailableAsync() is false, the session lives in memory only. In the web preview that means reloading the page signs you out. That is the safe choice: the obvious alternative, localStorage, is readable by any script on the page, and the web preview is only a development tool for this app. On a phone, the session is saved and restored.

💡 Mental model: the wristband and the lockbox

At a big cleanup, the crew leader checks your name once and gives you a wristband: that is the token, and showing it gets you gear without signing in again. Overnight, you keep it in the crew van's lockbox, which only you can open: that is secure storage. The leader's list of wristbands lives on a clipboard, and if the clipboard blows away (the API restarts), your wristband stops meaning anything. Then you go back to the sign-in table, and you throw the old band away.

🛑 Never store the password

The app sends the password once, gets a token back, and forgets the password at once (the screen even empties the field after a try that did not work). Only the token is stored. A token can be ended by the server or by signing out; a stolen password works everywhere the volunteer reused it.

🚧 Protected Routes

In the HQ, a route loader checked the session before a page rendered and threw a redirect(). Expo Router has no loaders for this; instead, a layout says which screens exist for the current user, with Stack.Protected:

import { Stack } from 'expo-router';

import { useSession } from '@/hooks/useSession';

// Two guards side by side: screens for signed-in volunteers, and screens for guests
export function GuardedStack() {
  const session = useSession();
  return (
    <Stack>
      <Stack.Protected guard={session !== null}>
        <Stack.Screen name="log/[id]" options={{ presentation: 'modal', title: 'New debris log' }} />
      </Stack.Protected>
      <Stack.Protected guard={session === null}>
        <Stack.Screen name="sign-in" options={{ presentation: 'modal', title: 'Sign in' }} />
      </Stack.Protected>
    </Stack>
  );
}

That sketch type-checks in the project. guard is a boolean: while it is true, the screens inside are ordinary screens; while it is false, they are taken out. The second group is what Shoreline Crew uses today. The first shows where Lesson 5.4's debris log will go: only signed-in volunteers record what the crew collected. The Expo Router source and the course's measurements in the web preview give the rules:

SituationWhat happens
Someone opens a guarded screen's address (a link, a typed address) while its guard is falseExpo Router redirects to the navigator's anchor: its first screen, here the tabs, so the Cleanups tab (measured: a link to /sign-in on a signed-in Profile opened Cleanups)

Notice that the guard does the "you are signed in now, go away" part of a sign-in flow for you: nothing in the app can open the sign-in screen for a signed-in volunteer. But it does not know where the volunteer came from, so the sign-in screen closes itself first and only then switches the app to signed in (Step 5 explains the order).

The other way: Redirect in a screen

Before Stack.Protected existed (it arrived in SDK 53), apps redirected from inside a screen or layout, and you will meet it in older code and articles. It still works, and it type-checks here:

import { Redirect } from 'expo-router';

import { AppText } from '@/components/AppText';
import { useSession } from '@/hooks/useSession';

// The other way: a screen that sends guests elsewhere itself, every time it is drawn
export function MembersOnly() {
  const session = useSession();
  if (session === null) {
    return <Redirect href="/sign-in" />;
  }
  return <AppText>Hello, {session.user.name}</AppText>;
}

The difference: with <Redirect>, the screen still exists, and every screen has to remember to check. With Stack.Protected, one place in the layout decides, and a guarded screen cannot be reached at all. Prefer the guard for whole screens; <Redirect> and router.replace() are still the tools when code decides where to go.

⚠️ A guard hides screens; the API protects data

Stack.Protected decides what the app shows. It is not security: anyone can call shoreline-api with curl. The API's 401 and 403 answers are what protect volunteers' data, exactly as in the HQ. The app's guard is about a sensible experience.

⏳ When the API Forgets You

shoreline-api keeps its sessions in memory. Stop it with Ctrl+C and start it again, and every token it handed out means nothing. Real APIs end sessions too: they expire, a password changes, an administrator signs someone out. A phone app meets this more often than a website, because its session lasts for weeks, not for one browser tab.

The API's answer to a token it does not know is the same everywhere: 401 with "Your session has ended. Sign in again." It sends that even for public addresses like the cleanup list, because the request claimed to be someone. Shoreline Crew copies the HQ's rule into request(): if a request that carried a token gets a 401, the client forgets the session. Every screen that reads the session redraws as signed out, and secure storage is cleared too.

One more question is when the app finds out. Profile asks GET /api/auth/me each time it comes into view, with useFocusEffect (Lesson 4.2's FAQ named it): a tab switch or a return to the app is enough. If that check cannot reach the API at all (no signal on the beach), Profile keeps the volunteer signed in and checks next time: only a 401 means the sign-in is really over. Lesson 5.2 replaces this hand-written check with TanStack Query, which refreshes on focus by itself.

⚠️ Common Mistakes

Sign-in bugs often look like something else: a page that renders twice, a warning about files, a modal that "goes to the wrong place". Each one below was produced on purpose in the finished project and is quoted the way the tools printed it. Reading the message closely is how you get from the symptom to the cause.

⚠️ "Missing getServerSnapshot"

Write useSession the way the HQ did, with two functions: useSyncExternalStore(onSessionChange, readSession). It type-checks. Open the web preview and Metro's terminal shows:

Expected output

...
λ  ERROR  SSR streaming render error: Error: Missing getServerSnapshot, which is required for server-rendered content. Will revert to client rendering.
...
Web  ERROR  [Error: Switched to client rendering because the server rendering errored:
Missing getServerSnapshot, which is required for server-rendered content. Will revert to client rendering.]
...

The web preview draws each page on a server first (the λ line), and on a server there is no session to read, so React needs a third function that says what the server should assume. The page still appeared, because React gave up on the server's version and drew it again in the browser, but every page load hits this error. You met the same fix for the color scheme in Lesson 2.5: pass () => null, "nobody is signed in on the server". Phones never call it.

⚠️ Two files that import each other

A tempting design: the client calls signOut() from session.ts on a 401, while session.ts already imports from the client. tsc and ESLint say nothing, but Metro does:

Expected output

...
Require cycle: src/api/client.ts -> src/auth/session.ts -> src/api/client.ts
...
Web  WARN  Require cycle: src/auth/session.ts -> src/api/client.ts -> src/auth/session.ts
Require cycles are allowed, but can result in uninitialized values. Consider refactoring to remove the need for a cycle.
...

In a cycle, one of the two files runs while the other is only half loaded, so a value it imports can still be undefined. Shoreline Crew keeps the arrows pointing one way: the client knows nothing about secure storage, and session.ts listens to the client (Step 3).

⚠️ Signed in, but on the wrong tab

Switch the app to signed in first and close the modal afterwards (for example, await a helper that sets the session, then call router.back()). The course measured it: opened from Profile, the volunteer landed on the Cleanups tab. The guard removed the sign-in screen before back() ran, and Expo Router redirected to the anchor. Close first, then set the session.

⚠️ "'session' is possibly 'null'"

A session is either there or not, and TypeScript makes you say which. In Profile, write session.token instead of session?.token:

Expected output

src/app/(tabs)/profile.tsx:14:17 - error TS18047: 'session' is possibly 'null'.

14   const token = session.token;
                   ~~~~~~~


Found 1 error in src/app/(tabs)/profile.tsx:14

This is TypeScript doing its job: a guest has no token. Check for null first, or use ?. when "no token" is a fine answer, as Profile does.

⚠️ Calling SecureStore without asking

Calling SecureStore.getItemAsync() in the web preview rejects with the TypeError from the table in Where a Session Lives. It is easy to miss because a phone never shows it. Ask isAvailableAsync() first, and decide what the app does without secure storage.

Step 3: A copy on the phone, and a hook (15 min)

This is the rewritten part. Create the folder src/auth and in it session.ts:

shoreline-crew/src/auth/session.ts
// Signing out, and the copy of the session kept on the phone (rewritten: the HQ kept its copy in
// the browser's session storage, which a phone does not have)
import * as SecureStore from 'expo-secure-store';

import {
  isSignInResponse,
  onSessionChange,
  postSignOut,
  readSession,
  setSession,
} from '@/api/client';

// The name of the saved session in secure storage (letters, numbers, ".", "-" and "_" only)
const sessionKey = 'shoreline-crew-session';

/**
 * Start with the session saved on this phone, and keep the saved copy up to date from then on.
 * Call it once, when the app starts. It never fails: if anything goes wrong, nobody is signed in.
 */
export async function loadSession(): Promise<void> {
  // The phone's secure storage: the iOS Keychain, or values encrypted with the Android Keystore.
  // The web preview has none, so there the session lives in memory only.
  if (!(await SecureStore.isAvailableAsync())) {
    return;
  }
  try {
    const saved = await SecureStore.getItemAsync(sessionKey);
    const value: unknown = saved === null ? null : JSON.parse(saved);
    setSession(isSignInResponse(value) ? value : null);
  } catch (error) {
    console.warn('Could not read the saved session', error);
  }
  // Every change from now on (signing in, signing out, a session the API forgot) is saved too
  onSessionChange(saveCopy);
}

function saveCopy() {
  const session = readSession();
  const saving =
    session === null
      ? SecureStore.deleteItemAsync(sessionKey)
      : SecureStore.setItemAsync(sessionKey, JSON.stringify(session));
  saving.catch((error: unknown) => console.warn('Could not save the session', error));
}

/** Sign out: tell the API, and forget the session on this phone at once */
export function signOut(): void {
  // The request takes the token with it as it starts; then the phone forgets the session
  postSignOut().catch(() => {
    // Nothing to do: the API forgets its sessions when it restarts anyway
  });
  setSession(null);
}
  • loadSession() runs once at startup. It asks whether secure storage exists, reads the saved JSON, and checks it with isSignInResponse before trusting it: data saved by an older version of the app, or damaged, means nobody is signed in rather than a crash. It catches every error, so the app always starts.
  • One listener keeps the copy in step. After loading, onSessionChange(saveCopy) writes every change: a sign-in from Step 5, a sign-out, and a session the client forgot after a 401. No code path can forget to update the phone's copy. (In the web preview, loadSession returns before adding it: memory only.)
  • The arrows point one way. session.ts imports from the client; the client never imports session.ts (Common Mistakes shows what Metro says otherwise).
  • signOut() is the HQ's: the request takes the token with it as it starts, then the session is forgotten at once, without waiting for the network. If the request fails, there is nothing to do: the API forgets its sessions when it restarts anyway.

Then the hook that components use. Create src/hooks/useSession.ts:

shoreline-crew/src/hooks/useSession.ts
import { useSyncExternalStore } from 'react';

import { onSessionChange, readSession, type Session } from '@/api/client';

/** Who is signed in (null: nobody). Components that use it re-render on every sign-in and sign-out. */
export function useSession(): Session | null {
  // The third function is for the web preview's server, which draws pages before any sign-in
  return useSyncExternalStore(onSessionChange, readSession, () => null);
}

It is the HQ's useSyncExternalStore(onSessionChange, readSession), plus the third function the web preview's server needs (the first Common Mistake shows the error without it). The HQ wrapped it in a context provider; Shoreline Crew does not need one, because any component can call the hook directly and the store lives outside React.

Now the screen. Create src/app/sign-in.tsx:

shoreline-crew/src/app/sign-in.tsx
import { router } from 'expo-router';
import { useState } from 'react';

import { ApiError, describeError, postSignIn, setSession } from '@/api/client';
import { AppText } from '@/components/AppText';
import { Button } from '@/components/Button';
import { FormField } from '@/components/FormField';
import { Screen } from '@/components/Screen';

// Why the last try did not work: one message for the form, and one per field the API named
type Problem = { message: string; fields: Record<string, string[]> };

// The sign-in modal. It exists only while nobody is signed in (Stack.Protected in _layout.tsx).
export default function SignInScreen() {
  const [email, setEmail] = useState('');
  const [password, setPassword] = useState('');
  const [sending, setSending] = useState(false);
  const [problem, setProblem] = useState<Problem | null>(null);

  async function submit() {
    setSending(true);
    setProblem(null);
    try {
      const session = await postSignIn({ email: email.trim(), password });
      // Close the modal first, back to the screen that opened it. Then switch to signed in: the
      // guard takes this screen away at once, and if it were still open, you would land on the
      // first tab instead.
      if (router.canGoBack()) {
        router.back();
      }
      setSession(session);
    } catch (error) {
      setPassword(''); // never keep a password around after a try that did not work
      setProblem(
        // 400: fields to fix; 401: wrong email or password. The API's own words fit both.
        error instanceof ApiError && (error.status === 400 || error.status === 401)
          ? { message: error.message, fields: error.fieldErrors ?? {} }
          : { message: describeError(error), fields: {} },
      );
      setSending(false);
    }
  }

  return (
    <Screen scroll edges={['bottom', 'left', 'right']}>
      <AppText>
        Sign in with your Shoreline Crew account to sign up for cleanups and see your own.
      </AppText>
      {problem !== null && (
        <AppText variant="error" accessibilityRole="alert">
          {problem.message}
        </AppText>
      )}
      <FormField
        label="Email"
        value={email}
        onChangeText={setEmail}
        error={problem?.fields.email?.join(' ')}
        keyboardType="email-address" // the keyboard with @ and .
        autoComplete="email"
        autoCapitalize="none"
        autoCorrect={false}
      />
      <FormField
        label="Password"
        value={password}
        onChangeText={setPassword}
        error={problem?.fields.password?.join(' ')}
        secureTextEntry // dots instead of letters
        autoComplete="current-password" // password managers offer the saved one
        autoCapitalize="none"
      />
      <Button
        label={sending ? 'Signing in…' : 'Sign in'}
        variant="primary"
        disabled={sending}
        onPress={submit}
      />
    </Screen>
  );
}
  • The keyboard fits the field. keyboardType="email-address" shows the keyboard with @ and . (in the web preview it becomes type="email": measured); autoCapitalize="none" and autoCorrect={false} stop the phone from "fixing" an address. secureTextEntry shows dots (Lesson 2.4 promised it), and the autoComplete values let password managers offer the saved login. Lesson 5.4 adds the return-key chain from Email to Password.
  • The API's words. A 400 comes with fieldErrors per field ("Enter an email address."), a wrong password is a 401 ("Email or password is incorrect."): the screen shows those messages, which describe the problem better than describeError's 401 text ("Your sign-in has ended"), written for a different situation. Anything else, such as the API not running, goes through describeError as usual.
  • The password is emptied after every try that did not work, as in the HQ. The email stays, so a typo in the password costs one field, not two.
  • Close first, then sign in. When the API says yes, the screen goes back to whatever opened it, and only then sets the session. The order matters: the moment the session is set, the guard takes the sign-in screen away, and if it were still open, Expo Router would send the volunteer to the first tab (measured; the third Common Mistake). Opened from its address with nothing underneath, canGoBack() is false, and the guard's redirect to the Cleanups tab is exactly right.

shoreline-crew/src/app/(tabs)/profile.tsx
import { Link, useFocusEffect } from 'expo-router';
import { useCallback, useState } from 'react';

import { ApiError, getMe } from '@/api/client';
import { AppText } from '@/components/AppText';
import { Button } from '@/components/Button';
import { Screen } from '@/components/Screen';
import { signOut } from '@/auth/session';
import { useSession } from '@/hooks/useSession';

// Profile: who you are, signing in and out, and the beach safety guide
export default function ProfileScreen() {
  const session = useSession();
  const token = session?.token;
  // true when the API said this phone's sign-in has ended (it restarted, or the session expired)
  const [ended, setEnded] = useState(false);

  // Each time Profile comes into view, ask the API whether it still knows this sign-in.
  // A 401 makes the client forget the session, and this screen shows the signed-out view.
  useFocusEffect(
    useCallback(() => {
      if (token === undefined) {
        return;
      }
      const controller = new AbortController();
      getMe(controller.signal).catch((error: unknown) => {
        if (error instanceof ApiError && error.status === 401) {
          setEnded(true);
        }
        // Anything else (no signal, the API not running): stay signed in and check next time
      });
      return () => controller.abort();
    }, [token]),
  );

  function signOutNow() {
    setEnded(false);
    signOut();
  }

  return (
    <Screen scroll edges={['left', 'right']}>
      {session === null ? (
        <>
          <AppText variant="heading" accessibilityRole="header">
            Not signed in
          </AppText>
          {ended && (
            <AppText variant="error" accessibilityRole="alert">
              Your sign-in has ended. Sign in again.
            </AppText>
          )}
          <AppText>Sign in to sign up for cleanups and to see the ones you signed up for.</AppText>
          {/* The sign-in modal; it closes by itself once you are signed in */}
          <Link href="/sign-in" asChild>
            <Button label="Sign in" variant="primary" />
          </Link>
        </>
      ) : (
        <>
          <AppText variant="heading" accessibilityRole="header">
            {session.user.name}
          </AppText>
          <AppText variant="muted">{session.user.email}</AppText>
          <AppText>
            Signed in as {session.user.role === 'organizer' ? 'an organizer' : 'a volunteer'}.
          </AppText>
          <Button label="Sign out" onPress={signOutNow} />
        </>
      )}
      <AppText variant="heading" accessibilityRole="header">
        Before every cleanup
      </AppText>
      <AppText>What to bring, and how to stay safe on the beach.</AppText>
      {/* A modal: it slides up over the tabs, and closes back to this tab */}
      <Link href="/before-you-go" asChild>
        <Button label="Before you go" />
      </Link>
    </Screen>
  );
}
  • useSession() decides which face to draw, and redraws the moment someone signs in or out, or the client forgets the session.
  • useFocusEffect runs its function each time Profile comes into view, and runs the cleanup (abort the request) when it leaves. It takes a function wrapped in useCallback, so the check runs again only when the token changes, not on every render. With no token there is nothing to check.
  • ended remembers that the last check got a 401, so the signed-out face can say why. Signing out on purpose clears it, so a volunteer who signs out is not told their sign-in "ended".
  • The Sign in button is a Link to /sign-in, like Before you go: the route exists only for guests, and only guests see this button.

❓ Common Questions at This Stage

How safe is a token in secure storage?

Much safer than anywhere else the app can write: according to the Expo and platform documentation, the Keychain and Keystore encrypt the value, tie it to your app, and on many phones keep the key in dedicated hardware. It is not magic: a phone that is rooted or jailbroken, or someone with the unlocked phone in hand, is a different threat. That is why sign-out deletes the token and why the API can end sessions on its side.

Where are "forgot password", "create an account" and refresh tokens?

Not in shoreline-api, so not in this course: volunteers get accounts from the crew, and a session simply lasts until the API forgets it. Real APIs often hand out a short-lived access token with a longer-lived refresh token, and the app quietly asks for a new access token when it gets a 401 before giving up. The shape you built (one place that reads the token, one place that reacts to 401, one saved copy) is where that logic would go.

Can the app ask for Face ID or a fingerprint?

Yes: setItemAsync and getItemAsync take a requireAuthentication option, and the config plugin from Step 1 accepts a faceIDPermission text for iOS. The documentation lists conditions (biometrics enrolled, the prompt can be cancelled or fail, and Face ID on iOS needs that permission text in your own build). It suits a banking app more than a volunteer app; Going Further asks you to weigh it.

Could I hide the My cleanups tab from guests instead?

You could: the JavaScript tabs have Tabs.Protected too (it is in Expo Router's types). But a tab bar whose tabs come and go is confusing, and a guest who sees "Sign in to see your cleanups" learns what the app offers. Guard whole screens that make no sense for a guest; give tabs a signed-out face.

What does an organizer see when they sign in on the phone?

The same app, with "Signed in as an organizer" on Profile. The API accepts organizers, and the phone app is built for volunteers; organizers' planning tools stay in the HQ. If you want a volunteer to try, the API's sample volunteers all use the password shoreline-demo (the API reference lists them).
