👆 Lesson 8.3: Testing Screens and Flows

A volunteer never calls sendWaitingLogs(). They tap a switch, type an email with cold fingers, wait for a list on one bar of signal, and read a tab that says one log has not gone out yet. Last lesson proved the decisions underneath; today you test what the volunteer actually touches: screens rendered in the same pretend phone, found by the names a screen reader would speak, pressed and typed into like a person would. Then you write the one test that runs the real app on a real device, end to end.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Write component tests with React Native Testing Library 14 and explain what changes from the web course's Testing Library: async render, userEvent.press, built-in matchers, no DOM

  • Render Expo Router screens with renderRouter, together with TanStack Query and the HQ's mock API, and handle the fake clock it switches on
  • Test hooks with renderHook and play the phone in a test: text size, platform, screen reader announcements
  • Describe an end-to-end test with Maestro, write a flow for Shoreline Crew, and say where such a flow can run
  • Decide what is worth a test, and read a coverage report without chasing its number

👋 Welcome: Tests That Tap

Lesson 8.2 left Shoreline Crew with 28 tests for its logic and a test setup that makes Node feel like a phone: Expo's preset, Node's fetch put back, the HQ's mock API answering, stand-ins for the native modules. Everything today runs on that setup. What is new is the subject: not functions, but what appears on the screen, and what happens when someone touches it.

You know this kind of test from Lessons 9.1 and 9.2 of the web course: render a component, find things the way a person does, act with user-event, wait for the result. React Native has its own version of the library, React Native Testing Library (RNTL), written in the same spirit and close enough in its names that most of your habits carry over. The differences are the interesting part, and each one says something about phones. By the end of the lesson:

  • Component tests keep the promises Lesson 8.1 made: a switch row flips exactly once, live texts are announced on an iPhone, the large-text layouts switch on at the right size.
  • Screen tests render real Shoreline Crew screens under Expo Router: the sign-in modal, the Cleanups list with TanStack Query and the mock API, and the tab bar with its "not sent yet" count.
  • An end-to-end flow for Maestro walks the real app on a device: open it, sign in, see your name, sign out.

Why it matters for your work: screen tests are where mobile teams catch the bugs users report: the button that stopped working after a refactor, the error message that never appears, the screen that hangs on "Loading…". And because Lesson 8.1 gave every control a name, your tests can find them by those names, which makes every test a small accessibility check too. Teams that test this way notice when a label disappears, because a test breaks.

🌱 You already know most of this

If a lot of today's code looks familiar, that is the point: the web course's testing habits are worth keeping, and you are learning a dialect, not a new language. When something does not work the way it did on the web, the terminal will say so, usually with the whole tree of the screen printed underneath. Read the tree. It is the test's eyes, and once you can read it, every "Unable to find an element" becomes a puzzle with the answer on the page.

🔁 From Testing Library to React Native Testing Library

RNTL was installed in Lesson 8.2 (@testing-library/react-native 14.1). npm also added Test Renderer (test-renderer 1.3, matching React 19.3), the piece that renders components into memory instead of onto a screen; RNTL lists it as a peer dependency, and npm installs those for you. Here is what changes from the HQ's tests:

Two rows deserve a closer look, because they decide how you write every test today.

Queries see what a screen reader sees

In Lesson 8.1, SwitchRow became one control: the words on the left are aria-hidden, and the switch carries them as its accessibilityLabel. RNTL respects that. getByRole('switch', { name: 'Group by date' }) finds the switch, while getByText('Group by date') finds nothing, because a screen reader would never land on those words. That is a feature: if a test can find a control by its role and name, so can VoiceOver and TalkBack. When you really need a hidden element (to tap the words, as a finger can), you say so: { includeHiddenElements: true }.

Presses follow the touch system

user.press() does not just call onPress. It walks the touch events the way React Native does (press in, press out, then press), and it respects pointerEvents: an element that does not take touches passes them to its parent. In SwitchRow, the switch has pointerEvents: 'none', so a press on it reaches the row's Pressable, exactly as a finger does on a phone. A screen reader is different: VoiceOver or TalkBack flip the native switch directly, which reports a valueChange event. One test can try both paths, which is how Lesson 8.1's promise "the row flips exactly once" gets checked.

💡 Mental model: the radio call, heard by the test

Lesson 8.1 described what a screen reader says as a radio call: label, role, state ("Group by date, switch, off"). An RNTL query is a crew member listening to that radio. getByRole('switch', { name: 'Group by date' }) means "I heard a switch called Group by date", and toBeChecked() means "and it said on". If the call is garbled (no role, no name, the words twice), the test cannot find the control either. Write tests that listen to the radio, not tests that peek at the wiring (testID, style values, component names), and your tests and your accessibility improve together.

📱 Playing the Phone in a Test

Component tests run in the same pretend phone as Lesson 8.2's logic tests. Three things about it matter for screens, and each was found by reading the setup files in node_modules, not by guessing:

  • The window. React Native's Jest preset says the window is 750 by 1334 points, with text at twice its normal size (fontScale: 2). So under Jest, out of the box, useLargeText() is true and useColumns() gives two columns: a tablet with large text, not a phone. Shoreline Crew's setup file sets a phone-sized window (390 by 844, fontScale 1) before every test, and tests that care about text size change it.
  • The platform. As in Lesson 8.2, jest-expo runs as an iPhone: Platform.OS is 'ios'. A test can switch it for itself with jest.replaceProperty(Platform, 'OS', 'android'), and put it back with jest.restoreAllMocks().
  • The accessibility services. React Native's Jest setup already replaces AccessibilityInfo with stand-ins that do nothing and remember their calls. jest.mocked(AccessibilityInfo.announceForAccessibilityWithOptions) lets a test ask "what did the app ask VoiceOver to say?"

The phone also sends the app news: the window turned, the person made the text bigger. On a device, React Native's native side reports those changes through Dimensions.set(), and every useWindowDimensions() re-renders. In a test, you call it yourself, inside act() so React finishes the re-render before you look:

shoreline-crew/src/hooks/useLargeText.test.ts
// What the phone tells the app when the person changes the text size in Settings
function changeTextSize(fontScale: number) {
  const window = { ...Dimensions.get('window'), fontScale };
  Dimensions.set({ window, screen: window });
}
  ...
  await act(() => changeTextSize(2)); // the largest size on many Android phones
  expect(result.current).toBe(true);

Hooks are tested with renderHook(), as in the HQ (now awaited): it renders a tiny component that calls the hook and keeps its latest return value in result.current. Step 3 uses it for useLargeText().

⚠️ A pretend phone answers what you tell it

A test that sets fontScale to 2 proves that Shoreline Crew switches layouts at 2. It does not prove that an Android phone at its largest text size reports 2 (newer Android versions scale text non-linearly), or that the layout looks good there. Lesson 8.1's checks on a phone, and an end-to-end flow on a device, cover that side.

🗺️ Screens Under Expo Router

A Shoreline Crew screen is not a component you can render on its own. The Cleanups list has Links on its cards, the sign-in modal calls router.back(), the form reads the header's height, and the tab bar is a navigator. In the HQ, Lesson 9.2 wrapped pages in a memory router. Expo Router ships the equivalent: expo-router/testing-library, which works with SDK 58 (checked for this lesson with expo-router 58.0.31 and RNTL 14.1). It gives you three things:

  • renderRouter(routes, { initialUrl }) renders a whole app made of the routes you give it, written like file names in src/app: { _layout: () => <Stack />, index: CleanupsScreen, 'sign-in': SignInScreen }. Real screens from your app sit next to small stand-in screens, so a test renders only what it is about.
  • testRouter: push, back, replace and friends, each wrapped in act() and followed by a check of the new address.
  • Router matchers: expect(screen).toHavePathname('/'), toHaveSegments(), toHaveSearchParams().

The diagram shows what one screen test puts together. Only the edges are pretend: the routes you list, and the mock API.

graph TD T["A screen test"] --> R["renderRouter: routes"] R --> S["A real screen"] S --> Q["TanStack Query"] Q --> F["fetch: Node's"] F --> M["MSW: the HQ's handlers"] S --> U["Seen by the queries"] U --> T

Three things to know before the first screen test

  • Where the tests live. Never in src/app/ (Expo Router would treat a test file as a route, according to Expo's documentation). Shoreline Crew keeps screen tests in src/test/screens/, next to the helpers they use.
  • The cache. Screens read data through TanStack Query, so a screen test needs a QueryClientProvider. The helper you write in Step 4 uses the app's own queryClient, because mutations.ts refreshes data through that exact object; each test file clears it after every test, so nothing cached leaks into the next test.
  • The clock. renderRouter switches Jest to fake timers (read in its source: it makes navigation finish at once). A fake clock is welcome for the app's own timers (the 1 and 2 second pauses before Query tries again run instantly), but Jest's fake timers also freeze process.nextTick and queueMicrotask, the tiny "right after this" steps Node's fetch and MSW use to finish a request. With those frozen, a screen waits on "Loading cleanups…" forever. One line in the Jest settings tells every fake clock to leave those two alone: "fakeTimers": { "doNotFake": ["nextTick", "queueMicrotask"] } (Step 1).

💡 Mental model: a rehearsal stage with real props

A theater rehearses on a bare stage: tape on the floor where the walls will be, a chair standing in for the throne. But the actor's script and the props in their hands are the real ones. A screen test is that rehearsal. The route list is the tape on the floor (a plain <Stack />, a stand-in Profile screen), while the screen under test, its form, its cache and the API's rulebook are real. If the play works on the bare stage, the parts you rehearsed are right; the full dress rehearsal on the real stage is the end-to-end flow.

🎬 End to End with Maestro

Everything so far ran in Node. An end-to-end test runs the real app, built for a real phone or emulator, and drives it from outside like a person would: taps, typing, waiting, looking. In the HQ, Lesson 9.3 of the web course did this with Playwright in a real browser. For phone apps, a popular choice with Expo is Maestro, an open-source tool from mobile.dev: you write each test as a short YAML file called a flow, and Maestro runs its steps on a device through the phone's own automation and accessibility layer.

Playwright in the HQMaestro in Shoreline Crew
A test file in TypeScriptA flow in YAML (.maestro/sign-in.yaml)
page.goto('/')launchApp for a built app; openLink to the project's exp:// address in Expo Go
getByRole('button', { name: 'Sign in' }).click()tapOn: Sign in: matches what is written on screen or the accessibility label
fill('theo…')tapOn: Email, then inputText: theo…
expect(…).toBeVisible(), auto-waitingassertVisible: Theo Nakamura; Maestro waits for the screen to settle on its own; extendedWaitUntil waits longer
npx playwright testmaestro test .maestro/sign-in.yaml

According to Maestro's documentation, tapOn: Sign in matches the visible text or the accessibility label (Android's contentDescription, iOS's accessibilityLabel) exactly, and is a regular expression, so .* makes a partial match. That is why the flow in Step 7 taps Profile.*: on an iPhone, the tab's accessibility name is "Profile, tab, 4 of 4" (Step 6 shows it). That is also why the names from Lesson 8.1 pay off a second time: Maestro finds controls through the same accessibility information a screen reader uses.

Where a flow can run (and where it cannot)

Maestro is a command-line program (it needs Java 17 or newer). Its documentation installs it with one curl command on macOS, Linux and WSL (or Homebrew on a Mac), and from a zip file on Windows; there is also a desktop app, Maestro Studio, for building and inspecting flows. It needs a device to drive. According to Maestro's documentation, at the time of writing:

  • Android: an emulator or an Android phone connected over USB with developer options on. Works from macOS, Linux and Windows.
  • iOS: the iOS Simulator, which needs a Mac with Xcode. Its setup guides cover simulators; check its current documentation before planning tests on real iPhones.
  • In the cloud: Maestro Cloud (a paid service from Maestro's makers) runs flows on their devices, and EAS Workflows can run Maestro flows against an EAS build on Expo's servers (Module 9 introduces EAS; check Expo's current plans and prices). Neither is needed for this course.

And the app it drives: Expo Go works for trying a flow locally (Maestro's React Native page says to open your project's exp:// address with openLink, since the app runs inside Expo Go), but teams run end-to-end tests against a development or preview build of the app, which has its own app id and does not depend on Metro running on your computer. Module 9 builds those.

📱 On your phone

This course's checks cannot run Maestro (there is no emulator or simulator on the machine the course was built on), so the flow in Step 7 is written from Maestro's documentation and checked only as YAML. If you have an Android emulator, an Android phone or a Mac, run it: it should open Expo Go, load Shoreline Crew, sign Theo in on the Profile tab, show his name, save a screenshot called signed-in.png and sign him out again. If a step cannot find its element, Maestro Studio's Inspect Screen shows the screen as Maestro sees it, with the text and labels it can match.

🎯 What Is Worth a Test

Shoreline Crew now has three kinds of tests, and each has its own job:

KindSpeed and costShoreline Crew today
Logic (Lesson 8.2)Milliseconds; no screenThe queue, the sender, schemas, reminders, the CSV file
Components and screens (today)Tens of milliseconds; a pretend phoneSwitch rows, live texts, large text, sign-in, the Cleanups list, the tab bar
End to end (today)Seconds to minutes; a device and a buildOne flow: sign in and out

Most tests should be the fast kinds. Write a screen test when a screen makes a decision a volunteer depends on: what to show while loading, after an error, for a guest; what a press does; which name a control has. Keep end-to-end flows for the few paths that must work on a real device every release (sign in, sign up for a cleanup, send a log), because they are slow and they break when the device is slow.

Do not write tests for:

  • Styles and pixels. A test that checks backgroundColor: '#1f6f8b' breaks on every redesign and says nothing about whether the screen looks right. Look at the screen instead (and Lesson 8.1's contrast checks).
  • Whole-tree snapshots. toMatchSnapshot() on a screen records hundreds of lines nobody reads; when it fails after a harmless change, people update it without looking. A small, named expectation says what matters.
  • Libraries. That FlashList recycles, that Query caches, that Expo Router navigates: their authors test that.
  • Implementation details. State variable names, how many times a component rendered, private functions. Test what a person sees and does.

Coverage (npm test -- --watchAll=false --coverage) lists, per file, how many lines and branches the tests ran. Use it to find code no test ever touches, then decide whether that code matters. A high number is not a goal: a test can run every line of a screen without checking anything a volunteer cares about.

🛠️ Project: Tests a Volunteer Would Recognize

// A screen's part: SwitchRow shows the value it is given, so the test keeps it in state, as

function GroupByDate({ onChange }: { onChange: (value: boolean) => void }) {

Step 4: Screens under the router: sign in (20 min)

First, a helper, the phone app's version of the HQ's renderWithProviders. Create src/test/render.tsx (.tsx: it has JSX):

shoreline-crew/src/test/render.tsx
// Render some of the app's screens in a test, the way Expo Router shows them (the HQ's
// renderWithProviders, for a phone app)
import { QueryClientProvider } from '@tanstack/react-query';
import { type MockContextConfig, renderRouter } from 'expo-router/testing-library';
import type { ReactNode } from 'react';

import { queryClient } from '@/api/queries';

// The providers the screens need from the root layout. The app's own queryClient, with its
// settings: mutations.ts refreshes data through it. Each test file clears it after each test.
function Providers({ children }: { children: ReactNode }) {
  return <QueryClientProvider client={queryClient}>{children}</QueryClientProvider>;
}

/**
 * Show `routes` (file names as in src/app, each with its screen) at `initialUrl`. The result has
 * RNTL's queries plus the router's: getPathname(), and toHavePathname() for expect(screen).
 */
export function renderScreens(routes: MockContextConfig, initialUrl = '/') {
  return renderRouter(routes, { initialUrl, wrapper: Providers });
}

MockContextConfig is Expo Router's type for the route list (it also accepts a folder path, which renders a real app folder; Shoreline Crew's root layout loads fonts, the saved session and the queue, so its tests list routes instead). wrapper is RNTL's render option: the providers go around Expo Router's root, as they do in _layout.tsx.

  await showCleanups();
  // The app tries three times, 1 and 2 seconds apart, before it gives up: Jest's fake clock
  // runs those seconds at once, but they count against findBy's 1-second limit
  const tryAgain = await screen.findByRole('button', { name: 'Try again' }, { timeout: 5000 });

🏋️ Exercise 1: The failed-load view

ErrorView (Lesson 3.1) shows a message and a Try again button on several screens. Write src/components/ErrorView.test.tsx: the message must be an alert (so screen readers say it at once), and one press on Try again must call onRetry once.

💡 Hint

getByRole('alert') finds the message; toHaveTextContent() checks its words. Pass jest.fn() as onRetry.

✅ Solution 
import { render, screen, userEvent } from '@testing-library/react-native';

import { ErrorView } from '@/components/ErrorView';

it('says what went wrong as an alert, and tries again once per press', async () => {
  const onRetry = jest.fn();
  const user = userEvent.setup();
  await render(<ErrorView message="Could not reach the server." onRetry={onRetry} />);
  expect(screen.getByRole('alert')).toHaveTextContent('Could not reach the server.');
  await user.press(screen.getByRole('button', { name: 'Try again' }));
  expect(onRetry).toHaveBeenCalledTimes(1);
});

No router and no cache: ErrorView is a plain component, so plain render is enough. Use renderScreens only when a component needs the router.

🏋️ Exercise 2: Grouped by date

The Cleanups screen's "Group by date" switch (Lessons 3.1 and 3.2) puts the cards under headings such as "Today" and "Within a week". Add a test to cleanups.test.tsx: after pressing the switch, there is a "Today" heading and a "Within a week" heading, and still eight cards.

💡 Hint

The headings are AppText with accessibilityRole="header", so getByRole('header', { name: 'Today' }) finds one. FlashList keeps a pinned copy of the current heading at the top: if a query finds two, which one does the test care about?

✅ Solution 
it('groups the cards under date headings', async () => {
  const user = userEvent.setup();
  await showCleanups();
  await screen.findByText('8 cleanups');
  await user.press(screen.getByRole('switch', { name: 'Group by date' }));
  expect(screen.getAllByRole('header', { name: 'Today' }).length).toBeGreaterThan(0);
  expect(screen.getByRole('header', { name: 'Within a week' })).toBeOnTheScreen();
  expect(openLinks()).toHaveLength(8); // the same cards, now in groups
});

The query finds two "Today" headings: the one in the list and the copy FlashList pins at the top of the screen (Lesson 3.2's sticky headings). The test only cares that the heading is there, so it uses getAllByRole; "Within a week" is not pinned yet, so getByRole finds exactly one. The cards stay the same eight: grouping changes the order and the headings, never which cleanups are shown.

🏋️ Exercise 3: The hook that sends the queue (Stretch)

useSendWaitingLogs() (Lesson 5.5) sends the waiting logs when someone is signed in, and again whenever the phone comes back online. Lesson 8.2 tested sendWaitingLogs() itself; test the hook with renderHook in src/hooks/useSendWaitingLogs.test.ts: a waiting log is sent at once; a log written while offline is sent when the connection returns; nothing is sent with nobody signed in.

💡 Hint

Reuse Lesson 8.2's sender setup: startMockApi(), jest.mock('@/storage/logbook'), the queue reset and setSession(volunteer). Flip onlineManager.setOnline() inside act(), and wait for the queue to empty with waitFor(): the hook sends in the background.

✅ Solution 
import { onlineManager } from '@tanstack/react-query';
import { act, renderHook, waitFor } from '@testing-library/react-native';

import { setSession } from '@/api/client';
import { useSendWaitingLogs } from '@/hooks/useSendWaitingLogs';
import { useLogQueue } from '@/state/logQueue';
import { makeLogToSend, volunteer } from '@/test/factories';
import { recordRequests, startMockApi } from '@/test/server';

jest.mock('@/storage/logbook'); // no SQLite in Jest: the sent logs go nowhere

startMockApi();
beforeEach(() => {
  useLogQueue.setState(useLogQueue.getInitialState());
  setSession(volunteer);
  onlineManager.setOnline(true);
});

function queueLog(clientId: string) {
  useLogQueue.getState().add(volunteer.user.id, makeLogToSend(clientId), []);
}

it('sends the waiting logs at once, and again when the phone is back online', async () => {
  queueLog('log-0001');
  const requests = recordRequests();
  await renderHook(() => useSendWaitingLogs(volunteer.user.id));
  await waitFor(() => expect(useLogQueue.getState().logs).toEqual([]));

  await act(() => onlineManager.setOnline(false));
  queueLog('log-0002'); // written on the beach, with no signal
  await act(() => onlineManager.setOnline(true));
  await waitFor(() => expect(useLogQueue.getState().logs).toEqual([]));
  expect(requests).toEqual(['POST /api/events/e17/logs', 'POST /api/events/e17/logs']);
});

it('sends nothing while nobody is signed in', async () => {
  queueLog('log-0001');
  const requests = recordRequests();
  await renderHook(() => useSendWaitingLogs(null));
  expect(requests).toEqual([]);
});

The hook does not return anything, so the test watches its effects: the queue and the requests. waitFor() retries the expectation until it passes (or times out), which is how a test waits for work that a hook starts without returning a Promise.

❓ Common Questions at This Stage

Should I use testID instead of names?

Prefer roles, names and visible text: they are what a person (and a screen reader) uses, and a test that finds them is an accessibility check for free. testID (which Maestro's React Native guide recommends) is a fallback for things that have no good name, like a decorative view whose size you must check, or several identical controls; RNTL finds it with getByTestId and Maestro with id:. If you reach for testID because a button has no name, give the button a name instead.

Why not render the whole app, root layout and all, with renderRouter('./src/app')?

You can point renderRouter at a folder, and for small apps that is a good start. Shoreline Crew's root layout waits for fonts, reads the session from SecureStore, loads the settings and the queue, starts reminders and the log sender: every test would need stand-ins for all of it, and each test would be about everything at once. Listing the routes keeps each test about one screen. The end-to-end flow is where the whole app runs together.

Is fireEvent wrong now that there is userEvent?

No, it is lower level. user.press() plays the whole touch (press in, press out, press) and respects pointerEvents and disabled controls, so prefer it for what a person does. fireEvent sends exactly one event by name, which is right for events no finger makes: a native switch reporting valueChange after a screen reader flipped it, a scroll view's onScroll, a RefreshControl's onRefresh.

Maestro or Detox?

Detox (from Wix) is the other well-known end-to-end tool for React Native. It runs tests written in JavaScript, synchronizes closely with the app, and needs the app built with its own setup, which in an Expo project means a development build and a config plugin. Maestro needs no changes to the app and flows are YAML, which is why many Expo teams start there. Both need a device or emulator; pick the one your team will actually keep running.

The web preview runs in a browser. Could Playwright test it, as in the HQ?

Yes, and this course's own checks do exactly that: every lesson's stage is exported for the web and checked in Chromium. It is a good test of data, navigation and forms, but it runs react-native-web, not the phone's native views: no native tab bar, no keyboard, no permissions, no gestures as they feel on a phone. Treat it as one more fast check, not as an end-to-end test of the phone app.

📝 Lesson Summary

🎓 Key Takeaways

  • React Native Testing Library 14 is the web's Testing Library for native views: render, renderHook, fireEvent and act are async; userEvent presses, types and clears; matchers like toBeOnTheScreen() are built in
  • Queries see what a screen reader sees: find controls by role and name, and expect hidden elements (and screens behind a modal) to be skipped unless you ask for them
  • user.press() follows React Native's touch rules, pointerEvents included; fireEvent sends one named event, such as a screen reader's valueChange
  • The pretend phone is a 750-point window with text at twice its size until your setup says otherwise; Dimensions.set(), jest.replaceProperty(Platform, 'OS', …) and the AccessibilityInfo stand-ins let a test play the phone
  • expo-router/testing-library works on SDK 58: renderRouter with a list of routes, testRouter, toHavePathname; it switches on fake timers, so keep nextTick and queueMicrotask real for requests
  • Maestro flows are YAML steps that drive the real app on an Android emulator or phone or an iOS Simulator; use them for the few paths that must work on a device
  • Test decisions a person depends on, by what they see and do; skip styles, snapshots, library behavior and implementation details; read coverage per file, as a map of what never ran
